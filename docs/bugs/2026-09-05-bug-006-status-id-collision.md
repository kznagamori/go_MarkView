## 1. 症状

利用者が E2E-225（Markdown 以外のドロップ）を実施する過程で、次の 3 つを観測した。

| # | 操作 | 結果 |
| --- | --- | --- |
| 1 | **ファイルを開いていない状態**で画像をドロップする | **正常。** ステータス領域に英語のエラーメッセージが出る |
| 2 | `testdata/showcase.md` を表示する | ステータス領域が `[ 109 ms] PlantUML version $version$ / $git.commit.id$ [Unknown compile time]` に変わる |
| 3 | 2 の状態で画像をドロップする | **ステータス領域が更新されない。** エラーメッセージが出ない |

観測 2 の文字列は MarkView が持つ文言ではない。**`js/strings.js` にも Go 側のエラー値にも存在しない**（IMP-290, UI-024）。

> [!IMPORTANT]
> **観測 1 と 3 の違いが決定的である。** ドロップの処理（BUG-001 で直した経路）は正しく動いており、
> **エラーは Go から届いているのに、それを表示する側が壊れている。**
> 「ドロップが効いていない」ように見えるが、原因はドロップとは無関係である。

---

## 2. 原因

### 2.1 同梱している PlantUML が `#status` を決め打ちで書き換える

`frontend/vendor/plantuml/plantuml.js`（@plantuml/core 1.2026.7 を TeaVM で JavaScript へ移植したもの）に、次のログ出力関数がある。

```js
BMA = b => {
  console.log(b);
  var el = document.getElementById('status');
  if (el) { el.textContent = b; }
}
```

- **`document` 直下から ID で要素を探し、見つかったら `textContent` を上書きする。**
- 呼び出し元は描画処理の末尾であり、**成功したときもエラー図を返したときも呼ばれる**（3 か所すべてが `render` の完了経路にある）。
- 渡される文字列は「経過時間 + 版情報」である。`$version$` と `$git.commit.id$` が展開されていないのは、**この TeaVM 移植版が Maven のプロパティ置換を経ていない**ためで、それ自体は異常ではない。

これは PlantUML の公式デモページ（`<div id="status">` を持つ）向けの配線が、ライブラリ本体に残ったものである。**利用側が知らないうちに、任意のページの `#status` を書き換える。**

### 2.2 MarkView の `index.html` は `<footer id="status">` を使っている

```html
<footer id="status" class="status">
  <span id="status-path"    class="status-path"></span>
  <span id="status-meta"    class="status-meta"></span>
  <span id="status-message" class="status-message" hidden></span>
</footer>
```

**ID が完全に一致する。** これは偶然だが、どちらも「状態を出す場所」という同じ意味で `status` を選んだ結果であり、**衝突しやすい名前**である。

### 2.3 何が起きるか

`el.textContent = b` は、**その要素の子ノードをすべて破棄して 1 つのテキストノードに置き換える**（DOM の仕様）。したがって PlantUML が 1 枚描いた時点で、

1. ステータス領域の表示が PlantUML のログ 1 行に置き換わる（**パス・文字コード・行数・倍率がすべて消える**。UI-060, DSP-150 に反する）
2. **`#status-path` / `#status-meta` / `#status-message` の 3 要素が DOM から消える**

2 の結果、ステータス領域を触る自前のコードは**すべて例外で落ちる**。

```js
// js/status.js
export function showMessage(text, level) {
  if (!text) return;
  const element = $("status-message");   // → null
  element.textContent = text;            // → TypeError
  ...
}

export function updateStatus() {
  const path = $("status-path");         // → null
  const meta = $("status-meta");         // → null
  clear(meta);                           // → clear() の node.firstChild で TypeError
  ...
}
```

`clear` は `while (node.firstChild)` であり、`null` を渡せばその場で落ちる（`js/util.js`）。

**この状態は文書を開き直しても直らない。** `#status` の中身は PlantUML が書いたテキストノード 1 つのままで、
**誰も作り直さないためである。** ページ全体を読み込み直す（アプリを再起動する）まで続く。

### 2.4 なぜ 5 秒で消えないのか

一時メッセージは 5 秒で消える規定がある（DSP-151）。しかし PlantUML が書いたのは `#status-message` ではなく
**`#status` 自身のテキストノード**であり、`showMessage` のタイマとは無関係である。**消える仕組みが無い。**

### 2.5 なぜ表示の直後ではなく少し遅れて壊れるか

`viewer.js` の `showDocument` は次の順で進む。

| 段階 | 内容 |
| --- | --- |
| 8 | `drawPlantUML(markdown)` を**待たずに**呼ぶ（NFR-012, NFR-013） |
| 10 | `updateStatus()` — **この時点ではまだ正常**。パスと行数が正しく出る |
| （非同期） | `ensurePlantUML()` が約 5 MiB の資産を読み、描画し、**最後に `BMA` がステータス領域を潰す** |

そのため「文書を開くと一瞬だけ正しく出て、図が描けた頃にログ 1 行へ変わる」という見え方になる。

### 2.6 3 つの観測がすべて説明できる

| 観測 | 説明 |
| --- | --- |
| 1. 文書なしのドロップは正常 | PlantUML が一度も動いていないため `#status` は無傷。`showMessage` が正しく働く |
| 2. `showcase.md` でログが出る | `showcase.md` には PlantUML ブロックが **2 つ**あり、描画のたびに `BMA` が呼ばれる |
| 3. その後の更新が効かない | `#status-message` が消えており、`showMessage` が `TypeError` で落ちる。**エラーは届いているが表示できない** |

### 2.7 衝突しているのは `status` だけである

同梱資産が決め打ちで参照する ID を全部洗い出し、`index.html` の 51 個の ID と突き合わせた。

| 資産 | 決め打ちの `getElementById` | MarkView に同名の要素があるか |
| --- | --- | --- |
| `plantuml/plantuml.js` | **`status`** | **ある（衝突）** |
| `mermaid/mermaid.min.js` | `cy` | 無い（いまは無事） |
| `katex/katex.min.js` | なし | — |
| `plantuml/viz-global.js` | なし | — |

> [!WARNING]
> **Mermaid にも同じ形の決め打ちがある**（`cy`）。いま無事なのは、たまたまその名前を使っていないからである。
> **同じ事故が別の名前で再発しうる。** 5.6 に再発防止を書く。

## 3. 原因の分類 — 仕様か、実装か

### 3.1 一次原因 — **実装の誤り**（`index.html` の ID）

`<footer id="status">` は、**外部から書き換えられうる名前**である。同梱資産をページに読み込む以上、
グローバルな名前空間である ID は共有される。**ここは自前で避けられた。**

「PlantUML が悪い」とは言えるが、**BR-042 が `plantuml.js` の改変を禁じている**以上、こちらが避けるしかない（5.3）。

### 3.2 仕様も同じ ID を定めている — **同時に直す**

`docs/specs/12-impl-frontend.md` の **IMP-202** が骨格として `<footer id="status" class="status">` を明記している。
**実装だけ直すと仕様と食い違う**（NFR-071）。

### 3.3 仕様の不足 — 「同梱資産がページのグローバルな状態を触りうる」ことがどこにも書かれていない

`IMP-230` / `IMP-233` は PlantUML の**呼び方**（読み込み順・完了検知・出力先の渡し方）を細かく定めているが、
**「処理系が渡した要素の外へ書くことがある」**という前提が無い。

- `IMP-233` は「出力先は要素の ID で渡す」「独自に HTML を組み立てて挿入しない」と定め、**DOM へ書くのは処理系である**ことを明示している
- しかし**書く先が「渡した要素だけ」だとは、どこにも保証がない**

**この暗黙の前提が破れたのが本件である。** 仕様に前提として書いていれば、ID の付け方を選ぶ段で気づけた。

## 4. なぜ単体テストと E2E の自動テストで見つからなかったのか

### 4.1 単体テスト — 対象外

`UT-002` が単体テストの対象を `internal/` に限っている。本件は
**`frontend/index.html` と同梱資産の相互作用**であり、Go のコードは 1 行も関わらない。

`docs/specs/31-test-cases.md` 31.10 の対応表も、UI-060 / DSP-150 / DSP-151 の行は GUI である。

### 4.2 描画スモークテスト — **`index.html` を読まないため、構造的に起こり得ない**

**これが決定的な理由である。**

`scripts/smoke`（BR-054, E2E-109）は PlantUML を実際に描画する唯一の自動テストであり、**本件の引き金である `render()` を毎回呼んでいる。**
それでも検出できないのは、配るページが違うからである。

| 項目 | 実物 | 描画スモークテスト |
| --- | --- | --- |
| ページ | `frontend/index.html` | `scripts/smoke/harness.html`（独自） |
| `id="status"` の要素 | **ある** | **無い**（`status` を含む文字列が 1 つも無い） |
| `BMA` の分岐 | `if (el)` が **真** → 書き換える | `if (el)` が **偽** → **何も起きない** |

つまり **`plantuml.js` の当該 1 行は、スモークテストでは常に空振りする。**
テストが弱いのではなく、**その行に到達できない形になっている。**

> [!IMPORTANT]
> **P9（検索バーの不具合）と同じ構図である。** あのときも
> 「描画スモークテストは `index.html` を読まない。`_smoke.html` という独自のページを配っている」ことが原因で、
> 構造の変更を見ているのがハーネスだけだった。
> **同じ穴に 2 回落ちている。** 5.6 で再発防止を扱う。

### 4.3 自動 E2E — UI を操作しない

`E2E-002` が「自動テストは UI を操作しない」と定めている。`scripts/e2e` は配布物の構成・起動・終了・CLI を見るだけで、
**ウィンドウの中を見ない。** ステータス領域の内容は対象外である。

### 4.4 手動テスト（rc.2）でも見つからなかった

**同梱資産は rc.2 と同一である**（`vendor.json` の PlantUML 1.2026.7 / fetched 2026-09-03）。
**rc.2 にも同じ不具合が入っていた**が、67 件のどれも NG にならなかった。理由は 2 つある。

1. **PlantUML のケース（E2E-239 / E2E-240）は「図が描けたか」しか見ていない。** 確認内容にステータス領域が出てこない
2. **ステータス領域を見るケース（E2E-211 / E2E-221 など）は、PlantUML を含まない文書で実施する**

**「PlantUML を描いた後にステータス領域を見る」という順序が、どのケースにも無い。**
今回見つかったのは、利用者が E2E-225 を**表示中の文書を `showcase.md` にしたまま**実施したためである。

### 4.5 仕様レビューでも見つからなかった

`IMP-202` の ID 一覧と、同梱資産が使う ID を突き合わせる検査項目が無い。
**そもそも「同梱資産が ID を決め打ちする」ことを誰も見ていない。**

### 4.6 まとめ

| 層 | 捕まえられたか | 理由 |
| --- | --- | --- |
| 単体テスト | **できない** | 対象が `internal/` のみ（UT-002）。Go は関わらない |
| 描画スモーク | **できない** | `index.html` を配らないため `if (el)` が常に偽（4.2） |
| 自動 E2E | **できない** | UI を操作しない（E2E-002） |
| 手動テスト | **できたはず** | PlantUML の後にステータス領域を見る手順が無かっただけ（4.4） |
| 仕様レビュー | **できたはず** | 資産の決め打ち ID と自前 ID の突き合わせは**機械的にできる**（2.7 で実際に行った） |

## 5. 修正方法

### 5.1 案 1（推奨）— ステータス領域の ID を改名する

`index.html` の 1 行を変える。

```html
<footer id="statusbar" class="status">
```

**影響はこれだけである。** 実際に確かめた。

| 参照元 | `status` を使っているか |
| --- | --- |
| `frontend/js/*.js` | **使っていない**（参照するのは `status-path` / `status-meta` / `status-message` の 3 つ） |
| `frontend/css/*.css` | **使っていない**（`.status` というクラス名で書かれている） |
| `frontend/index.html` | 150 行目の 1 か所のみ |

- **子要素（`status-path` 等）は改名しなくてよい。** 決め打ちされているのは `status` だけである（2.7）
- 改名後は `#status` を持つ要素が無くなり、`BMA` の `if (el)` が偽になって**何も起きなくなる**

### 5.2 案 2 — ID を消す

`<footer class="status">` とする。JavaScript も CSS も参照していないため、消しても動く。

**採らない。** `IMP-202` の骨格は主要な領域すべてに ID を与えており、ここだけ外すと一貫性が崩れる。
将来ステータス領域を触る必要が出たときに、**同じ名前で戻される危険**もある。

### 5.3 採らない案 — `plantuml.js` を改変する

**禁止されている。**

- `BR-042` は同梱資産を**改変せずに格納する**ことを前提としている
- `BR-043` がリリース CI（rc タグ）で資産を**自動更新する**ため、手で当てた修正は**次の rc で消える**
- 消えたことに気づく手立てが無い。**最悪の直し方である**

### 5.4 採らない案 — `status.js` を null 安全にするだけ

`if (!element) return;` を足せば例外は止まる。**しかし根治ではない。**

- ステータス領域の中身が消える事実は変わらない（パス・文字コード・行数が出なくなる。UI-060, DSP-150）
- PlantUML のログが利用者に見えたままになる（UI-024, IMP-290 に反する。**MarkView の文言ではない**）
- 「壊れているのに静かに動く」状態になり、次に誰かが気づく機会を奪う

**案 1 と併用する価値もない。** ID が衝突しなければ `null` にはならず、`null` になったとすれば
それは `index.html` と `status.js` の食い違いという別の不具合であり、**そのときは落ちたほうがよい。**

### 5.5 あわせて直すべき仕様

**NFR-071 に従い、同じ変更で仕様書も直す。**

| 文書 | 直す内容 |
| --- | --- |
| `12-impl-frontend.md` **IMP-202** | 骨格の `<footer id="status">` を新しい ID にする。**なぜその名前にできないのかを NOTE で残す**（消すと、次の改訂で戻される） |
| `12-impl-frontend.md` **IMP-230 / IMP-233** | **「同梱資産は、渡した要素の外にも書くことがある」**ことを前提として明記する。`plantuml.js` が `#status` を決め打ちで書き換える実例を添える |
| `06-build-release.md` **BR-042 / BR-043** | 資産を更新したときに、**決め打ちの ID が増えていないか**を確かめる手順を足す（5.6） |
| `41-e2e-manual.md` **E2E-239 / E2E-240** | 確認内容に「**図を描いた後もステータス領域が正しい**（パスと行数が出ている）」を足す。4.4 のとおり、この順序の確認がどのケースにも無い |
| `docs/specs/README.md` | 改訂履歴に 1 行追加し、版を上げる（NFR-071） |

### 5.6 再発防止 — 決め打ち ID の衝突を機械的に検査する

2.7 で行った突き合わせは**完全に機械的**である。

```bash
# 同梱資産が決め打ちする ID を洗い出す
grep -ohE "getElementById\('[^']+'\)" frontend/vendor/**/*.js | sort -u

# index.html の ID と突き合わせる（交差が空であること）
```

- `BR-043`（資産の自動更新）の後に走らせるのが自然である。**資産が変われば決め打ちも変わりうる**
- Mermaid の `cy`（2.7）は、いま**たまたま**無事なだけである。**検査があれば「たまたま」でなくなる**
- **`scripts/smoke` に足すのが素直**である。あちらは既に同梱資産を読み込んでおり、ID の一覧も持てる

> [!NOTE]
> **4.2 の「スモークテストが `index.html` を読まない」問題そのものには踏み込まない。**
> ハーネスを `index.html` へ寄せる案は、E2E-002（自動テストは UI を操作しない）の改訂を伴う大きな判断であり、
> **2026-09-04 に利用者が「いまの枠組みのまま」と判断している。**
> **ID の突き合わせは UI を操作せずに行える**ため、その判断と両立する。

## 6. 影響範囲

| 範囲 | 影響 |
| --- | --- |
| 利用者への影響 | **大きい。** PlantUML を含む文書を 1 度でも開くと、**そのセッションの間ずっとステータス領域が死ぬ。** パス・文字コード・行数・倍率が出ず、以降のエラーメッセージ（FR-110）が**すべて表示されない** |
| 見え方 | ドロップ・リンク切れ・コピー失敗・エディタ起動など、**通知がすべて無音になる。** 利用者からは「操作が効かない」に見える（実際には処理は成功している） |
| 他の通知先 | 本文中（DSP-272 の理由表示）と状態画面（DSP-3xx）は**無事**。壊れるのはステータス領域だけである（FR-110 の 3 か所のうち 1 つ） |
| 文書の表示 | **無事。** 本文・アウトライン・ツリーは正常に出る。`updateStatus` が落ちるのは `showDocument` の最終段のため、本文の描画は完了している |
| PlantUML の描画 | **無事。** 図は正しく出る。壊すのは描画の**後**に呼ばれるログ関数である |
| `v1.0.0-rc.2` | **同じ不具合がある**（同梱資産が同一）。手動テストでは検出されなかった |
| リリース判断 | **rc.3 の前に直すべきである。** FR-110 の通知が丸ごと効かなくなるため、影響は BUG-001〜005 のどれよりも広い |

## 7. 修正後の検証方法

### 7.1 機械的な確認

```bash
# 1. #status を持つ要素が無いこと
grep -n 'id="status"' frontend/index.html          # 何も出ないこと

# 2. 子要素の ID は残っていること
grep -n 'id="status-' frontend/index.html          # 3 件

# 3. 自前のコードが #status を参照していないこと
grep -rn '"status"' frontend/js/ frontend/css/     # 何も出ないこと

# 4. 決め打ち ID と自前 ID の交差が空であること（5.6）
```

### 7.2 実機での確認（W1）

1. `testdata/showcase.md` を開く
2. **PlantUML の図が描けた後**でステータス領域を見る → **パスと文字コードと行数が出ている**（ログ 1 行になっていない）
