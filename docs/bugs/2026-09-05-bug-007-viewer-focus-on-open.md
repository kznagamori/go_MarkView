## 1. 症状

Markdown ファイルを開いた直後、**本文ペインにフォーカスが無い**。そのため `PageUp` / `PageDown` でスクロールできない。

`UI-051`（**MUST**）は次を定めている。

> - マウスホイール、スクロールバー、`PageUp` / `PageDown` / `Home` / `End` / 方向キーでスクロールできる。

**マウスホイールとスクロールバーは動く。キーボードだけが動かない。**

---

## 2. 原因

### 2.1 スクロールする器は `#viewer` だけであり、`body` はスクロールしない

```css
/* frontend/css/base.css */
html,
body {
  height: 100%;
  margin: 0;
  overflow: hidden;   /* ← 既定のスクロール器を殺している */
}

.viewer {
  overflow-x: hidden;
  overflow-y: auto;   /* ← 実際にスクロールするのはここだけ */
}
```

ブラウザの `PageUp` / `PageDown` / `Home` / `End` / 方向キーは、**フォーカスされている要素を含むスクロール器**を動かす。
`#viewer` の外にフォーカスがあるとき、たどり着く先は `body` であり、そこは `overflow: hidden` である。
**キーは届いているが、動かせる器が無い。**

### 2.2 `#viewer` にフォーカスを移す処理が 1 か所しかない

`frontend/js/` 全体で `.focus()` を呼んでいるのは 8 か所あり、**`#viewer` を対象にしているのは 1 つだけ**である。

| 呼び出し | 対象 | 契機 |
| --- | --- | --- |
| `search.js:94` | **`#viewer`** | **検索バーを閉じたとき**（UI-080） |
| `search.js:69` / `search.js:321` | 検索入力欄 | 検索バーを開いたとき |
| `overlay.js` × 4 / `editors.js` × 1 | ダイアログ内の操作要素 | ダイアログを開いたとき（IMP-295） |

**文書を表示したときにフォーカスを移す処理は存在しない。**

### 2.3 どの経路で開いてもフォーカスは本文の外にある

| 開き方 | 操作後の `document.activeElement` | キーボードで動くか |
| --- | --- | --- |
| 起動時の引数（FR-012） | `body`（誰も触っていない） | **動かない** |
| `Open` ボタン（FR-010） | `#btn-open`（クリックしたボタン） | **動かない** |
| `Ctrl+O`（UI-090） | 直前のまま。多くは `body` | **動かない** |
| ドラッグ＆ドロップ（FR-011） | 直前のまま | **動かない** |
| ファイルツリーから選択（FR-033） | **直前のまま。** ツリーの項目は `<li>` / `<div>` で `tabindex` を持たず、**クリックしてもフォーカスを受け取らない** | **動かない** |
| 本文中のリンク（FR-050） | `#viewer`（**本文をクリックした時点で入っている**） | 動く |
| 検索バーを `Esc` で閉じた後（UI-080） | `#viewer`（`search.js:94`） | 動く |

**「本文をクリックしてから」なら動くが、「開いた直後」は動かない。** これが利用者の観測と一致する。

> [!NOTE]
> `#viewer` は `tabindex="-1"` を持つため、**その中身をクリックすると `#viewer` 自身がフォーカスを受け取る**
> （フォーカス可能な最も近い祖先へ移る、というブラウザの規則）。
> **この経路があるために、症状が「たまに直る」ように見える。**

### 2.4 ショートカット層は無関係である

`shortcuts.js` の `onKeyDown` は表を引いて、**登録が無いキーには一切触れない**。

```js
const id = byKey.get(keyOf(event));
if (!id) return;          // PageUp / PageDown はここで抜ける
```

`SHORTCUTS` に `PageUp` / `PageDown` / `Home` / `End` / 方向キー（`Alt+←` / `Alt+→` を除く）は無い。
**キーが握りつぶされているのではない。**

### 2.5 同じ問題は情報ダイアログで既に一度解かれている

```js
// frontend/js/overlay.js:360
const body = document.createElement("pre");
body.className = "about-licenses";
body.tabIndex = 0; // キーボードでもスクロールできるようにする（IMP-295）
```

ライセンス全文の欄には、**「キーボードでスクロールできるように」という理由で明示的に `tabIndex` が与えられている。**
**同じ配慮が、本体である本文ペインに対しては行われていない。**

## 3. 原因の分類 — 仕様か、実装か

### 3.1 一次原因 — **仕様の欠落**（UI-051 を担当する実装 ID が無い）

`90-traceability.md` の正引きはこうなっている。

```
| UI-051 | スクロール | — | DSP-350 |
             （実装 ID が「—」）
```

`UI-051` は **2 つのこと**を定めている。

| # | 定めていること | 担当 |
| --- | --- | --- |
| 1 | **入力手段**（ホイール・スクロールバー・`PageUp` / `PageDown` / `Home` / `End` / 方向キー）でスクロールできる | **どこにも無い** |
| 2 | スクロール位置が FR-014 / FR-015 / FR-051 に従って維持・復元される | `DSP-350` |

**対応表は 2 だけを拾っている。** 1 を実現するには「本文ペインがフォーカスを持つ」ことが要るが、
**それを書いた実装仕様が存在しない。**

> [!IMPORTANT]
> **[BUG-002](2026-09-04-bug-002-filetree-reload-on-show.md) とまったく同じ構図である。**
> あちらは FR-035 が定める 3 つの契機のうち 1・2 の担当がどの ID にも無く、実装されないまま通過した。
> **箇条書きが複数ある要求は、対応表の 1 行が「全部見た」に見える。**
>
> 90 章にはこの教訓を **4.24.0 で NOTE として明記済み**である。しかし
> **既存の要求を洗い直す作業はしていない**ため、UI-051 は同じ穴に残っていた。

### 3.2 実装は「書かれていないことをしていない」だけである

`IMP-202` は `#viewer` の `tabindex="-1"` について、こう書いている。

> `#viewer` に `tabindex="-1"` を与える。**検索バーを閉じたときにフォーカスを本文へ戻す（UI-080）ために必要**であり、負値のため `Tab` の巡回順には入らない。

**目的が UI-080 に限定されている。** 実装はこの記述に忠実であり、`search.js` からしかフォーカスを移していない。
**実装者を責められる誤りではない。**

`IMP-295`（アクセシビリティ）も「**状態画面・ダイアログの表示時**に、フォーカスを内部の操作要素へ移す」までしか定めておらず、
**文書の表示時が含まれていない。**

### 3.3 仕様の不明瞭 — 「キーボードでスクロールできる」に前提が書かれていない

UI-051 の「`PageUp` / `PageDown` … でスクロールできる」は、**ブラウザの既定動作に任せれば自然に満たされる**ように読める。
実際には `html, body { overflow: hidden }`（DSP-041 / UI-050 の「横スクロールを発生させない」を満たすための指定）と組み合わさった時点で、
**フォーカス位置が前提条件になる。**

**2 つの要求の組み合わせで初めて生じる前提であり、どちらの文書にも書かれていない。**
これは [BUG-003](2026-09-04-bug-003-outline-auto-hide.md) の「要求どうしの算術的な整合が検査項目に無い」と同じ種類の抜けである。

## 4. なぜ単体テストと E2E の自動テストで見つからなかったのか

### 4.1 単体テスト — 対象外

`UT-002` が単体テストの対象を `internal/` に限っている。フォーカス管理は `frontend/js/` にあり、Go のコードは関わらない。
`31-test-cases.md` 31.10 の対応表も、この要求の行はこうなっている。

```
| UI-051 | — (GUI) | |
```

**「GUI だから見ない」と明示的に決めた要求である。**

### 4.2 自動 E2E — ウィンドウもキーボードも無い

`E2E-002` が「自動テストは UI を操作しない」と定めている。`scripts/e2e` は配布物の構成・起動・終了・CLI を見るだけで、
**キー入力を送る経路が無い。**

### 4.3 描画スモークテスト — `index.html` を読まない

`scripts/smoke`（BR-054）は独自の `harness.html` を配る。`#viewer` も `body { overflow: hidden }` も存在せず、
**フォーカスの話が成立しない。**（[BUG-006](2026-09-05-bug-006-status-id-collision.md) 4.2 と同じ理由）

### 4.4 手動テスト — **UI-051 を担当するケースが、キーボードを使わない**

`40-e2e-auto.md` 40.5 の対応表は `UI-051 | E2E-253` としている。**UI-051 を見るケースはこれ 1 つだけ**である。

```
### E2E-253: スクロール連動
- 関連要求: FR-042, UI-051
- 概要: 本文のスクロールにアウトラインが追従することを確認する
- 手順:
  1. 本文をゆっくりスクロールする
  2. 一気に末尾までスクロールする
- 確認内容:
  1. 現在位置の見出しがアウトライン上で強調される
  2. 強調が 1 つだけである
  3. 強調項目が…自動でスクロールして見える位置に来る
  4. スクロールがカクつかない
```

問題は 3 つある。

| # | 問題 |
| --- | --- |
| 1 | **確認内容 4 項目はすべてアウトライン側**である。UI-051 の「入力手段」は 1 つも確認していない |
| 2 | **手順がスクロールの手段を指定していない。** ホイールで実施すれば必ず通る |
| 3 | **「本文をゆっくりスクロールする」ためには、まず本文をクリックするのが自然である。** その瞬間に `#viewer` がフォーカスを得て（2.3 の NOTE）、**症状が消える** |

**このケースは、症状を踏まないように作られている。**

さらに、`PageUp` / `PageDown` という語は **`03-ui.md` の UI-051 にしか出てこない**（仕様書 20 文書を検索して確認）。
**41 章のどのケースにも、キーボードでスクロールする手順が存在しない。**

### 4.5 仕様レビューでも見つからなかった

90 章の対応表で **実装 ID が `—` の要求は 19 件**ある。その大半は正当である（`BR-*` のようにビルド工程が担当するもの、
`MD-010` / `MD-011` のように表示仕様が担当するもの）。

**`UI-051` はその中で例外的に「実行時の振る舞い」を定めている**が、割り当てられた `DSP-350` は
**スクロール位置の契機だけ**を扱っており、入力手段には触れていない。

**「MUST でありながら、振る舞いを担当する実装 ID が無い要求」を洗い出す検査項目が無かった。**

### 4.6 まとめ

| 層 | 捕まえられたか | 理由 |
| --- | --- | --- |
| 単体テスト | **できない** | 対象が `internal/` のみ（UT-002）。31.10 が明示的に「— (GUI)」 |
| 自動 E2E | **できない** | UI を操作しない（E2E-002）。キー入力の経路が無い |
| 描画スモーク | **できない** | `index.html` を読まない |
| 手動テスト | **できなかった** | UI-051 を担当する唯一のケースがキーボードを使わず、しかも**先に本文をクリックさせる**手順になっている（4.4） |
| 仕様レビュー | **できたはず** | 90 章で「実装 ID を持たない MUST」を機械的に洗える。**4.24 で入れた NOTE を既存の要求へ適用していなかった**（3.1） |

## 5. 修正方法

### 5.1 案 A（推奨）— 文書を表示したときに本文ペインへフォーカスを移す

`viewer.js` の `showDocument` で、スクロール位置を適用した後にフォーカスを移す。

```js
// 9. スクロール位置を設定する（13 章 ScrollDTO）
applyScroll(viewer, doc.scroll, previousTop);

// **本文ペインへフォーカスを移す**（UI-051）。
// キーボードでのスクロールは、スクロールする器がフォーカスを持って初めて効く。
// body は overflow: hidden であり、外にフォーカスがあると PageUp が空振りする。
focusViewer();
```

**3 つの条件を満たす必要がある。**

| # | 条件 | 理由 |
| --- | --- | --- |
| 1 | **`focus({ preventScroll: true })` とする** | 12 章が既に定めている規則。フォーカス移動に伴うスクロールが、直前の `applyScroll`（DSP-350）を打ち消しうる。[BUG-004 / P9](2026-09-03-search-jump-buttons.md) で実際に起きた種類の事故である |
| 2 | ~~検索バーの入力欄にフォーカスがあるときは奪わない~~ → **不要**（下記の訂正） | — |
| 3 | **ダイアログを表示している間は奪わない** | ダイアログは開いたままファイル更新の自動検知（FR-014）を受けうる。**背後の本文へフォーカスが移り、フォーカストラップ（IMP-251, IMP-252）が破れる** |

> [!IMPORTANT]
> **訂正（2026-09-05。仕様への反映時に判明）。** 上の条件 2（検索）と、条件 3 の「状態画面」は**成立しない。**
>
> - `renderDocument` は**手順 0 で `closeSearch()` を呼ぶ**（IMP-220。FR-080 の「切り替え・再描画時は
>   検索状態をリセットする」）。手順 11 に達した時点で検索は閉じており、**奪う相手が居ない。**
>   さらに `closeSearch` は入力欄にフォーカスがあれば**自分で本文へ戻す**（`search.js:94`）
> - 状態画面は `renderDocument` ではなく `showStateScreen` が出す。**「大きなファイルの確認」から
>   `Open anyway` で本文が出た場合は、フォーカスを本文へ移すのが正しい**
>
> **残る条件は 1（`preventScroll`）と 3（ダイアログ）の 2 つである。** 仕様（IMP-220）はこの形で書いた。

### 5.2 案 B（あわせて検討）— `#viewer` を `Tab` の巡回に入れる

`tabindex="-1"` を `0` にすれば、`Tab` でも本文へ到達できる。

**単独では採らない。** `IMP-202` が負値を選んだのは「`Tab` の巡回順には入らない」ためであり、
巡回に本文を入れるとツールバーのボタン間の移動に 1 段増える。**利用者の判断が要る。**

なお案 A があれば、開いた直後は既に本文にフォーカスがあるため、**案 B が無くても症状は解消する。**

### 5.3 採らない案 — `PageUp` / `PageDown` を自前で処理する

`shortcuts.js` に割り当てを足し、`#viewer.scrollTop` を自分で動かす。

**採らない。**

- UI-051 は `Home` / `End` / 方向キーも含む。**既定の挙動を一式作り直すことになる**（1 行あたりの移動量、加速、選択との関係）
- `IMP-244` は「キー割り当ての唯一の定義」を持つ表であり、**ブラウザの既定動作の代替をそこへ混ぜると、表の意味が変わる**
- フォーカスが無いという本当の問題は残る。**スクリーンリーダから見て、本文が「現在地」にならない**（DSP-016, IMP-295）

### 5.4 採らない案 — `body` をスクロールさせる

`html, body { overflow: hidden }` をやめれば既定のスクロール器が復活する。

**採らない。** ツールバーとステータス領域を画面に固定する前提（UI-020, UI-060, DSP-030）が崩れ、
**本文だけがスクロールする**という設計そのものが壊れる。

### 5.5 判断が要るところ — ファイルツリーから開いたとき

**ツリーの項目を選んで開いた直後にフォーカスを本文へ移すと、ツリーのキーボード操作の続きが断たれる。**

`UI-030` は「ペインにフォーカスがあるとき、`↑` `↓` でノード間を移動、… `Enter` でファイルを開く」と定めており、
**連続して別のファイルを見て回る使い方**を想定している。開くたびに本文へ移ると、この流れが途切れる。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A-1** | どの経路でも本文へ移す | 単純。UI-051 を確実に満たす。**ツリーの連続操作は途切れる** |
| **A-2** | ツリーから開いたときだけ移さない | 使い勝手は良い。**契機ごとの分岐が増える**（DSP-350 と同じ形の表が要る） |

**現時点では A-1 を推奨する。** 9 章のとおり**ツリーのキーボード操作は現状まったく動いていない**ため、
A-2 が守ろうとしている流れは**まだ存在しない**。A-2 は、ツリーのキーボード操作を実装するときに改めて判断すればよい。

## 6. 影響範囲

| 範囲 | 影響 |
| --- | --- |
| 利用者への影響 | **中〜大。** 閲覧専用のアプリでありながら、**開いた直後にキーボードで読み進められない。** 一度本文をクリックすれば動くため「効かないときがある」という形で現れ、原因が分かりにくい |
| 対象となる操作 | `PageUp` / `PageDown` / `Home` / `End` / `↑` `↓` `←` `→` / `Space`（すべて同じ理由） |
| 動くもの | マウスホイール、スクロールバーのドラッグ、アウトラインのクリック（FR-041）、検索の移動（FR-080）、履歴（FR-051）。**いずれもフォーカスを必要としない** |
| アクセシビリティ | `IMP-295`（SHOULD）と `DSP-016` の意図に反する。**キーボードだけで操作する利用者は、開いた文書を読み進められない** |

## 7. 修正後の検証方法

### 7.1 まず切り分ける（**実装前に行う**）

**2.3 の分析（クリックすれば動く）が正しいことを確かめる。** 手元では GUI を起動していないため、ここは実測で裏を取る。

1. MarkView を起動し、ファイルを開く
2. **マウスに触れずに** `PageDown` を押す → **動かないはず**
3. 本文の適当な位置を**クリックする**
4. もう一度 `PageDown` を押す

| 結果 | 判定 |
| --- | --- |
| **手順 4 では動く** | 本報告のとおり。**原因はフォーカスだけ**であり、5.1 で直る |
| **手順 4 でも動かない** | **別の原因がある。** `#viewer` が実際にフォーカスを得ているか（開発者ツールで `document.activeElement`）、`.viewer` に `overflow-y: auto` が効いているかを順に確認する |

### 7.2 修正後の手動確認（W1）

1. **引数で起動**して `PageDown` → 動く
2. `Ctrl+O` で開いて `PageDown` → 動く
3. **ドロップ**して `PageDown` → 動く
4. **ツリーから選んで** `PageDown` → 動く（5.5 の A-1 を採る場合）
5. `Home` / `End` / `↑` `↓` → 動く
6. **`Ctrl+F` で検索を開き、文字を入力する** → **入力できる**（5.1 の条件 2。フォーカスを奪っていない）
7. 検索中に**ファイルを外部から書き換える**（FR-014 の自動反映）→ **入力欄のフォーカスが外れない**
8. **大きなファイルの確認画面**を出す（FR-016）→ `Open anyway` に `Enter` が効く（5.1 の条件 3）
9. `F5` で再読み込み → **スクロール位置が維持される**（DSP-350。5.1 の条件 1 が効いている）
10. `Alt+←` で戻る → **記録された位置に復元される**（FR-051）

> [!IMPORTANT]
> **手順 9 と 10 が要である。** `preventScroll` を省くと、フォーカス移動がスクロール位置を先頭へ戻しうる。
> **P9（検索バー）で実際に踏んだ罠である。**

### 7.3 機械的な確認

grep -n "focus(" frontend/js/viewer.js

# ショートカット表に PageUp / PageDown を足していないこと（5.3 を採らない）
grep -n "PageUp\|PageDown\|Home\|End" frontend/js/shortcuts.js   # 何も出ないこと

## 9. 調査中に気づいた別件（**本報告の対象外**）

`UI-030` は「ペインにフォーカスがあるとき、`↑` `↓` でノード間を移動、`→` で展開、`←` で折りたたみ、`Enter` でファイルを開く」と定めており、

| --- | --- |
| ツリーの項目がフォーカスを受け取れるか | **受け取れない**（`tabindex` を持たない） |
