## 1. 症状

タスクリスト（`- [ ]` / `- [x]`。MD-022）のチェックボックスが、**Linux でわずかに小さい。**

実施者の記録（E2E-231）:

> W1: OK
> L1: NG
> チェックボックスが少し小さい（GitHub, Win: 13pix、Linux: 12pix）

| 環境 | チェックボックスの大きさ |
| --- | --- |
| GitHub（基準。MD-002） | **13 px** |
| W1（WebView2 / Chromium） | **13 px** — 一致 |
| **L1（WebKitGTK）** | **12 px** — **1 px 小さい** |

**クリックしても状態が変わらないこと（MD-022）は両環境で満たされている。** 大きさだけの差である。

---

## 2. 原因

### 2.1 チェックボックスの大きさをどこにも指定していない

```css
/* frontend/css/markdown.css */
.markdown-body input[type="checkbox"] {
  margin: 0 0.2em 0.25em calc(var(--md-em) * -1.1667);
  vertical-align: middle;
  cursor: default;
  pointer-events: none;
}
```

**`width` も `height` も `font-size` も無い。** 大きさは描画エンジンがネイティブ部品として決めた既定値がそのまま出る。

| エンジン | `input[type="checkbox"]` の既定の大きさ |
| --- | --- |
| Blink（WebView2 / Chrome） | 13 px 相当（`markdown.css` のコメントは 13.33px と実測している） |
| **WebKit（WebKitGTK）** | **12 px 相当** |

GitHub 側も `github-markdown-css`（DSP-001）が大きさを指定しておらず、**閲覧者のブラウザ既定に従っている**。実施者が見た「GitHub 13px」は **Chromium 系ブラウザで GitHub を開いた結果**であり、GitHub が 13px と決めているわけではない。

### 2.2 負のマージンの定数も Chromium から逆算されている

同じブロックのコメント:

> **左だけ本文基準にする。** input は文字サイズを継承せず、**Chromium の既定（13.33px）が基準になる**ため、同梱物の `-1.4em` は実測 `-18.67px` になる。em のままだと本文が倍率で広がってもここだけ動かず、ずれていく（DSP-021）。**18.67 / 16 = 1.1667** を本文 1 文字ぶんに掛け、100 % では GitHub と同じ位置に、倍率を上げると一緒に広がるようにする。

**`1.1667` という定数は Chromium の既定 13.33px から導いた値**である。したがって L1 では、

1. **大きさが 12px になる**（観測された症状）
2. **左位置も理屈のうえでずれる**——引き出し量は本文基準（`--md-em`）で決まるのに対し、部品の幅がエンジンで違うため、**マーカー位置との相対関係が変わる**

**2 は今回観測されていない。** 1px 前後であり、目視で気づける差ではない。**修正するなら 1 と 2 を一緒に解く。**

### 2.3 `DSP-121` が値を定めていない

`DSP-121: 本文要素`（**MUST**）のタスクリストの行:

> | タスクリスト | チェックボックスは読み取り専用（MD-022）。`cursor: default`、`pointer-events: none` |

**定めているのは「読み取り専用であること」だけ**で、大きさも位置も書かれていない。`DSP-001`（値の正は `github-markdown-css`）に従うと解釈しても、**同梱物がこの部品の大きさを定めていない**ため、結局どこにも書かれていないことになる。

### 2.4 `DSP-011` は「OS が描く部品」があることを既に認識していた

```
- **`color-scheme` をテーマに合わせて宣言する。** タスクリストのチェックボックス（MD-022）のように
  OS が描く部品は、色を CSS のトークンで指定できない。この宣言がないと Dark でも明るい配色のまま浮く。
```

**「OS が描く部品」であることは仕様に書いてある。** しかし対処したのは**色だけ**で、**大きさは委ねたままだった。** 同じ理由（エンジンが描く）から同じ種類の差（環境ごとに違う）が出るのに、片方しか塞いでいない。

### 2.5 `NFR-061` の一覧から漏れている

`NFR-061: 表示の互換性`（**SHOULD**）が両環境で同等とするものは次の 4 つで、**「本文のレイアウト」の括弧内は「見出し・表・コードブロック・リストの構造と余白」**である。

> - 本文のレイアウト（見出し・表・コードブロック・リストの構造と余白）
> - テーマの配色
> - Mermaid 図・PlantUML 図・数式の描画結果
> - コピーボタンの位置と動作

**「リストの構造と余白」にチェックボックスの大きさが含まれるかは読み取れない。** BUG-008 と同じく、**エンジンの既定に委ねているものが一覧に無い。**

## 3. 原因の分類 — 仕様か、実装か

### 3.1 一次原因 — **仕様の不足**（DSP-121 が値を定めていない）

**表示仕様が値を書いていないため、実装は書きようがない。** DSP-001 に従っても同梱物が定めていない。

### 3.2 二次原因 — 実装が Chromium の既定を前提に定数を置いた

`1.1667` は Chromium の実測から導いた値であり、**コメントにその出自がはっきり書いてある。** これは隠れた前提ではなく、**明示された前提**である。ただし「Chromium 以外ではどうなるか」は書かれていない。

**実装の誤りとまでは言えない**——仕様が値を定めていない以上、どこかの実測から決めるほかない。**書き残し方は正しく、対象を 1 つに限った点だけが足りない。**

### 3.3 分類の結論

| 問い | 答え |
| --- | --- |
| **仕様が不明瞭か** | **はい。** DSP-121 はチェックボックスの大きさを定めておらず、NFR-061 も対象に含むかどうかが読み取れない |
| 仕様が間違いか | いいえ。**書かれていることは正しい** |
| 実装が間違いか | **部分的に。** Chromium の実測値から定数を置き、他方のエンジンを確かめていない。**ただし仕様が値を与えていないので、実装だけの責任ではない** |

> [!NOTE]
> **BUG-008 とは分類が違う。** あちらは「**仕様が誤った手段を明示的に指定した**」（DSP-123 の NOTE）。
> こちらは「**仕様が何も指定しなかった**」。**結果として現れる症状は同じ種類（エンジン差）である。**

## 4. なぜ単体テストと E2E の自動テストで見つからなかったのか

### 4.1 単体テスト — 対象外（UT-002）

CSS も HTML も対象外である。**そもそも「1px 小さい」を判定するテストは、レンダリング結果を測らなければ書けない。**

### 4.2 自動 E2E — ウィンドウ内を操作しない（E2E-002）

`E2E-002` は自動テストを「WebView の UI を操作しない」範囲に限っている。さらに `40-e2e-auto.md` の禁止事項に次がある。

> | スクリーンショットを撮って画像比較する | フォント・DPI・OS のテーマで差が出て、意味のない失敗が続く |

**この不具合は、まさにその「画像比較」でしか自動検出できない種類のものである。** 禁止の理由（環境差で無意味に失敗する）はいまも妥当であり、**この 1 件のために方針を変えるのは割に合わない。**

### 4.3 描画スモークテスト — Chromium 系しか起動せず、大きさも測らない

`scripts/smoke/browser.go` の候補は Chrome / Chromium / Edge であり、**Linux で実行しても WebKitGTK は使われない**（BUG-008 の 4.3 と同じ）。加えてスモークテストが見るのは同梱資産が描けるかだけで、**部品の寸法は測らない。**

### 4.4 手動テスト（rc.2）— **L1 を 1 件も実施していない**

| 版 | W1 | L1 |
| --- | --- | --- |
| rc.2 | **64** | **0** |
| rc.3 | 64 | **34** |

**rc.3 が Linux を見る最初の機会だった。**

### 4.5 手動テスト（rc.3）で見つかったのは、GitHub と並べたから

E2E-231 の確認内容 4 は次のとおりである。

> 4. タスクリストのチェックボックスが表示され、クリックしても状態が変わらない

**この文面だけを見れば L1 は OK である。** 表示されているし、クリックしても変わらない。**実施者が GitHub と並べて見比べていた（手順 1）ため、1px の差に気づけた。**

言い換えると、**この不具合を捕まえたのは「確認内容」ではなく「テスト概要（GitHub と同じ体裁で表示されること）」である。** 41 章の書き方として、**ここは番号付きの確認内容で拾えていない。**

### 4.6 仕様レビューでも見つからなかった

`DSP-011` は「OS が描く部品」の存在を認識していた（2.4）。**にもかかわらず、色だけを塞いで大きさを見送ったことが、レビューで問題として立ち上がらなかった。** 一貫した記述の中の「片手落ち」は、突き合わせでは出てこない。

### 4.7 まとめ

| 層 | 見つけられたか | 理由 |
| --- | --- | --- |
| 単体テスト | **原理的に不可** | フロントエンドは対象外。寸法を測れない |
| 自動 E2E | **不可（方針として）** | 画像比較を明示的に禁止している（40-e2e-auto.md） |
| 描画スモーク | **原理的に不可** | Chromium 系しか起動せず、寸法も測らない |
| 仕様レビュー | 不可 | DSP-011 が「OS が描く部品」を認識しながら、色だけで完結していた |
| **手動テスト（L1、GitHub と並置）** | **可。実際にここで見つかった** | **確認内容ではなくテスト概要が効いた** |

## 5. 修正方法

### 5.1 案 1（**採らない**）— 大きさを明示し、負のマージンをそこから算出する

> [!NOTE]
> **この案は採らないことになった**（見出しの表の「決着」）。**記録として残す。**
> 将来 `NFR-061` の許容差を見直すとき、または別の理由で `input` の寸法を触るときに読む。

**エンジンの既定を使わない。** 13px（本文 16px に対して `0.8125em`）を自分で決める。

```css
/* frontend/css/markdown.css（案）*/
.markdown-body input[type="checkbox"] {
  /* **大きさをこちらで決める。** 既定はエンジンごとに違い（Chromium 13.33px /
     WebKitGTK 12px）、委ねると環境差になる（NFR-061, BUG-009）。
     0.8125em = 13px / 16px。GitHub を Chromium で見たときの値に合わせる。 */
  width: calc(var(--md-em) * 0.8125);
  height: calc(var(--md-em) * 0.8125);
  /* 引き出し量も同じ基準から出す。1.4em は同梱物の値（DSP-001）。 */
  margin: 0 0.2em 0.25em calc(var(--md-em) * -0.8125 * 1.4);
  vertical-align: middle;
  cursor: default;
  pointer-events: none;
}
```

| 論点 | 判断 |
| --- | --- |
| 倍率（DSP-021） | **改善する。** 実測では**現状のチェックボックスは倍率 50 %〜300 % のいずれでも 13px のまま**で、**まったく追従していない**（負のマージンだけが `--md-em` 基準で動いている）。この案では大きさも本文と一緒に拡大する |
| テーマ（DSP-011） | **変えない。** `color-scheme` による配色はそのまま効く。`appearance` を触らないため、部品はエンジンが描き続ける |
| **L1 で本当に効くか** | **実機での確認が要る。** ネイティブ部品に `width` / `height` を与えたときの拡縮の扱いはエンジンで違いうる。**5.4 の検証を先に行う** |
| 現状 100 % での見え方（W1） | 13.33px → 13px。**0.33px 縮む。** 目視では変わらない |

### 5.2 案 2 — `appearance: none` で自前に描く

チェックボックスを完全に自前の見た目にすれば、エンジン差は消える。

**採らない。**

- **`DSP-011` の前提（OS が描く部品なので `color-scheme` で配色する）を壊す。** 自前で描くなら、チェック済みの ✓ も枠も色も自分で持つことになる
- **GitHub の見た目から離れる恐れがある**（MD-002）。GitHub 自身がネイティブ部品を使っている
- **読み取り専用（MD-022）の見え方**——`disabled` に対するエンジンの淡色化も自前で再現することになる
- 直したい差は **1px** である。**釣り合わない**

### 5.3 案 3（**採用**）— 直さず、許容差として決着させる

`NFR-061` は **SHOULD** であり、**「細部に差異が生じうる」ことを前提に書かれている。**

> Windows の WebView2（Chromium）と Linux の WebKitGTK では描画エンジンが異なるため、**細部に差異が生じうる**。

1px の部品差はこの「細部」に当たると解釈し、**NFR-061 に許容差を明記して決着させる**。BUG-003（アウトラインの自動隠し）と同じ形——**コードを変えず、仕様の不備を直して閉じる**。

**この場合でも仕様の修正は要る。** 「何も書かないまま NG が残る」状態が最も悪い。

| 案 | コード | 仕様 | 判断の勘所 |
| --- | --- | --- | --- |
| 案 1 | 変える | 値を明記する | **エンジン差を根本から消す。**BUG-008 と同じ方向 |
| **案 3（採用）** | **変えない** | **許容差を明記する** | **1px に見合うか。** 直せば消えるものを許容と書くのは、後から読む人に説明が要る |

**案 3 を採る**（利用者の判断。2026-09-06）。**この決着を仕様に書き残さないと、次の rc で同じ NG がもう一度上がる。** 5.5 の 4 か所を必ず直す。

> [!IMPORTANT]
> **「許容差」の範囲を数字で書く。** 「細部の差異は許容する」だけでは、次に別の 1px が出たときに
> また判断が要る。**`NFR-061` に「OS / エンジンが描く部品（フォームコントロール）の寸法は、
> 2px 以内の差を許容する」のように、対象と幅を書く。**
>
> **`BUG-008`（画像の代替テキスト）は許容差にできない。** あちらは 1px の差ではなく、
> **`FR-022`（MUST）の「代替テキストを表示する」が満たされていない**——**要求の欠落**である。
> **2 件を同じ扱いにしない。**

> [!NOTE]
> **BUG-008 の 5.6 で提案した「委ねている箇所を 1 つずつ塞ぐ」という方向は、ここでは採らない。**
> 委ねている箇所は 2 つ見つかっており（画像の `alt`、チェックボックスの寸法）、
> **前者は塞ぎ、後者は許容する。** 分ける根拠は「**要求（MUST）が満たされているか**」である。

### 5.4 修正の前に確かめること（**案 1 を採る場合のみ。今回は不要**）

案 1 は「ネイティブのチェックボックスに `width` / `height` が効くか」に依存する。**先に確かめる。**

1. L1 で `testdata/showcase.md` を開く
2. WebKitGTK の開発者ツール（`WEBKIT_INSPECTOR_SERVER` などが要る場合がある）か、**簡単な HTML を Epiphany / WebKitGTK 系ブラウザで開いて**、`input[type=checkbox]{width:13px;height:13px}` が実際に 13px で描かれるかを見る
3. 効かない場合は案 3（許容差として決着）へ切り替える

### 7.1 仕様の確認（5.5 の 4 か所を直したあと）

comm -3 /tmp/def.txt /tmp/ref.txt

# 記録用 Excel が生成できること（41 章を触るため）

**数字（何 px まで）と対象（どの部品か）が書かれていなければ、書き直しである。**
