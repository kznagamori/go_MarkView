## 1. 症状

参加者 4 人・`opt` が縦に 4 つほどのシーケンス図が、図にならず `PlantUML could not render this diagram.` と元のソースだけが出た。**画面からは、大きすぎたのが原因だと分からなかった**（上限を超えたことと、対応していない図種別を区別して出さない。DSP-272）。

縦に長いシーケンス図は、メッセージ 1 本でおよそ 33〜40 px 伸びる（注記の数による）。**メッセージが 100 本を超えると 4096 px を超える**（実測: 注記を 10 本に 1 つ挟んで、100 本で 4,050 px・200 本で 7,740 px）。業務のやり取りを 1 枚に描くと、すぐに届く。

---

## 2. 原因

### 2.1 上限の値を、実用の図の大きさで決めていなかった

4096 px は、v1.0.0 で同梱した処理系（1.2026.7）の固定値である。1.2026.8 で処理系の既定が 8192 px になったとき、**描ける図の大きさが資産の更新だけで変わらないよう、MarkView が 4096 を明示して渡すことにした**（4.64.0。利用者の判断）。**どちらのときも、実際に書かれる図がこの大きさに収まるかは測っていなかった。**

### 2.2 処理系は配置を計算し終えてから大きさを確かめる（上限では待ち時間を縛れない）

利用者の基準は「**図 1 枚が出るまで 5 秒を超えると、止まったと感じる**」である。当初は、上限を大きくすると描画に時間がかかる図が増えるため、5 秒に収まる大きさを上限にする考えだった。**計測で、この前提が成り立たないことが分かった。**

| 図（JSON・キー 300） | 上限 | 結果 | かかった時間 |
| --- | --- | --- | --- |
| 210 × 26,983 px | 4096 | 拒否（`Diagram too large for browser rendering: 210x26983 (max 4096 …)`） | 5,532 ms |
| 同じ図 | なし（0） | 図が出る | 5,595 ms |

**処理系は配置を最後まで計算してから大きさを確かめ、超えていれば拒む。** 上限を下げても待ち時間は減らず、待った末に「描けなかった」と出るだけになる。**上限が決めるのは「計算した図を画面に出すか」だけである。** ほかの種類でも、拒むまでの時間と描くまでの時間の差は数十 ms だった（シーケンス図 29,880〜118,440 px、アクティビティ図、マインドマップ、ガント、WBS、JSON）。

### 2.3 描いている間、メインスレッドが止まる（NFR-011 の注記が成り立たない）

NFR-011 の注記は「同梱する処理系は細切れに実行されるため、400 ms かかる図でもメインスレッドの停止は 4 ms 以下であった」としていた。**Graphviz を使わない図では成り立たない。** Long Tasks API で測ると、**計算の間ずっと 1 つのタスクでメインスレッドが止まる**（JSON 26,983 px で 5.5 秒、アクティビティ図 73,076 px で 7.0 秒）。その間は、スクロールもボタンも効かない。Graphviz を使う図は一部が細切れになる（class 50 個で 392 ms のうち最長の停止 234 ms。v1.0.0 の資産）。

**v1.2.0 で始まったことではない。** v1.0.0（1.2026.7）と v1.1.0（1.2026.8）の資産でも、シーケンス図・アクティビティ図・JSON は描く時間の全体が 1 つのタスクだった（v1.1.0 の資産で、高さ 15,120 px のシーケンス図が 791 ms 止まる）。1.2026.9 は 1.2026.8 より 2〜5 倍速い。

---

## 3. 原因の分類 — 仕様か、実装か

**仕様の不足である。** 実装は MD-083 / IMP-233 の値をそのまま渡している。値を決めるときに、実際に書かれる図の大きさと、上限が何を縛るのかを確かめていなかった。

2.3 は**仕様の前提の誤り**である（NFR-011 の注記と NFR-012 の「描画中も UI 操作が阻害されないこと」）。描画の処理系は改変できず（BR-042）、別スレッド（Web Worker）へ移すこともできない——処理系は出力先を要素の id で受け取り、`document` へ直接書く（IMP-233 の 1・2）。

## 4. なぜ見つからなかったのか

| 層 | 見つからなかった理由 |
| --- | --- |
| 手動テスト | **E2E-239 / E2E-240 の図は小さい**（showcase の図と、上限を超えさせるための図だけ）。実用の大きさの、上限より少し大きい図が無かった |
| 仕様レビュー | 上限の値は「処理系の既定が変わっても描ける大きさを保つ」観点だけで見ていた（4.64.0） |
| 性能の計測 | NFR-011 の PlantUML の目標は図 1 枚（標準的な大きさ）で測り、大きさを変えて測っていなかった。メインスレッドの停止も同じ |

### 5.1 上限を決めた手順（利用者の判断。2026-11-11）

| # | 問い | 答え |

| 6 | 上限を超えた図の表示 | 文言に理由の候補を足す（`… It may be unsupported or larger than 100,000 px.`）。処理系の英文では判定しない |
| 10 | 描いている間の表示 | 描き終えるまで原文を出す（DSP-272 の「描画前」のとおり） |

### 5.2 計測の結果（2026-11-11。開発機。5 回の中央値と、初回を含む最大）

**図 1 枚を描き始めてから表示されるまで**（`render()` を呼んでから SVG が入り、2 フレーム後まで）:

| 同 | 407 × 15,120 | 91 ms | 123 ms |
| 同 | 407 × 29,880 | 170 ms | 227 ms |
| 同 | 415 × 59,400 | 322 ms | 424 ms |
| 同 | 415 × 99,990 | 539 ms | 708 ms |
| シーケンス（参加者が横に並ぶ） | 20,451 × 13,232 | 590 ms | 706 ms |
| アクティビティ（縦に長い） | 229 × 21,976 | 580 ms | 600 ms |
| 同 | 229 × 43,876 | 2,245 ms | 2,293 ms |
| アクティビティ（`fork` で横に広い） | 14,814 × 299 | 535 ms | 585 ms |
| マインドマップ | 320 × 72,000 | 298 ms | 470 ms |
| WBS | 15,821 × 342 | 68 ms | 135 ms |
| ガント | 19,412 × 12,079 | 717 ms | 825 ms |
| JSON（入れ子のオブジェクト） | 211 × 13,483 | 794 ms | 830 ms |
| 同 | 211 × 17,983 | 1,641 ms | 1,661 ms |
| 同 | 211 × 22,483 | 2,941 ms | 2,969 ms |
| YAML | 209 × 22,483 | 2,907 ms | 2,956 ms |

**3.5 秒に届く大きさ**（上の値から外挿）: JSON・YAML は約 24,000 px、縦に長いアクティビティ図は約 52,000 px、シーケンス図は約 470,000 px（高さ 472,680 px で 3.5 秒）。**どの種類も、時間は大きさに比例するより速く伸びる**（JSON は大きさの 2.3〜2.6 乗）。

**画面に出す手間**（本物の `index.html` と `main.js`。高さ 97,512 px のシーケンス図と幅 96,091 px の WBS）:

| 操作 | シーケンス図 | WBS |
| --- | --- | --- |
| 文書が出てから図が出るまで（資産の読み込みを含む） | 2,326 ms | 1,931 ms |
| 本文のスクロール（末尾へ・先頭へ） | 30 / 34 ms | 49 / 33 ms |

ヘッドレスの Edge では、高さ 472,680 px（シーケンス図）・幅 41,740 px の図も表示できた。

### 5.3 決めた値: 100,000 px

- **計算し終えた図は捨てずに出す。** 画面に出す手間は 10 万 px でも 0.12 秒以内である（5.2）。
- **3.5 秒以内に計算が終わる図は、ほぼすべて 10 万 px に収まる。** 収まらないのは、計算の軽い種類をとても大きく描いた場合だけである——メッセージ約 2,700 本を超えるシーケンス図、項目約 2,100 を超えるマインドマップ、約 720 工程を超える WBS（いずれも 1〜2 秒ほどで計算が終わる）。
- **それより大きく取らない（0 で検査を外さない）。** WebKitGTK（L1）で巨大な SVG をどこまで描けるかは確かめていない。上限は、極端に大きな SVG で WebView が不安定になることを防ぐ最後の手段として残す。

### 5.4 実装

| 対象 | 変えたこと | 規定 |
| --- | --- | --- |
| `frontend/js/puml.js` | `PLANTUML_MAX_SVG_SIZE` を 100000 に。**描き終えるまで原文を出しておく**——器は隠して原文の後ろに置き、そこへ描かせ、図が得られたら原文と入れ替える。描けなければ器を外して理由を添える（原文はそのまま）。描き直し（テーマ）が描きかけのブロックに当たったら、器だけを外す。**隠した器へ描かせても、得られる図は変わらない**（8 種類で大きさと時間が同じ。実測） | IMP-233, DSP-272 |
| `frontend/js/strings.js` | `pumlUnsupported` を、上限の値を受け取って `PlantUML could not render this diagram. It may be unsupported or larger than 100,000 px.` を返す関数に | IMP-290, DSP-272 |
| `testdata/e2e/plantuml-limits.md` | 6 節を、上限を超える図（`!while` で作る高さ 116,520 px のシーケンス図）に。**9 節に上限のすぐ下の図（高さ 90,120 px）を足した**（描ける。6 節の対照） | E2E-240, E2E-239 |
| `scripts/smoke` | limits 部で 9 節の図が描けること（高さ 80,000 px 以上）を見る | BR-054, UT-812 |
| `scripts/gentestdata` | `slow-plantuml.md` の最後の図を、上限を超えるシーケンス図に。**埋めの図を 16 枚から 60 枚に**（1.2026.9 では 1 枚 0.15〜0.35 秒に縮み、16 枚では検索を打つ前に描き終えうる。60 枚で約 10 秒） | E2E-271, E2E-012 |

### 5.5 採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| 最も重い種類（JSON）が 3.5 秒に届く大きさ（約 24,000 px）を上限にする | 上限では計算の時間を縛れない（2.2）。計算を待った末に捨てることになり、軽いシーケンス図まで 2.4 万 px で止まる |
| 上限を外す（0） | 極端に大きな SVG で WebView が不安定になっても止めるものが無い。L1 は未確認 |
| 処理系の英文を読んで「大きすぎる」を分けて出す | 英文は処理系の版で変わってきた（IMP-233）。資産の自動更新（BR-043）で黙って見分けられなくなる |
| 描画を別スレッドへ移し、画面を止めない | 処理系は出力先を要素の id で受け取り、`document` へ直接書く（IMP-233）。改変もできない（BR-042） |

## 6. 影響範囲

- **これまで描けなかった、幅か高さが 4,096〜100,000 px の PlantUML の図が描けるようになる。** Markdown の中のブロックと PlantUML のファイル（FR-025）の両方。
- **描いている間も原文が出ている**（v1.2.0-rc.1 までは描き始めに原文を外していた）。描き終えると図に置き換わる。
- 上限を超えた図・対応していない図の文言が変わる（理由の候補と上限の値を足した）。
- **大きな図を描く間は画面が止まる**（2.3）。v1.0.0 からの振る舞いであり、上限を上げたことで止まる時間は変わらない（上限を超える図も、計算し終えるまで止まっていた）。

## 7. 修正の前後に確かめたこと

### 7.1 直す前（2026-11-11）

- 利用者の報告の形（参加者 4 人・`opt` 4 つ）で、メッセージ 100 本の図が 4,050 px・200 本が 7,740 px になることを測った（上限 4096 で後者は描けない）。
- 2.2 と 2.3 を、計測用のページ（`workspace/tmp/_pumlbench`。本物の `frontend/` と同梱資産）と v1.0.0 / v1.1.0 のタグの資産で測った。

### 7.2 直した後

- 描画スモーク 2 部 OK（limits 部で 6 節が理由表示、9 節が 413 × 90,120 px の図）。UT-812 の足したケースは、9 節の検査を外すと落ち、戻すと通る（UT-033）。
- **描いている間の図の場所**（本物のフロントエンド。`requestAnimationFrame` ごとに、見えている原文も図も無いフレームを数えた）: 線 1,000 本の class 図で、**直す前の `puml.js` は空のフレームが 3、直した後は 0**（描き終えるまでの 28 フレームのうち 27 で原文が見えていた）。縦に長いシーケンス図は計算の間ずっとメインスレッドが止まるため、直す前も空のフレームは無かった。
- 既存の DOM 検査（テーマの描き直し・拡大画面・原寸表示・コピー・図のファイル・コードブロックの編集欄・検索との組み合わせほか 11 本）がすべて PASS。**描画前の検索（BUG-017）の検査は、描けない PlantUML の図として「4096 px を超える class 図」を使っていたため、上限超えの図に替え、描けなかった原文がそのまま残る（ハイライトも現在位置も保たれる）ことを期待値にした**（Mermaid と同じ振る舞い）。
- 本物のフロントエンドで、上限付近の図の表示・拡大画面・原寸表示・スクロール・テーマの描き直しを測った（5.2）。
- `slow-plantuml.md` の最後の図が上限で拒まれること（1.2 秒）と、埋めの図 60 枚で約 10 秒かかることを測った。
- **rc.2 の手動テスト**: E2E-239 の確認内容 8〜10（W1 / L1。上限のすぐ下の図が描け、描いている間も原文が出ていて、拡大画面で見られる）、E2E-240 の確認内容 3・5（W1。上限を超えた図の理由の文と、9 節が描けること）、E2E-271 の手順 11〜13（埋めの図 60 枚で検索が間に合うこと）。
