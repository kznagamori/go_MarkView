# BUG-003: ウィンドウを最小まで狭めてもアウトラインが隠れない

| 項目 | 内容 |
| --- | --- |
| 不具合番号 | **BUG-003** |
| 報告日 | 2026-09-04 |
| 対象 | `v1.0.0-rc.2`（`aeae862` + リリース CI の資産更新コミット） |
| 検出 | 手動テスト **E2E-246**（NG） |
| 環境 | Windows / WebView2 |
| 関連要求 | UI-026, UI-011, UI-030, UI-040, UI-110, UI-114, DSP-380, IMP-246 |

---

## 1. 症状

**手順**（E2E-246）:

1. ツリーとアウトラインの両方を表示した状態で、ウィンドウを最小サイズ付近まで狭める
2. ツールバーのアウトラインボタンの状態を確認する
3. ウィンドウを元の幅に戻す

**期待**: 本文が読めなくなる前にアウトラインペインが隠れる（UI-026）
**実測**: **隠れない。** 実施者の記録は次のとおり。

> 本文、ファイルツリー、アウトラインとも最小幅以下にならない
> これは問題ないのでは？

つまり「狭めきっても、3 つのどれも下限を割らなかった」という観測である。

---

## 2. 原因

### 2.1 抑制が起きる条件（実装）

`frontend/js/panes.js` の `applyResponsive()` が判定する。

```js
const CONTENT_MIN = 240;         // UI-026 / DSP-380 の「本文の最小幅」
const PANE_MIN = 160;            // UI-030 / UI-040 の下限
const PANE_MAX_RATIO = 0.4;      // UI-030 / UI-040 の上限

export function applyResponsive() {
  const outline = state.outlineVisible ? effectiveWidth("outline") : 0;
  const tree    = state.fileTreeVisible ? effectiveWidth("filetree") : 0;
  const content = window.innerWidth - outline - tree;

  const suppressed = state.outlineVisible && content < CONTENT_MIN;
  ...
}

function clampWidth(px) {
  const max = Math.floor(window.innerWidth * PANE_MAX_RATIO);
  return Math.max(PANE_MIN, Math.min(Math.round(px), Math.max(PANE_MIN, max)));
}
```

条件を式にすると次になる。

```
抑制する  <=>  innerWidth - clamp(outlineWidth) - clamp(treeWidth) < 240
```

**`outlineWidth` と `treeWidth` は利用者が決めた値であり、設定に保存されて次回も残る**（UI-110, UI-114）。

### 2.2 幅の組み合わせによっては、**最小ウィンドウでも抑制が起きない**

最小ウィンドウ幅は 640（UI-011）。その幅における上限は `floor(640 * 0.4) = 256`、下限は 160 である。
組み合わせごとに計算すると次のようになる。

| アウトライン幅 | ツリー幅 | 実効値（640 でクランプ後） | 本文の幅 | 抑制するか |
| --- | --- | --- | --- | --- |
| 240（既定） | 260（既定） | 240 + 256 | **144** | **する** |
| 240 | 200 | 240 + 200 | **200** | **する** |
| 240 | 160（下限） | 240 + 160 | **240** | **しない**（`<` なので境界ちょうどは抑制しない） |
| 200 | 160 | 200 + 160 | **280** | **しない** |
| 160（下限） | 160（下限） | 160 + 160 | **320** | **しない** |

**両ペインを下限（160）まで狭めていると、本文は最小ウィンドウでも 320 px あり、UI-026 は決して発火しない。**
これは実装の都合ではなく、**UI-011（最小 640）・UI-030 / UI-040（ペイン下限 160）・UI-026（本文下限 240）という 3 つの要求の算術上の帰結**である。

```
到達しうる本文の最小幅 = 640 - 160 - 160 = 320  >  240
```

実施者の観測「本文、ファイルツリー、アウトラインとも最小幅以下にならない」は、**この状態そのものを述べている。**
そして「これは問題ないのでは？」という指摘は**正しい。** その幅の組み合わせでは、アウトラインを隠さないほうが UI-026 に忠実である。

### 2.3 なぜその幅になっていたのか — 直前のケースが幅を変える

**E2E-245（ペイン幅の変更）が E2E-246 の直前にある。**

> **手順**:
> 1. ツリーペインの右端の境界をドラッグして広げる
> 2. **極端に狭く、極端に広くしてみる**
> 3. アプリを再起動する

手順 2 で下限（160）まで狭めた状態が最後になれば、**その値が設定に保存される**（`setPaneWidth` → `saveConfig`。UI-114）。
手順 3 の再起動を挟んでも復元されるため、**E2E-246 はその幅を引き継いで始まる。**

**E2E-246 の前提条件は「ツリーとアウトラインの両方を表示している」だけで、幅を指定していない。**
したがってこのケースは、**直前のケースが何を残したかで結果が変わる。**

### 2.4 DSP-380 の作例は「既定幅」を黙って前提にしている

DSP-380 は次の作例を載せている。

```
1280px            → Files + Outline + 本文（980px 上限）
 800px            → Files + Outline + 本文（300px）
 640px（最小）     → Files + 本文（384px）  ← Outline を一時的に隠す
```

検算すると、いずれも**既定幅（アウトライン 240 / ツリー 260）**のときの値である。

| 幅 | 検算 |
| --- | --- |
| 800 | 800 − 240 − 260 = **300** ✓（本文 300 ≥ 240 なので抑制しない） |
| 640 | 640 − 240 − min(260, 256) = 640 − 240 − 256 = **144** < 240 → 抑制 → 640 − 256 = **384** ✓ |

**実装の計算は DSP-380 の作例と 1 px も違わない。**
つまり**実装は仕様どおりに動いている。** 仕様の作例が、成立に必要な前提（既定幅であること）を書いていない。

## 3. 原因の分類 — 仕様か、実装か

### 3.1 実装の誤り — **見つかっていない**

- 判定式は UI-026 / DSP-380 と一致する
- `outlineSuppressed` と `state.outlineVisible` を分けている（IMP-246 の要点）
- `aria-pressed` と設定値を変えていない（UI-026 の 2 番目の項目）
- `resize` を `requestAnimationFrame` でまとめている（NFR-012）
- `[hidden] { display: none !important }`（`base.css` 40）があるため、`hidden` 属性の切り替えは確実に効く

**コードを読む限り、抑制の条件が満たされれば正しく隠れる。**

> [!NOTE]
> **切り分けを実施し、実装が正常であることを確認した**（2026-09-05。7.1 の実施結果）。
> 既定幅（240 / 260）でウィンドウを最小まで狭めると、**アウトラインは隠れ、ボタンは ON のまま、広げると戻り、ファイルツリーは隠れなかった。**
> 本節の「実装の誤りは見つかっていない」は**推定ではなく実測に裏づけられている。** 修正対象はコードではなく、仕様とテスト仕様である。

### 3.2 一次原因 — **仕様の不備（UI-026 / DSP-380）**

UI-026 は「本文が 240 を下回ったら隠す」とだけ定めており、**その条件が到達可能かどうかに触れていない。**
NOTE では次のように述べている。

> 幅の上限規定（UI-030, UI-040）だけでは、最小ウィンドウ幅で両ペインを開いたときに本文が 150 論理ピクセル程度まで潰れ、実質的に読めなくなる。

**「150 px 程度まで潰れる」のは、両ペインが上限（40 %）にあるときだけである。** 下限（160）にあるときは 320 px あり、潰れない。
**この要求が守るべき状態は、幅の組み合わせによっては存在しない。** そのことが仕様に書かれていない。

DSP-380 も同様で、作例の 3 行が既定幅の場合の数値であることを明示していない（2.4）。

### 3.3 二次原因 — **テスト仕様の不備（E2E-246）**

前提条件が「ツリーとアウトラインの両方を表示している」だけであり、**幅を固定していない。**
ペイン幅は設定に保存されて再起動をまたぐ（UI-110, UI-114）ため、**このケースは再現性が無い。**

さらに、**直前の E2E-245 が幅を極端に変える手順を含んでいる。** 順に実施すると、E2E-246 が失敗する側の状態で始まる可能性が高い。

**これは「テストが偶然落ちた」のではなく、「テストの前提が足りない」ものである。**

## 4. なぜ単体テストと E2E の自動テストで見つからなかったのか

### 4.1 単体テスト — 対象外

31 章 31.10 の対応表はこうなっている。

```
| UI-026 | — (GUI) | |
```

判定は `frontend/js/panes.js` にあり、UT-002 が単体テストの対象を `internal/` に限っている。**フロントエンドのロジックにはテストが 1 件も無い。**

> [!NOTE]
> **この判定は「純粋な算術」であり、DOM に依存しない。** 単体テストにしやすい形をしている（入力は `innerWidth` / 2 つの幅 / 表示フラグ、出力は真偽値）。
> ただし AR-050 / BR-001 が Node.js とテストランナーの導入を禁じており、**JS の単体テストを走らせる場所が無い。** これは意図した割り切りであって、書き忘れではない。

### 4.2 自動 E2E — ウィンドウを持たない

40 章の対応表も、UI-026 の検証は手動ケースだけだと記録している。

```
| UI-026 | E2E-246 |  |
```

自動 E2E は配布物の検査と CLI の確認であり、**ウィンドウの大きさを変える経路が無い。**

### 4.3 仕様レビューでも見つからなかった

`specs-4.2.0` 以降、20 文書の横断レビューを複数回（4.7.0 / 4.10.0 / 4.22.0）実施しているが、**この種の「要求どうしの算術的な整合」は検査項目に入っていない。**
90 章の対応表は「要求 ↔ 実装 ↔ 表示」のひも付きを見るものであり、**数値の突き合わせは行わない。**

UI-011（640）・UI-026（240）・UI-030 / UI-040（160〜40 %）は**別々の章にある**ため、3 つを並べて計算する機会がなかった。

### 4.4 まとめ

| 層 | 捕まえられたか | 理由 |
| --- | --- | --- |
| 単体テスト | **できない** | 対象が `internal/` のみ（UT-002）。JS のテスト基盤を持たない（AR-050, BR-001） |
| 自動 E2E | **できない** | ウィンドウを操作しない |
| 仕様レビュー | **できたはず** | 3 つの要求の数値を並べれば「到達しない条件がある」ことは計算で分かる。**検査項目に無かった** |
| 手動テスト | **できた（ただし偶然）** | 幅の組み合わせが「抑制しない」側だったために露見した。既定幅なら OK になり、**問題は見つからないまま通過していた** |

> [!IMPORTANT]
> **この NG は、テストが弱いから見つかったのではなく、テストが不安定だから見つかった。**
> 既定幅で実施していれば E2E-246 は OK になり、仕様の穴は残ったままリリースされていた。

## 5. 修正方法

**この不具合の修正対象はコードではなく、仕様とテスト仕様である**（3.1 の IMPORTANT の切り分けで実装の誤りが見つかった場合を除く）。

### 5.1 案 1（推奨）— テスト仕様の前提条件を固定する

E2E-246 の前提条件に、**幅を既定へ戻す手順**を加える。

```
- **前提条件**: ツリーとアウトラインの両方を表示している。
  **両ペインの幅を既定（アウトライン 240 / ツリー 260）に戻しておく。**
  幅は設定に保存されるため（UI-110, UI-114）、直前の E2E-245 の状態を引き継がない。
  戻せない場合は %TEMP%\MarkView\config.json を削除して起動する。
```

**理由も併記する。** 「なぜ幅を戻すのか」が書かれていないと、次の実施者がまた同じ迷いに入る。

### 5.2 案 2（あわせて行う）— 仕様に成立条件を明記する

| 文書 | 直す内容 |
| --- | --- |
| `03-ui.md` UI-026 | NOTE に、**両ペインが下限（160）にあるときは最小ウィンドウでも本文が 320 px あり、この要求は発火しない**ことを明記する。「潰れる」のは幅が広い側にあるときだけである |
| `22-display-states.md` DSP-380 | 作例の 3 行が**既定幅（240 / 260）の場合の数値**であることを明記する。数値だけを見て実装すると、条件の成立範囲を誤る |
| 同上 | 「到達しうる本文の最小幅 = 640 − 160 − 160 = 320」を表に加え、**UI-026 の閾値 240 との関係**を書く |
| `docs/specs/README.md` | 改訂履歴に 1 行追加し、版を上げる（NFR-071） |

### 5.3 採らない案 — 閾値を上げる

`CONTENT_MIN` を 320 より大きくすれば、下限幅でも発火するようになる。**これは行わない。**

- 本文 320 px は読める幅である。隠す理由が無い
- UI-026 は「**読めなくなる前に**隠す」ための規定であり、読める状態で隠すのは要求に反する
- 閾値は UI-026 と DSP-380 の 2 か所に書かれた数値であり、変えれば両方の改訂が要る。**得るものが無い**

### 5.4 採らない案 — ペイン幅の下限を上げる

`PANE_MIN` を上げれば下限側でも発火するが、**UI-030 / UI-040 が定める利用者の自由を狭める。** 目的と手段が逆である。

| 利用者への影響 | **無い。** 幅を狭めているときはアウトラインが出たままだが、本文は 320 px 以上あり読める。幅が広いときは仕様どおり隠れる |

| リリース判断 | **この 1 件だけならリリースを止める理由にならない。** ただし E2E-246 は「実施できないケース」であり、**この状態で OK を付けるべきではない** |

## 7. 修正後の検証方法

### 7.1 まず切り分ける（**これを最初に行う**）

**仕様・テスト仕様の不備なのか、実装の誤りなのかを確定させる。**

1. MarkView を終了する
2. `%TEMP%\MarkView\config.json` を削除する（設定が無くても既定値で起動する。UI-113）
3. 起動して、ファイルツリーを表示する（既定では非表示。`FileTreeVisible: false`）
4. **幅を触らずに**ウィンドウを最小まで狭める

| 結果 | 判定 |
| --- | --- |
| **アウトラインが隠れ、ボタンは ON のまま、広げると戻る** | **実装は正常。** 本報告の 3.2 / 3.3 のとおり、仕様とテスト仕様を直す |
| **隠れない** | **実装の誤りが別にある。** `applyResponsive()` が呼ばれているか、`window.innerWidth` の値、`refresh()` の `hidden` の書き込みを順に確認する（`MARKVIEW_DEBUG=1` では JS のログは出ないため、WebView の開発者ツールで見る） |

#### 実施結果（2026-09-05）

**上の表の 1 行目。実装は正常である。**

| 実施したこと | 内容 |
| --- | --- |
| 使ったビルド | `build/bin/MarkView.exe`（2026-09-03。**この調査の時点からコードは 1 行も変わっていない**） |
| 設定 | **削除していない。** 実施前の `%TEMP%\MarkView\config.json` が既に `outlineWidth: 240` / `fileTreeWidth: 260` を持ち、`config.go` の既定値と一致していたため、7.1 の手順 2 は不要だった（削除すると `editor` の設定も失われる） |
| 観測 | **アウトラインが隠れ、`Outline` ボタンは ON のまま、広げると戻った。ファイルツリーは隠れなかった** |

**DSP-380 の検算どおりである。** 640px で `240 + 256（上限 40 % で縮む）= 496` が引かれ、本文は 144px となって閾値 240 を下回る。

したがって**本報告の 3.2 / 3.3 が確定**し、修正は仕様（UI-026 / DSP-380）とテスト仕様（E2E-246）に対して行う。
**いずれも 2026-09-04 の 4.23.0 で反映済みであり、この不具合に対するコードの変更は無い。**

### 7.2 仕様・テスト仕様を直したあとの手動

1. **E2E-246（改訂後）**（W1）— 既定幅で最小まで狭める → アウトラインが隠れ、ボタンは ON のまま、広げると戻る、ツリーは隠れない
2. **下限幅での確認（新規の観点）** — 両ペインを 160 まで狭めてから最小ウィンドウにする → **アウトラインは隠れない。それが正しい**（本文 320 px）
3. **E2E-245 の回帰** — 幅の下限・上限・再起動後の保持

### 7.3 機械的な確認

```bash
# 閾値が仕様と一致していること（240 / 160 / 0.4）
grep -n "CONTENT_MIN\|PANE_MIN\|PANE_MAX_RATIO" frontend/js/panes.js
grep -n "240\|160\|40 %" docs/specs/03-ui.md docs/specs/22-display-states.md
```
