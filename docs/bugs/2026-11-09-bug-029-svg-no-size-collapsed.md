## 1. 症状

`width` / `height` を持たず `viewBox` だけを持つ SVG（アイコンや図の書き出しに多い形）を画像として表示すると、**本文に何も見えない。** 画像の場所には高さの無い隙間だけが残る。

| 場面 | GitHub・v1.0.0 | v1.1.0 | v1.2.0 の実装中（T28-1 の前） | 直した後 |
| --- | --- | --- | --- | --- |
| Markdown に埋め込んだ SVG（`![…](nosize.svg)`。本文の幅 916px） | **本文の幅いっぱい**（916 × 458） | **0 × 0**（見えない） | 0 × 0 | 916 × 458 |
| 画像ファイルとして開いた SVG（FR-027） | — | — | **0 × 0**。ステータス領域に `300 × 150 px` が出る | 916 × 458。寸法は出さず大きさだけ |

数値はヘッドレスの Edge 157（ウィンドウ 1280 × 800）で測った。`nosize.svg` の `viewBox` は `0 0 200 100`（縦横比 2 : 1）。

---

## 2. 原因

### 2.1 画像を包む器が中身に合わせて縮む

v1.1.0 は、原寸表示と拡大画面のボタン（FR-120）を画像の右上に置くため、読み込めた画像を次の形に包む（IMP-228）。

```html
<span class="media-image">                 <!-- display: inline-block（DSP-124）。中身に合わせて縮む -->
  <span class="media-frame"><img …></span>  <!-- display: block、max-width: 100% -->
  <span class="media-actions">…</span>
</span>
```

**`inline-block` の器は、中身の大きさに合わせて縮む（shrink-to-fit）。** 大きさを持たない SVG は、自分の幅を持たない。**包む前（段落やブロックの中）では、ブラウザは CSS 2.1 の推奨どおり、囲む要素の幅いっぱいに描く**（916 × 458）。**中身に合わせて縮む器の中では、器の幅が中身で決まり、中身の幅が器で決まる循環になる**（CSS 2.1 は「未定義」とする）。Chromium はこれを幅 0 に解いた。

DSP-124 は「**包む前と画像の位置と大きさが変わらない**ようにする」と定めていたが、**それが成り立たない画像があることを考えていなかった。** 大きさを持つ画像（PNG・`width` / `height` のある SVG）では成り立つ。

### 2.2 v1.2.0 の仕様の前提: `naturalWidth` が 0 にならない

v1.2.0 の仕様（4.75.0〜4.80.0）は、**固有の大きさを持たない SVG は `naturalWidth` が 0 になる**として、次を定めていた。

- 読み込みの失敗の判定を `naturalWidth === 0` から `decode()` へ改める（IMP-226）。0 を失敗と取り違えないため
- 画像ファイルのステータス領域に、`naturalWidth` が 0 なら寸法を出さない（IMP-228, UI-060）
- 拡大画面の本来の大きさを、`naturalWidth` が 0 なら本文で描いている大きさにする（IMP-228, DSP-173）

**Chromium は、この SVG の `naturalWidth` / `naturalHeight` を 300 / 150 と返す**（既定の大きさ。縦横比に合わせた値）。W1（WebView2）も Chromium であり、**仕様どおりに作ると W1 では `300 × 150 px` が出る**（FR-027・E2E-393 の確認内容 8 に反する）。90.6.5 は「`naturalWidth` を 0 と返す」を**実機で確かめる前提**として挙げていたが、**実装の前にヘッドレスで確かめられた。**

`decode()` への改め（1 つ目）は、Chromium では害も益も無い（300 なので v1.1.0 の判定でも失敗と取り違えない）。0 を返すエンジンのために残す。3 つ目は、2.1 で本文に 0 × 0 で描かれるため、拡大画面の中身も 0 になっていた（WebKitGTK が 0 を返す場合）。

---

## 3. 原因の分類 — 仕様か、実装か

**仕様の不備である。** v1.1.0 の実装は DSP-124 と IMP-228 のとおりに作られており、**仕様が大きさを持たない画像の描き方を定めていなかった。** 要求（FR-022 の「画像の最大表示幅は本文幅」）は、大きさを持たない画像を消すことを求めていない。**GitHub は本文の幅いっぱいに描く**（MD-002）。

2.2 は v1.2.0 の仕様の前提の誤りで、v1.2.0 の実装より前に直したため配布物には入っていない。

## 5. 修正

### 5.1 実装（v1.2.0 の P28 の T28-1）

- **`frontend/js/media.js` の `classifyImage`**: 画像を包んだ直後に、**`naturalWidth` が 0 か、器が描かれているのに画像の幅が 0 に縮んだもの**を「大きさを持たない画像」と見分け、器に `is-fluid` を付ける。**器が描かれていない（閉じた `<details>` の中をエンジンが配置しない）ときは決めずに残し**、`toggle` と幅の変化（判定のやり直しの契機）で決める。**書き手が `width` / `height` を書いた画像（生 HTML）は見分けない。**
- **`frontend/css/markdown.css`**: `.media-image.is-fluid` を `display: block` にし、中の画像を `width: 100%` にする（本文の幅いっぱい）。**`width: 100%` は明示する**——ブロックの中で幅いっぱいに描くのは CSS 2.1 の推奨にすぎず、要求をエンジンの既定に委ねない（NFR-061）。
- **画像ファイルのステータス領域**: 寸法を出すのは、見分けで `is-fluid` にしなかった画像だけ（`naturalWidth` が 0 かどうかでは決めない）。
- **拡大画面**: 本来の大きさを、本文から外す前に `naturalSize` で測る（`naturalWidth` が 0 のエンジンでは本文で描いている大きさ。本文で幅いっぱいに描かれるので、0 にならない）。

### 5.2 仕様（4.91.0）

| 対象 | 変えたこと | 規定 |
| --- | --- | --- |
| 要求 | **固有の大きさを持たない画像は、本文の幅いっぱいに縦横比を保って描く**（GitHub と同じ）。画像ファイルも同じ | FR-022, FR-027 |
| 実装 | 見分け方（上の 5.1）と `is-fluid`。寸法を出す条件を `naturalWidth` から見分けの結果へ。Chromium が 300 を返すことを書いた | IMP-228 |
| 表示 | `.media-image.is-fluid` の表示と、`width: 100%` を明示する理由 | DSP-123, DSP-124, DSP-129 |
| 手動テスト | **E2E-236 に手順 10 と確認内容 13**（`testdata/e2e/README.md` の画像の節に埋め込んだ `nosize.svg` が本文の幅いっぱいに出る）。**E2E-393 の確認内容 8** に、画像ファイルの `nosize.svg` が本文の幅いっぱいに出ること | E2E-236, E2E-393 |
| 検証用データ | `testdata/e2e/README.md` の「画像」の節の末尾に「大きさを持たない SVG」の小節 | 40.2 |
| E2E の方針・対応表 | 40.3 の不具合の表に BUG-029 の行、40.5 の FR-022 の備考、90.6.5 の前提の行（「`naturalWidth` を 0 と返す」は Chromium で成り立たなかった） | 40.3, 40.5, 90.6.5 |

### 5.3 採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| 見分けた画像は包まない（ボタンを付けない） | 画像ファイルの拡大画面のボタン（FR-027 は「読み込みに成功していれば常に出す」）が無くなる |
| 既定の大きさ（300 × 150）で描く | GitHub（本文の幅いっぱい）と見た目が違う（MD-002）。利用者の判断で幅いっぱいとした |
| `naturalWidth` が 0 かどうかだけで見分ける | Chromium は 300 を返すため、W1 で見分けられない |
| **包む前に描かれた幅が `naturalWidth` を超えるかで見分ける**（利用者に示した案の見分け方） | 閉じた `<details>` の中（描かれていない）と、本文の幅が 300px より狭いときに見分けられない。**包んだ後に幅 0 に縮んだことを見るほうが、症状そのものを見ている**ため、こちらにした（結果の描き方は同じ） |
| Go 側で SVG のルート要素の `width` / `height` を読む | 画像ファイルは中身を読まない（IMP-102, IMP-128）。埋め込み画像（リモートを含む）には使えない |

## 6. 影響範囲

- **表示だけである。** 文書・設定に影響しない。
- **v1.1.0 で、`width` / `height` の無い SVG を Markdown に埋め込んだ文書**（ローカル・リモートとも。MD-071）では、その画像が見えない。原寸表示と拡大画面のボタンも出ない（縮小表示中にならないため）。
- `width` / `height` を持つ SVG、PNG などの画像、読み込みに失敗した画像（`span.img-broken`。包まない）は影響を受けない。
- 生 HTML で `width` を書いた大きさを持たない SVG は、その幅で描かれていた（影響を受けない）。

## 7. 修正の前後に確かめたこと

### 7.1 直す前（2026-11-09）

- **本物の `index.html` と `main.js` を Go のバインドと Wails のランタイムの代役で起動する使い捨ての検査**（`workspace/tmp/_nosizeprobe`。ヘッドレスの Edge 157）で、**`v1.1.0` のタグの木のフロントエンド**（`git worktree add --detach`）に、本物の `document.Load` で変換した Markdown（`before ![nosize](nosize.svg) after`）を渡し、`/__local/` を本物の `assetsrv` で配った。**画像は 0 × 0、器は幅 0 だった**（`naturalWidth` は 300）。
- `v1.0.0` には `frontend/js/media.js` が無く、画像を包まない（`git cat-file`）。包む処理は `20d2479`（2026-09-18。`v1.1.0-rc.1` から）で入った（`git log -S media-image`）。
- **配布物の実機（WebView2 / WebKitGTK）では確かめていない。** WebKitGTK が大きさを持たない画像を `inline-block` の中でどう描くか（0 にするか、既定の大きさにするか）と、`naturalWidth` に何を返すかは分からない。

### 7.2 直した後

- 使い捨ての DOM 検査 `workspace/tmp/_imagefilecheck`（本物の `document.Load` の HTML と本物の `assetsrv`）で、次を確かめた（47 項目すべて PASS）。画像ファイルと段落の中の `nosize.svg` が 916 × 458 で、器に `is-fluid` が付く。**大きさを持つ SVG（`width="300" height="150"`）は見分けず 300 × 150 のまま、寸法 `300 × 150 px` を出す**。生 HTML で `width="200"` を書いた `nosize.svg` は 200px のまま。閉じた `<details>` の中のものは開いた後に幅いっぱい。描かれていない間（本文ペインを `display: none`）は決めず、描かれた後に決める。**`naturalWidth` を 0 に差し替えたページ**（WebKitGTK の場合を再現）でも幅いっぱいで、寸法を出さず、拡大画面の中身が縦横比 2 : 1 で出る。
- **実装を壊して確かめた**: 見分けを消す・描かれていない間も決める・描かれた後に決め直さない・寸法を `naturalWidth` で決める・器をブロックにしない、の変異でいずれも FAIL になった。**`width: 100%` を外す変異だけは PASS のまま**（Chromium はブロックの中で幅いっぱいに描くため。5.1 のとおり NFR-061 のために明示している）。
- v1.1.0 の DOM 検査（`_mediacheck` / `_expandcheck` / `_redrawcheck` ほか）は全 PASS。
- **v1.2.0 の rc の手動テストで、E2E-236 の確認内容 13 と E2E-393 の確認内容 8 を W1 / L1 で見る。**
