## 1. 症状（コードから導いたもの）

**文書を表示している状態で、本文の中の「画像やその他のファイルへのリンク」または「`http(s)` / `mailto` のリンク」を押し、OS への委譲に失敗すると起きる。**

| # | 条件 | 起きること | 経路 |
| --- | --- | --- | --- |
| 1 | **Linux で `xdg-open` が `PATH` に無い**環境で、`[図を既定のビューアで開く](./docs/img/sample.png)` を押す（最小構成のデスクトップ、`xdg-utils` を入れていない環境） | **本文が消え、本文ペインに `render-error` の状態画面（`Failed to render this document.`）が出る。** 主テキストは `sample.png`（リンクの `href` の名前）である。ステータス領域に理由は出ない。**文書は描画に失敗していない** | `link.go:67-71` が `opener.OpenFile` を呼び、`opener.go:95-100` の `exec.Command("xdg-open", …).Start()` が見つからないエラーを返す。`link.go:88-90` の `linkFailure` → `errors.go:56-70` の `newErrorDTO` → `errors.go:94-124` の `classifyError` は、どの番兵にも当たらないため **`errors.go:120-122` の既定の枝で `render-error`** にする。フロントエンドは `main.js:375-393` の `handleLink` の `default` から `main.js:205-215` の `showError` を呼び、`render-error` が `STATE_SCREENS`（`main.js:35-39`）にあるため `showStateScreen` が本文を空にする |
| 2 | 1 と同じ環境で、`https://` のリンクや `mailto:` のリンクを押す | 1 と同じ | `link.go:51-56` → `opener.go:43-55` の `OpenURL` → `open` が同じエラーを返す |
| 3 | リンクを押してから `opener.OpenFile` が確かめるまでの間に、リンク先のファイルが消える | 1 と同じ（OS を問わない。**時間の窓は狭い**） | `link.go:61` の存在確認の後で、`opener.go:70-72` が `opener.ErrNotFound` を返す。`classifyError` は `document.ErrNotFound` と `fs.ErrNotExist` しか見ない（`errors.go:96`・`errors.go:114`）ため、これも既定の枝へ落ちる |

- **許可されていないスキーム**（`javascript:` / `file:` など）も同じ既定の枝へ落ちる（`opener.go:50-52` の `ErrUnsupportedScheme`）。**ただし現在は本文から届かない。** サニタイズが `http` / `https` / `mailto` 以外のスキームの `href` を落とす（`internal/renderer/sanitize.go:66-68`）ためである。**FR-050 の IMPORTANT は「リンク先を開けない旨をステータス表示する」と定めており、届いた場合の写像も同じく誤っている。**
- **Go 側の状態は変わっていない。** `followLink` は `open` を呼ばないため、`current` と `target`、ウィンドウタイトルは元の文書のままである。**画面だけが状態画面になり、Go 側は文書を表示しているつもりでいる**（IMP-190 の「画面の対象」と画面が食い違う）。「エディタで開く」は押せ、元の文書が開く。
- 状態画面から元の文書へ戻るには、ツリーから開き直すか `F5` を押す。`Alt+←` は**履歴を 1 つ前へ戻る**ため、元の文書ではなくその前の文書へ移る（リンクの失敗は履歴に積まれていない）。

> [!IMPORTANT]
> **「開けなかった」を「描画に失敗した」と伝えている。** 利用者は文書が壊れていると受け取り、
> 原因（`xdg-open` が無い）へ辿り着けない。FR-053 は「既定のアプリケーションが関連付けられていない、
> またはファイルが存在しない場合、その旨をステータス表示する」と定めている。

## 2. 原因

### 2.1 委譲の失敗に `Kind` が無い

IMP-312 は「`opener` が受け付けないスキームは `kind: error` とする」と定め、IMP-305 は「失敗は `ErrorDTO` をそのまま載せる」と定める。**しかし IMP-315 の分類表には、リンク先を OS へ委譲して失敗したことを表す行が無い。** あるのは `link-not-found`（リンク先が見つからない）であり、これは `link.go` が存在確認の時点で返す `errLinkNotFound` だけに対応する。

### 2.2 分類できないエラーが、状態画面の種別へ落ちる

IMP-315 の `render-error` の行は「変換エラー・パニック回復」である。実装（`errors.go:54-55` のコメント）は「分類できないエラーは `render-error` とする。想定外の失敗を『見つからない』と伝えると、利用者は存在するファイルを探し続ける」とし、既定の枝をここへ向けた。**文書を開く経路ではこの判断は正しい**が、**`FollowLink` の委譲の失敗は文書を開く失敗ではなく、状態画面を出す理由が無い。**

### 2.3 フロントエンドは `Kind` で表示先を選ぶ

`showError` は `Kind` が状態画面の種別なら状態画面を、それ以外ならステータス領域を選ぶ（IMP-315 の「表示先」列どおり）。**リンクの失敗かどうかは見ない。** リンク先が大きな Markdown だった場合に確認画面を出す必要がある（IMP-305）ため、この振る舞い自体は正しい。

---

## 3. 原因の分類 — 仕様か、実装か

### 3.1 一次原因 — **仕様の不足**

**FR-053 と FR-050 の IMPORTANT は「ステータス表示」を求めているのに、IMP-315 がそのための `Kind` を持たず、FR-110 の通知の一覧にも行が無かった。** 実装者は既存の分類のどれかへ写すしかなく、「分類できないもの」として扱った。

- FR-110 の表には「リンク先が見つからない」（FR-050）と「リンク先を開けない」（FR-050 / FR-053）の行が**どちらも無かった**。**要求の一覧に無い通知は、下位の分類表からも漏れる。**

### 3.2 実装の既定の枝も、利用者に誤った理由を伝えている

分類できないエラーを状態画面の種別へ落とす既定は、**表示先まで変えてしまう。** 仕様の不足を直した後も、`FollowLink` の失敗は `open-failed` へ明示的に写し、既定の枝に頼らない。

## 4. なぜ見つからなかったのか

| 層 | 見つからなかった理由 |
| --- | --- |
| 単体テスト | `opener` の単体テスト（UT-701 / UT-702）は、スキームの拒否と組み立てた引数を見る。**`package main` の `classifyError` と、フロントエンドの表示先の選択は対象外**（UT-002） |
| 自動 E2E | ウィンドウを操作しない（E2E-020）。起動するのは実際の OS のハンドラであり、自動では押さない |
| 手動テスト | E2E-264 は**委譲に成功する環境**でだけ行う。W1 は `rundll32.exe` が必ずあり、L1 の試験環境は `xdg-utils` を持つ。**失敗させる手順がどのケースにも無い** |
| 仕様レビュー | FR-053 の「その旨をステータス表示する」と IMP-315 の表を突き合わせていなかった |

## 5. 修正方法

### 5.1 採った案 — 委譲の失敗に専用の種別 `open-failed` を置く

| 対象 | 変えること | 規定 |
| --- | --- | --- |
| 要求 | FR-110 の表に「リンク先が見つからない（FR-050）」と「リンク先を開けない（許可されていないスキーム・既定のアプリケーションが無い。FR-050, FR-053）」を足す。**通知先はステータス領域、描画は直前の内容を維持** | FR-110 |
| Go | IMP-315 に **`open-failed`**（ステータス、`Cannot open: <href>`）を足す。`FollowLink` が OS へ委譲して失敗したもの（`opener.ErrUnsupportedScheme`、`opener.ErrNotFound`、プロセスを起動できない）は、**すべてこれに写す**。既定の枝（`render-error`）へ落とさない | IMP-315, IMP-312 |
| フロントエンド | `strings.js` に `errOpenFailed` を足し、`open-failed` と対応させる | IMP-290 |
| 手動テスト | E2E-264（外部リンクと画像リンク。W1 / L1）に、**L1 で `xdg-open` の無い `PATH` で起動し、画像へのリンクを押す**手順を足す（本文が残り、ステータス領域に `Cannot open:` が出る） | E2E-264 |

### 5.2 採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| 既存の `link-not-found` に写す | **ファイルは在る。** 「見つからない」と伝えると、利用者は存在するファイルを探し続ける（`errors.go:54-55` のコメントが既定の枝を `not-found` にしなかった理由と同じ） |
| 分類できないエラーの既定を、ステータス領域に出す種別へ変える | **文書を開く経路の想定外の失敗が、状態画面ではなく 1 行の通知になる**（FR-111 は想定外のエラーを状態画面に出すと定める）。経路ごとに既定を変えるより、`FollowLink` の失敗を明示的に写すほうが、次に経路を足したときに誤らない |
| フロントエンドの `handleLink` で、リンクの失敗は状態画面に出さない | **リンク先が大きな Markdown のときの確認画面（IMP-305, FR-016）が出なくなる。** 表示先の判断を `Kind` 以外に広げると、IMP-315 の表が表示先の正でなくなる |

## 6. 影響範囲

- **文書の内容は変わらない。** 表示だけの不具合である。
- **v1.1.0 では、画面と Go 側の状態の食い違いが編集モードに及ぶ。** 状態画面を出す経路は文書の切り替えとして後始末をする（IMP-250）が、Go 側は `Left` を呼んでいない（`open` を通っていない）。**編集モードの状態（IMP-109）とボタンの表示が食い違う経路になる**ため、対策を入れずに実装しない。
- セキュリティ上の影響は無い。**許可されていないスキームを OS へ渡していない**ことは変わらない（NFR-030）。

## 7. 修正後の検証方法

### 7.1 機械的な確認

**無い。** `classifyError` の写像とフロントエンドの表示先は、単体テストの対象外である（UT-002）。`opener` がスキームを拒むこと（UT-701）と、コマンドを別々の引数で組み立てること（UT-702）は既存の単体テストが見ているが、**起動に失敗したときにエラーを返すことは見ていない**（実際にプロセスを起動するテストは書かない。UT-035）。

### 7.2 実機での確認（L1）

E2E-264（4.44.0 で L1 の手順 3 を追加）で行う。**`xdg-open` が `PATH` に無い状態で起動し**（例: `env PATH=/nonexistent ./MarkView testdata/e2e/README.md`）、画像へのリンクを押す。**実装の前に同じ手順で `render-error` の状態画面が出ることを確かめてから直す。**

### 7.3 回帰

リンクの結果の写像を変えるため、次を見る: 外部リンクと画像リンク（E2E-264）、相対リンクの遷移（E2E-261）、アンカー付きリンク（E2E-263）、**リンク先が大きな Markdown の場合の確認画面**（FR-016。IMP-305）。
