## 1. 症状（コードから導いたもの）

**状態画面**とは、本文ペインに文書の代わりに出す画面のうち `confirm-large`（10 MB 超の確認）/ `too-large`（50 MB 超）/ `render-error`（描画の失敗）である（UI-052）。**文書 A（例 `README.md`）を表示した後に、状態画面になるファイル B（例 12 MB の `big.md`）を開くと起きる。**

| # | 操作 | 起きること | 経路 |
| --- | --- | --- | --- |
| 1 | A を表示してから、ツリーで B を選ぶ | **ウィンドウタイトルは `big.md - MarkView` になるのに、ステータス領域の左は `README.md` のまま、右も A の文字コードと行数のまま**残る。**ツリーの強調も A のまま**である（DSP-302 は 3 つとも「対象ファイル」と定める。FR-016 は「確認画面を表示した時点でパス表示を対象のものに更新する」と定める） | タイトルは Go 側が `screenTarget` から決める（`open.go:66`・`open.go:76-78`）。**ステータス領域は `status.js:19-48` の `updateStatus` が `state.doc` だけを見て組み立て**、`state.doc` を差し替えるのは文書を描いたとき（`viewer.js:92`）だけである。状態画面を出す `main.js:205-215` の `showError` → `overlay.js:83-115` の `showStateScreen` はステータス領域を触らない。ツリーの強調も `filetree.js:342-343` の `markSelected` が `state.doc` から決める |
| 2 | 起動時の引数に B を渡す（`MarkView big.md`） | 確認画面は出るが、**ステータス領域の左が空**になる | `main.js:151-152` が `updateStatus()` を呼ぶが、`state.doc` が `null` のため `status.js:25-27` でパスを消す。`ErrorDTO`（IMP-307）には表示用の相対パスが無く、フロントエンドは組み立てられない |
| 3 | 1 の確認画面を出したまま、別のエディタで A を書き換えて保存する | **確認画面が消え、A の表示に戻る。** タイトルも `README.md - MarkView` に戻り、`Open anyway` を押す手段が消える。**履歴の現在位置は B のまま**であり、`Alt+←` を押すと、いま見ている A へ「戻る」ことになる | `open.go:199-218` の `commitPending` は監視に触れず、監視を切り替える `watchCurrent` は読み込みに成功したときだけ呼ばれる（`open.go:172`）。**A の監視が残る。** 監視のイベントは `app.go:286-293` → `app.go:301-310` の `onCurrentModified(ev.Path)` が**イベントのパスをそのまま**開き直し（`openFromReload`）、`target` を A へ戻し（`open.go:146-147`）、確認待ちを消し（`open.go:176`）、`document:changed` を送る。フロントエンドはこれを文書の表示として描く（`main.js:166`） |
| 4 | 1 の確認画面を出したまま、A を削除する | **B の確認画面の上に `File was deleted: README.md` が出る** | `app.go:315-317` の `onCurrentRemoved` が A の削除を送り、`main.js:169` がそのまま出す |
| 5 | 1 の確認画面を出したまま、`F5`（または再読み込みのボタン）を押す | **B ではなく A が読み直され、確認画面が A の表示に置き換わる。** タイトルとステータス領域が B を指している（1 の直し方をした後）のに、押すと別の文書が出る | `bind.go:253-265` の `Reload` は `current`（A）を開き直す。FR-015 は「表示中のファイル」とだけ書いており、状態画面の場合を定めていなかった |

- **`too-large` と `render-error` でも同じである。** どちらも `commitPending` を通り（監視が残る）、`showStateScreen` を通る（ステータス領域が残る）。
- 1 の症状は**リンクと履歴から B を開いた場合も同じ**である（`openFromLink` / `openFromHistory` も `commit` を通る）。
- **v1.1.0 の仕様（4.43.0）のままでは、1 の症状の形が変わるだけで直らない。** IMP-250 は状態画面へ移るときに `state.doc` を `null` にすると定めており、ステータス領域のパスは**空**になる（DSP-302 の「対象ファイル」にはならない）。3 は、**編集モードの判断（IMP-109）にも読み込みの結果を渡す**ため、状態画面の間に A の `Loaded` が呼ばれ、画面と Go 側の状態が食い違う形でも現れる。

> [!IMPORTANT]
> **3 は「勝手に画面が変わる」ように見える。** 利用者は B を開こうとして確認画面を見ているのに、
> 別のエディタで A を保存した瞬間に A が表示される。**A を書き換えているのは利用者自身**（UC-03 のように
> 外部エディタで文書を直しながら MarkView で見る使い方）であり、ありふれた操作で起きる。

## 2. 原因

### 2.1 状態画面の対象を、ステータス領域を組み立てる側が知らない

ステータス領域の左に出す**表示用のパス**（ツリールートからの相対パス、ツリー外なら絶対パスと `(outside tree)`。UI-060, DSP-150）は **Go 側が算出する**（`session.DisplayPath`。`open.go:180`）。算出するのは**読み込みに成功したときだけ**であり、結果は `DocumentDTO` に載る。

状態画面になった場合、フロントエンドへ届くのは `ErrorDTO`（IMP-307）であり、**`Kind` / `Message` / `Path` / `Size` / `Limit` しか無い。** 表示用のパスもツリー外かどうかも載っていない。フロントエンドは相対パスを自分で組み立てない（IMP-300 と同じく、パスの解釈は Go 側に置く）ため、**正しく出したくても出せない。**

### 2.2 状態画面へ移っても、前の文書の監視を外していない

FR-014 は「表示対象を切り替えたときは、以前のファイルの監視を解除する」と定める。**状態画面への移行も表示対象の切り替えである**（1.7 の「文書の切り替え」、IMP-250 の「状態画面へ移ることは文書の切り替えである」）。しかし IMP-192 は「監視対象の切り替え（`watcher.Watch`）もここで行う」とだけ書き、**状態画面になった結果でどうするかを定めていない。** IMP-314 の「監視は張らず」は**確認画面の対象 B を監視しない**ことであり、A の監視を外すことではない。

### 2.3 監視のイベントを、いまの画面の対象と照らしていない

`onCurrentModified` はイベントのパスを**そのまま**開き直す（`app.go:301-310`）。**そのパスが、いま画面が対象にしているファイルかどうかを確かめていない。** IMP-320 も IMP-192 も、この確認を定めていない。監視が 1 つ以下であることだけに頼っているため、2.2 で監視が残ると、前の文書のイベントが画面を上書きする。

## 3. 原因の分類 — 仕様か、実装か

### 3.1 一次原因 — **仕様の不足**

**要求と表示仕様は正しい振る舞いを定めていたが、実装仕様がそれを実現する手段を定めていなかった。**

| 要求・表示仕様が求めること | 実装仕様の不足 |
| --- | --- |
| FR-016「確認画面を表示した時点で、ウィンドウタイトルとステータス領域のパス表示を対象ファイルのものに更新する」、DSP-302（`confirm-large` / `too-large` / `render-error` の行のステータスとツリーの強調は「対象ファイル」） | IMP-307 の `ErrorDTO` に表示用のパスが無い。IMP-250 はステータス領域の更新を書いていない（4.43.0 では `state.doc = null` とし、パスが空になる） |
| FR-014「表示対象を切り替えたときは、以前のファイルの監視を解除する」、FR-016「確認画面を表示しているだけの状態では監視しない」 | IMP-192 は状態画面になった結果での監視の扱いを定めていない。IMP-320 は監視のイベントを画面の対象と照らすことを定めていない |

- **タイトルは正しく更新されている**（UI-013。IMP-190 / IMP-192 の `target`）。タイトルとステータス領域の片方だけが対象に追随しており、**同じ要求の文の半分だけが実装仕様へ降りていた。**

### 3.2 実装は実装仕様どおりである

`updateStatus` が `state.doc` を見ること（IMP-220 の手順 10）、状態画面で `state.doc` を差し替えないこと（IMP-250）、成功したときに監視を切り替えること（IMP-192）は、いずれも実装仕様に反していない。

## 4. なぜ見つからなかったのか

| 層 | 見つからなかった理由 |
| --- | --- |
| 単体テスト | `package main` とフロントエンドは対象外（UT-002）。`session.DisplayPath` の単体テストは、**算出が正しいこと**しか見ない（BUG-005 と同じ形） |
| 自動 E2E | ウィンドウを操作しない（E2E-020） |
| 手動テスト | **E2E-322 の確認内容は、確認画面の表示・`Open anyway`・上限超過だけ**であり、ステータス領域のパス・ツリーの強調・`Alt+←` を見ていない。E2E-226（自動反映）と E2E-324（削除）は、**文書を表示している間**の監視だけを見る。E2E-345 は手順 3 で「ステータス領域が大きなファイルを指していることを確かめる」と書くが、**手順であって確認内容ではない**（記録の対象にならない）。**確認画面を出したまま前の文書を外部で書き換える手順は、どのケースにも無い** |
| 仕様レビュー | DSP-302 の表と FR-016 の文は読まれていたが、**「その値をどこから取るか」まで降りて確かめていなかった** |

> [!IMPORTANT]
> **E2E-345 の手順 3 は、確認していないのに確認したように読める。** UI-031 が 1 行の確認内容を通り抜けたのと同じ形である
> （4.38.0）。**確かめたいことは確認内容に番号付きで書く**（E2E-200）。

## 5. 修正方法

### 5.1 採った案 — 状態画面の対象を `ErrorDTO` で渡し、状態画面へ移るときに前の文書の監視を外す

| 対象 | 変えること | 規定 |
| --- | --- | --- |
| Go ↔ フロントエンド | `ErrorDTO` に **`DisplayPath string` / `OutsideTree bool`** を足す。状態画面の種別（`needs-confirm` / `too-large` / `render-error`）で設定し、`session.DisplayPath` を使う（成功したときと同じ算出）。起動時の `confirm-large`（IMP-193）も同じ値を載せる | IMP-307, IMP-193 |
| Go（監視） | **状態画面になる結果では、前の文書の監視を外し、画面が文書を表示していない（`showing` が偽）ことを記録する。** 監視のイベントは `ioMu` を取った後で「`showing` が真で、イベントのパスが `current` と同じファイル」であることを確かめ、違えば捨てる。状態画面の間の `SameDocument` は偽とする | IMP-192, IMP-320, IMP-321 |
| フロントエンド | 状態画面を出すとき、`state.target = { path, displayPath, outsideTree }` を置く。`updateStatus()` は `state.doc ?? state.target` のパスを出し、状態画面の間の右側（文字コード・行数）は空にする。**ツリーの強調（DSP-302 の列）も同じ対象に合わせる** | IMP-250, IMP-220 |
| Go（再読み込み） | **`Reload` は画面の対象（`target`）を読み直す。** 状態画面の間はその対象をもう一度開く（利用者の判断。FR-015 に明記した） | FR-015, IMP-310 |
| 手動テスト | E2E-322 を広げる: 確認画面・上限超過でステータス領域の左が対象を指す、`Alt+←` で前の文書へ戻れる、**確認画面の間に前の文書を外部で書き換えても画面が変わらず、通知も出ない** | E2E-322 |

- **確認画面から `Open anyway` で描いたとき**は、通常の成功と同じく B の監視を張る（IMP-192）。
- **状態画面から `Alt+←` で A へ戻ったとき**は、A を開き直すため、その時点の A の内容が出る（監視が外れていた間の変更も反映される）。

### 5.2 採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| 監視は残し、状態画面の間に届いたイベントだけを捨てる | **FR-014 の「以前のファイルの監視を解除する」に反する**（監視を 1 つ以下にする規則は、監視の数ではなく「表示対象のファイルだけ」を意味する）。捨てたイベントの間に A が削除・再作成されると、戻ったときの監視の張り直しの前提も崩れる |
| フロントエンドが `ErrorDTO.Path` とツリールートから相対パスを組み立てる | **パスの解釈をフロントエンドに持ち込む**（IMP-300）。Windows の大文字小文字やシンボリックリンクの扱い（IMP-025）を 2 か所に書くことになり、ツリー外の判定が文書の表示と食い違いうる |
| 状態画面の間はステータス領域の左を空にする（4.43.0 の IMP-250 のまま） | **FR-016 と DSP-302 に反する。** タイトルだけが対象を指し、「いま何を開こうとしているか」をパスで確かめられない |

## 6. 影響範囲

- **文書の内容は変わらない。** 表示と監視だけの不具合である。
- **3 は、利用者が見ている対象を黙って入れ替える。** v1.0.0 では書き込みの経路が無いため、取り違えは表示にとどまる。**v1.1.0 では、状態画面の間に A の読み込みの結果が編集モードの判断（IMP-109 の `Loaded`）へ渡る**ため、対策を入れずに実装すると、画面の状態と Go 側の状態が食い違う経路になる。
- **「エディタで開く」の対象は正しい。** `target` は状態画面の対象 B を指しており（IMP-190）、1 の症状の間にエディタで開くのは B である。**3 の後は A になる**（タイトルと一致する）。

## 7. 修正後の検証方法

### 7.1 機械的な確認

**無い。** 変更はいずれも `package main` とフロントエンドにあり、単体テストの対象外である（UT-002）。表示用のパスの算出（`session.DisplayPath`）は既存の単体テストが見ている。

### 7.2 実機での確認（W1）

**E2E-322** の手順で行う（4.44.0 で手順と確認内容を足す）。**実装の前に同じ手順で症状（ステータス領域が前の文書のまま、確認画面が A の表示に戻る）が出ることを確かめてから直す。**

### 7.3 回帰

監視と状態画面の経路を変えるため、次を見る: ファイル更新の自動反映（E2E-226）、表示中ファイルの削除（E2E-324）、確認画面から `Open anyway`（E2E-322）、状態画面からエディタで開く（E2E-345）、状態画面の間に文書を切り替える操作（E2E-327 の手順 12）、**編集モードの自動終了**（E2E-381 の手順 8）。
