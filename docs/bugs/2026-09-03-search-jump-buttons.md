# 検索バーの「前へ / 次へ」ボタンで該当箇所へ移動しない

| 項目 | 内容 |
| --- | --- |
| 報告日 | 2026-09-03 |
| 対象 | `develop/work`（`74edeb2` 時点） |
| 環境 | Windows / WebView2 系 |
| 関連要求 | FR-080, UI-080, DSP-160, IMP-241, IMP-211 |
| 分類 | **実装の誤り 1 件 + 仕様の不備 1 件**（下記「原因の分類」） |
| 混入時期 | `5c1f34c feat: P4 フロントエンド — 表示と操作の一式`。**PlantUML 対応（P8）とは無関係** |

---

## 1. 症状

`Ctrl+F` で検索し、検索バーの **∧（前へ）/ ∨（次へ）ボタンをクリックしても、該当箇所へ移動しない。**

アウトラインの項目をクリックした場合は、該当する見出しへ正しく移動する。

**切り分けの結果、`Enter` / `Shift+Enter`（キーボード）では移動する**（利用者に確認。2026-09-03）。
**ボタン経路だけが効かない。**

| 操作 | 移動 |
| --- | --- |
| `Enter` / `Shift+Enter` | **する** |
| ∧ / ∨ ボタンのクリック | **しない** |
| アウトラインの項目クリック | する |

---

## 2. 原因

### 2.1 直接の原因 — ボタンのハンドラだけが、直後にスクロールを巻き戻している

`frontend/js/search.js` の `createButton`（末尾）。

```js
button.addEventListener("click", () => {
  handler();
  // 操作の続きをキーボードで行えるよう、入力欄へ戻す（UI-080）。
  if (state.search.open) $("search-input").focus();
});
```

`handler()` は `jump(±1)` → `select()` を呼び、その中で

```js
hits[wrapped].scrollIntoView({ block: "center" });   // ここで該当箇所へスクロールする
```

を実行する。**そこまでは正しく動いている。**

問題はその直後の `$("search-input").focus()` である。`HTMLElement.focus()` は
**既定で対象要素を可視域へスクロールする**（`preventScroll` を指定しない限り）。
検索バーが画面外にあると、ブラウザは**それを見せるために本文のスクロールを巻き戻す。**
結果として `scrollIntoView` の効果が打ち消される。

**キーボード経路にはこの `focus()` が無い。**

```js
// frontend/js/main.js
searchNext: () => jump(1),
searchPrev: () => jump(-1),
```

これが「`Enter` は動くがボタンは動かない」の理由である。
アウトライン（`frontend/js/outline.js` の `onClick`）も `target.scrollIntoView()` のあとに
`focus()` を呼んでいないため、正しく動く。

### 2.2 前提となる条件 — 検索バーは本文と一緒にスクロールして画面外へ出る

`focus()` が巻き戻すのは、**検索バーがそのとき画面外にあるから**である。なぜ画面外に出るのか。

```html
<!-- frontend/index.html 141〜144 -->
<section id="viewer" class="viewer" tabindex="-1">   <!-- スクロールする器 -->
  <article id="markdown" class="markdown-body"></article>
  <div id="state-screen" class="state-screen" hidden></div>
  <div id="searchbar" class="searchbar" hidden></div> <!-- ← 器の中にある -->
</section>
```

```css
/* frontend/css/base.css:176 */
.viewer { position: relative; overflow-y: auto; }

/* frontend/css/components.css:556 */
.searchbar { position: absolute; top: 16px; right: 16px; }
```

`position: absolute` の要素は、包含ブロック（`.viewer`）の**パディングボックス基準**で
配置されるが、**スクロールする内容の一部として一緒に流れる。**
`position: fixed` や `sticky` と違い、スクロール位置に固定されない。

したがって本文を下へスクロールすると、**検索バーは上へ流れて画面外へ出る。**

> [!IMPORTANT]
> **この 2 つは別々の欠陥であり、両方直さないと機能しない。**
>
> 2.1 だけを直すと、ジャンプは効くようになるが、**ジャンプ先で検索バー自体が画面外にあるため、
> 続けて ∨ を押すことができない。** 逆に 2.2 だけを直すと、検索バーが常に可視域にあるので
> `focus()` はスクロールを起こさなくなり、症状は消える。

### 2.3 実測（推測ではない）

`frontend/css/` の実物を読み込み、`index.html` と同じ入れ子を作って計測した
（HeadlessChrome 152 / Edg 152）。

| # | 検査 | 結果 |
| --- | --- | --- |
| 0 | 適用されている CSS | `searchbar: position=absolute, top=16px` / `viewer: position=relative, overflow-y=auto` |
| 1 | 検索バーはスクロールに追従するか | `scrollTop=0` で上端 **108px** → `scrollTop=800` で **−692px**。**本文と一緒に流れ、画面外へ出る** |
| 2 | `scrollIntoView` → `focus()`（ボタン経路） | `1078` → **`0`**。**1078px 巻き戻された** |
| 3 | `scrollIntoView` のみ（`Enter` 経路） | `1078` のまま。**巻き戻らない** |
| 4 | `focus({ preventScroll: true })` | `1078` のまま。**巻き戻らない** |

検査 2 と 3 の差が、そのまま「ボタンは効かない / `Enter` は効く」という症状に対応する。

## 3. 原因の分類 — 仕様か、実装か

**2 つの層に分かれており、答えも 2 つある。**

### 3.1 報告された症状そのもの → **実装の誤り**

FR-080 は次のように定めている。

> `Enter` / `Shift+Enter` **または検索バーのボタン**で、次・前の一致箇所へ移動する。
> **移動時は該当箇所までスクロールする。**

**仕様は明瞭であり、誤ってもいない。** 2 つの経路を明示的に挙げ、スクロールを **MUST** としている。
実装はそのスクロールを行ったうえで、自分で取り消している。

`createButton` のコメントは `focus()` の根拠を UI-080 としているが、UI-080 が定めているのは

> **表示と同時に**入力欄へフォーカスを移す。

であり、**「ボタンを押すたびにフォーカスを戻す」ことは要求していない。**
実装側が利便性のために足したものであり、その副作用が FR-080 の MUST を破っている。

### 3.2 検索バーが流れること → **仕様の不備（不明瞭）**

DSP-160 は位置をこう定めている。

| 項目 | 値 |
| --- | --- |
| 位置 | 本文ペインの右上（`position: absolute`）。本文を押し下げない（UI-080） |
| オフセット | 上 16px / 右 16px（スクロールバーの内側） |

**意図（本文ペインの右上）と実現手段（`position: absolute`）の両方が書かれているが、
`.viewer` がスクロールする器である以上、この手段では意図が実現しない。**

- UI-080 は「本文ペインの右上に**オーバーレイ表示**する」としており、常に見えていることを含意する
- DSP-160 の図も、ペインの右上に置かれた状態を描いている
- しかし `position: absolute` という指定だけを守ると、スクロールで流れ去る

**実装は下位仕様（DSP-160 の手段）に忠実に従った結果、上位仕様（UI-080 の意図）を満たしていない。**
5 層構成の「上位が下位を規定し、矛盾したら上位を正とする」に照らせば、**DSP-160 側の記述が不足している。**

> [!NOTE]
> **`position: absolute` 自体が誤りとは限らない。** 包含ブロックがスクロールしなければ正しく働く。
> 欠けているのは「**スクロールしても本文ペインの右上に留まること**」という、意図の側の記述である。
>
> 同じ `position: absolute` を使う `.state-screen`（`components.css:141`）は**安全**である。
> 状態画面を出すとき `showStateScreen`（`overlay.js`）が `clear($("markdown"))` で本文を空にするため、
> そもそもスクロールが発生しない。

## 4. なぜ単体テストと E2E の自動テストで見つからなかったのか

**3 つの層すべてで、構造上この経路に触れていなかった。**

### 4.1 単体テスト — 対象外（意図的な除外）

UT-002 は対象範囲をこう定めている。

| 区分 | 対象 | 根拠 |
| --- | --- | --- |
| 対象 | `internal/` 配下の全パッケージ | IMP-012, IMP-040 |
| **対象外** | **フロントエンド（JavaScript）** | 開発ホストに Node.js を要求しないため（BR-001）。**検証は描画スモークテスト（BR-054）と手動確認による** |

`search.js` は最初から単体テストの範囲外である。**これはこの不具合による欠陥ではなく、
BR-001（Node.js を持ち込まない）から導かれた設計判断であり、UT-002 が明記している。**
その代償として「検証は描画スモークテストと手動確認による」と書かれているが、
**次の 4.2 のとおり、描画スモークテストはこの種の不具合を検出できない。**

### 4.2 E2E の自動テスト — 操作を行わない

自動 E2E は E2E-101〜109 の 9 件であり、いずれも**配布物そのものの検査**である。

| ID | 内容 | 検索に触れるか |
| --- | --- | --- |
| E2E-101 | 配布アーカイブの構成 | 触れない |
| E2E-102 / 103 / 105 | `--version` / `--help` / 不正な引数 | 触れない（ウィンドウを開かない） |
| E2E-104 | 起動と終了 | 触れない |
| E2E-106 | Linux の依存ライブラリ | 触れない |
| E2E-107 / 108 | バイナリサイズ / チェックサム | 触れない |
| E2E-109 | **描画スモークテスト**（BR-054） | **触れない** |

E2E-109 は唯一ブラウザを起動するが、**行うのは「Mermaid・PlantUML・KaTeX が描画できたか」の確認だけ**である。
`scripts/smoke/harness.js` は `lazy.js` の描画関数を呼んで SVG の有無と寸法を数えるのみで、
**クリックもキー入力もスクロールも行わない。** 検索バーはそもそも生成されない
（`initSearch()` は `main.js` から呼ばれ、ハーネスは `main.js` を読み込まない）。

### 4.3 手動テスト — **手順にボタンを押す操作が無い**

90 章の対応表は `FR-080 → E2E-271, E2E-272` を割り当てており、**どちらも 41 章（手動）である。**
自動化されていないこと自体は E2E-031 の分類どおりで不足ではない。**問題は手順の中身である。**

E2E-271「文書内検索」の手順は次のとおり。

```
1. Ctrl+F を押す
2. 複数箇所にある語を入力する
3. Enter と Shift+Enter で移動する      ← キーボードだけ
4. ヒットしない語を入力する
5. Esc で閉じる
```

**FR-080 は移動手段を 2 つ（キーボード / バーのボタン）定めているのに、手順は片方しか踏んでいない。**
そして本件は、**踏まれた側（キーボード）だけが正常に動く**不具合である。

さらに確認内容にも欠けがある。

```
- 検索バーが本文の右上に出て、本文が押し下げられない
- 入力に応じて即座にハイライトされる
- 現在位置のヒットが他と異なる色で示される
- 3 / 12 のようなヒット数が表示される
- ヒットしないとき No results が表示される
- Esc でハイライトが消え、本文が元に戻る
```

**FR-080 の MUST である「移動時は該当箇所までスクロールする」が、確認内容に入っていない。**
「検索バーが本文の右上に出て」は開いた直後の状態しか見ておらず、**スクロール後も右上に留まるか**は見ていない。

したがって、**仮に手順 3 でボタンを押していたとしても、確認内容にスクロールの項目が無いため
見落とされた可能性が高い。**

### 4.4 そもそも手動テストが実施されていない

`v1.0.0-rc.1` は**手動テストを実施せずリジェクト**されており（外部エディタと PlantUML を
`v1.0.0` に含めると決めたため）、`v1.0.0-rc.2` はまだ打たれていない。
`v0.1.0-rc.1` / `rc.2` は CI の試験用タグであり検証対象ではない。

**この機能は、実装（P4）以降ただの一度も体系的な手動テストを通っていない。**

### 4.5 まとめ

| 層 | この不具合を検出できたか | 理由 |
| --- | --- | --- |
| 単体テスト | **できない** | UT-002 でフロントエンドは対象外（BR-001 に基づく設計判断） |
| E2E 自動 | **できない** | E2E-101〜109 は配布物の検査。E2E-109 も描画のみで操作しない |
| E2E 手動（ケース定義） | **できなかった** | **E2E-271 の手順にボタン操作が無く、確認内容にスクロールが無い** |
| E2E 手動（実施） | **未実施** | rc.1 はリジェクト、rc.2 は未着手 |

**唯一の検出機会だった手動テストのケース定義に穴があった**、というのが答えである。

## 5. 修正方法

### 5.1 案 1（最小）— `preventScroll` を付ける

```js
// frontend/js/search.js  createButton
button.addEventListener("click", () => {
  handler();
  // **preventScroll を付ける。** focus() は既定で対象を可視域へスクロールし、
  // jump() が行った移動を打ち消す（FR-080 の「該当箇所までスクロールする」）。
  if (state.search.open) $("search-input").focus({ preventScroll: true });
});
```

| | |
| --- | --- |
| 効果 | 実測 4 のとおり、巻き戻しは起きなくなる |
| 変更量 | 1 行 |
| **残る問題** | **検索バーは流れたままなので、ジャンプ後にボタンが画面外へ出て、続けて押せない**（2.2） |

**これ単独では実用にならない。**

### 5.2 案 2（根治）— 検索バーをスクロールしない位置へ移す

`#searchbar` を `#viewer`（スクロールする器）の外へ出し、スクロールしない包含ブロックの
子にする。`position: absolute` は DSP-160 の指定どおり保てる。

```html
<!-- frontend/index.html -->
<div class="viewer-wrap">                              <!-- position: relative（スクロールしない） -->
  <section id="viewer" class="viewer" tabindex="-1">   <!-- overflow-y: auto -->
    <article id="markdown" class="markdown-body"></article>
    <div id="state-screen" class="state-screen" hidden></div>
  </section>
  <div id="searchbar" class="searchbar" hidden></div>  <!-- ← 器の外へ -->
</div>
```

```css
.viewer-wrap { position: relative; flex: 1; min-width: 0; display: flex; }
.viewer { flex: 1; min-width: 0; /* position: relative は state-screen のために残す */ }
```

| | |
| --- | --- |
| 効果 | 検索バーが常に本文ペインの右上に留まる。**`focus()` はスクロールを起こさなくなり、症状も消える** |
| 変更量 | `index.html` 1 か所、`base.css` に規則 1 つ |
| 注意 | **`.state-screen` は `#viewer` の中に残す。** `inset: 0` で本文領域を覆う必要があり、本文を空にするためスクロールしない（2.2 の注記） |

### 5.3 推奨

**案 2 を本筋とし、案 1 も併せて入れる。**

案 2 で検索バーが常に可視域に入れば `focus()` はスクロールを起こさないため、案 1 は動作上は
不要になる。それでも入れる理由は、**「フォーカスの副作用でスクロールしない」という意図をコードに
残すため**である。将来レイアウトを変えたときに、同じ罠へ戻らない。

### 5.4 あわせて直すべき仕様とテスト仕様

**この 3 つを直さないと、同じ不具合が再び作り込まれても再び見つからない。**

| 文書 | 直すこと |
| --- | --- |
| `21-display-components.md` DSP-160 | 位置の欄に「**本文のスクロールに追従せず、常に本文ペインの右上に留まる**」を加える。`position: absolute` を使う場合、**包含ブロックがスクロールする器であってはならない**ことを明記する |
| `41-e2e-manual.md` E2E-271 | 手順に「**バーの ∧ / ∨ ボタンで移動する**」を加える（FR-080 が定める 2 つ目の経路）。確認内容に「**移動のたびに該当箇所までスクロールする**」「**スクロールしても検索バーが本文ペインの右上に留まる**」を加える |
| `31-test-cases.md` / `30-test-policy.md` | **変更しない。** UT-002 の除外は BR-001 に基づく設計判断であり、この不具合を理由に覆すべきものではない。**代償は手動テストが受け持つ**と UT-002 自身が書いており、直すべきは手動テストのケース定義（上記）である |

> [!NOTE]
> **自動テストで拾えるようにする案も考えられるが、勧めない。**
> `scripts/smoke` を拡張してクリック操作まで行わせると、BR-054 の目的（同梱資産を更新しても
> 描画できるか）と、UI 操作の回帰テストという別の目的が 1 つの仕組みに同居する。
> Node.js を持ち込まないという BR-001 の判断とも整合しにくい。
> **まずは手動テストのケース定義の穴を塞ぐのが筋である。**

## 6. 影響範囲

| 対象 | 影響 |
| --- | --- |
| 検索バーの ∧ / ∨ ボタン | **移動しない**（本件） |
| 検索バーの ✕（閉じる）ボタン | `closeSearch()` の中で `$("viewer").focus()` を呼ぶ経路であり、閉じるので実害なし |
| `Enter` / `Shift+Enter` | 正常 |
| アウトラインからの移動 | 正常 |
| 検索バーの可視性 | **本文をスクロールすると画面外へ出る**（2.2。本件と同根の未報告の欠陥） |
| 状態画面 | 影響なし（本文を空にするためスクロールが起きない） |
| Go 側 | 影響なし。フロントエンドのみ |

**データの破損や情報漏洩を伴わない。** 表示と操作の不具合に限られる。

## 7. 修正後の検証方法

### 7.1 手動（E2E-271 を直したうえで）

1. 長い文書を開き、`Ctrl+F` で複数箇所にある語を検索する
2. **∨ ボタンを繰り返し押す。** 押すたびに該当箇所へ移動すること
3. **移動後も検索バーが本文ペインの右上に見えていること**
4. 本文をホイールでスクロールしても、検索バーが右上に留まること
5. `Enter` / `Shift+Enter` でも同様に移動すること（回帰していないこと）
6. `Esc` で閉じ、ハイライトが消えること

### 7.2 機械的な確認

本報告書の実測（2.3）に用いた手順を再実行し、次の 2 点を確かめる。

- 検査 1（スクロール追従）で、`scrollTop` を変えても検索バーの上端が**変わらない**こと
- 検査 2（`scrollIntoView` → `focus()`）で、`scrollTop` が**巻き戻らない**こと
