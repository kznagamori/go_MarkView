## 1. 症状

読み込みに失敗した画像が、**Linux では代替テキスト（`alt`）の文字列を表示しない。**

| 環境 | 見え方 |
| --- | --- |
| W1（WebView2 / Chromium） | 破線 1px の枠の中に、`alt` の文字列が淡い色で出る（**DSP-123 のとおり**） |
| **L1（WebKitGTK）** | **破線 1px の枠は出る。その中に矩形の枠があり、中心の正方形の中に `?` がある。`alt` の文字列はどこにも出ない** |

実施者の記録（E2E-236）:

> W1: OK
> L1: NG
> 画像は表示される
> 代替テキストの文字列が出ないかつ、その画像が□＋?

追加で確認したところ、**「破線の中に矩形の線があり、その中心の正方形の中に `?` の文字がある」**であった。

`FR-022`（**MUST**）は次を定めている。

> 画像が存在しない・読み込めない場合、**代替テキスト（alt）と破損を示すプレースホルダを表示する**。文書全体の描画は継続する。

**プレースホルダは出ている。代替テキストだけが出ていない。** MUST の 2 つの要素のうち片方が欠けている。

### 1.1 観測された 2 つのケース

| ケース | 文書 | 失敗する画像 |
| --- | --- | --- |
| E2E-236 | 相対パス画像・存在しない画像・リモート画像を含む文書 | 存在しない画像、およびネットワーク切断時のリモート画像 |
| E2E-231 | `testdata/showcase.md` | 226 行目付近の `![リモート画像の代替テキスト](https://example.com/nosuch.png)` |

**E2E-231 の確認内容に画像の項目は無い。** 見比べの最中に目に入ったものであり、ケースとしては E2E-236 が本体である（4.5 で述べる）。

## 2. 原因

### 2.1 `is-broken` の付与も CSS も、L1 で正しく効いている

**破線の枠が出ている**ことが決め手である。枠は次の 1 か所からしか出ない。

```css
/* frontend/css/markdown.css */
.markdown-body img.is-broken {
  display: inline-block;
  padding: 8px 12px;
  border: 1px dashed var(--color-border-default);
  color: var(--color-fg-muted);
  background-color: transparent;
}
```

`is-broken` を付けるのは JavaScript だけである（IMP-226）。

```js
// frontend/js/viewer.js
export function markBrokenImages(root) {
  for (const img of root.querySelectorAll("img")) {
    img.addEventListener("error", () => img.classList.add("is-broken"));
    img.addEventListener("load", () => img.classList.remove("is-broken"));
    if (img.complete && img.naturalWidth === 0) {
      img.classList.add("is-broken");
    }
  }
}
```

したがって **L1 でも `error` は発火し、クラスは付き、CSS も適用されている。** 検知の不具合ではない。

> [!NOTE]
> **ここを取り違えると、直す場所を間違える。** 「Linux で枠が出ない」なら `img.complete` / `naturalWidth` の
> エンジン差を疑うことになるが、**実際には枠は出ている。** 欠けているのは枠の中身だけである。

### 2.2 代替テキストの描画は「ブラウザ既定」に委ねられている

`DSP-123`（**MUST**）の NOTE:

> **CSS だけでは実装できない。** 読み込みに失敗した `img` を選ぶセレクタが **Chromium に存在しない**ため、クラスの付与に JavaScript が要る（IMP-226）。表示仕様がクラス名を名指ししているのはこのためで、`.is-broken` は 12 章と 21 章の接続点である。
>
> **代替テキストの描画そのものはブラウザ既定の `alt` 表示に任せる。フロントエンドで文字を組み立てない**（IMP-220）。

`IMP-226`（**MUST**）も同じことを言っている。

> **クラスを付けるだけで DOM を組み立てない。** 代替テキストの描画はブラウザ既定の `alt` 表示に任せ、枠と色は CSS が与える（DSP-123）。`alt` は文書由来の文字列であり、`innerHTML` に渡してはならない（IMP-220）。

**MarkView は代替テキストを一度も描いていない。** `alt` 属性を DOM に置いたあとは、描画エンジンの既定の振る舞いを当てにしている。

### 2.3 その「ブラウザ既定」がエンジンごとに違う

| エンジン | 読み込みに失敗した `img` の既定の描画 |
| --- | --- |
| Blink（WebView2 / Chrome） | **`alt` の文字列をインラインのテキストとして流し込む。** 要素の大きさは文字列に応じて決まる |
| **WebKit（WebKitGTK）** | **自前の「壊れた画像」アイコンを描く。**`alt` の文字列は描かれない |

L1 で観測された「矩形＋□＋`?`」は、**WebKitGTK 自身が描く欠落画像のアイコン**である。MarkView の CSS はその外側に破線の枠を描いており、二重の枠に見えていた。

`AR-003`（**MUST**）が定めるとおり、この製品は **2 つの異なる描画エンジンの上で動く**。

| OS | WebView |
| --- | --- |
| Windows 11 | WebView2（Chromium ベース） |
| Ubuntu 24.04 以降 | **WebKitGTK 4.1** |

**「ブラウザ既定」に委ねた時点で、この 2 つで違う結果になることが決まっていた。**

### 2.4 仕様の文面そのものに証拠が残っている

DSP-123 の NOTE は「セレクタが **Chromium に存在しない**」と書いている。**「WebView2 と WebKitGTK のどちらにも存在しない」ではない。** IMP-226 の IMPORTANT も同じ書き方である。

`markdown.css` のチェックボックスのコメントも「**Chromium の既定（13.33px）が基準になる**」と書いており（BUG-009）、**表示層の仕様と実装が、一貫して Chromium だけを見て書かれている。**

### 2.5 `NFR-061` の一覧から漏れている

`NFR-061: 表示の互換性`（**SHOULD**）は、両環境で同等であるべきものを列挙している。

> - 本文のレイアウト（見出し・表・コードブロック・リストの構造と余白）
> - テーマの配色
> - Mermaid 図・PlantUML 図・数式の描画結果
> - コピーボタンの位置と動作

**「読み込みに失敗した画像のプレースホルダ」は入っていない。** 入っていないから見比べる根拠が無く、レビューでも気づかれなかった。

> [!IMPORTANT]
> **この一覧の作り方に共通の弱点がある。** 列挙されているのは「**こちらが CSS で値を決めているもの**」ばかりで、
> **「エンジンの既定に委ねているもの」が 1 つも入っていない。** 差が出るのは後者である。

## 3. 原因の分類 — 仕様か、実装か

### 3.1 一次原因 — **仕様の誤り**（DSP-123 / IMP-226）

**MUST の要求（FR-022）を満たす手段として、エンジン既定の振る舞いを指定した。** これは実装の裁量ではなく、表示仕様と実装仕様がそろって明示的に決めたことである。

- DSP-123 の NOTE: 「代替テキストの描画そのものはブラウザ既定の `alt` 表示に任せる」
- IMP-226: 「クラスを付けるだけで DOM を組み立てない」

**実装はこの 2 つに正確に従っている。** `viewer.js` の `markBrokenImages` はクラスを付けるだけで、DOM を組み立てていない。**実装を責めるところが無い。**

### 3.2 二次原因 — 仕様の不足（NFR-061 の一覧）

2.5 のとおり、比較対象の一覧に「失敗した画像」が無い。**あれば E2E-236 の確認内容に「W1 と L1 で同じ」と書けた。**

### 3.3 三次原因 — 手動テストの実施範囲（rc.2 は W1 のみ）

rc.2 の 67 件は **64 件が W1、3 件が対象外**であり、**L1 は 1 件も実施していない**。rc.3 で初めて L1 を 34 件実施し、そこで出た。**これは手順の欠落ではなく、rc.2 の時点で L1 の成果物を確かめる機会がまだ無かったためである**（CLAUDE.md も「Linux 側の確認もここが最初の機会」と書いていた）。

### 3.4 分類の結論

| 問い | 答え |
| --- | --- |
| 仕様が不明瞭か | **いいえ。明瞭である。** DSP-123 も IMP-226 も「ブラウザ既定に任せる」とはっきり書いている |
| **仕様が間違いか** | **はい。** MUST の要求を、環境によって結果が変わる手段に委ねた |
| 実装が間違いか | **いいえ。** 仕様どおりに書かれている。実装だけを見ても誤りが見つからない |

## 4. なぜ単体テストと E2E の自動テストで見つからなかったのか

### 4.1 単体テスト — 対象外（UT-002）

`UT-002` は対象を `internal/` と `scripts/domids` に限っている。**フロントエンドは対象外**である。JS のテスト基盤を持たないのは `BR-001`（Node.js を導入しない）と `AR-050` の帰結であり、この不具合が通り抜けたのは方針どおりの結果である。

**仮に JS のテストがあっても見つからない。** 誤っているのは JavaScript の論理ではなく、**その先のエンジンの描画**である。`markBrokenImages` の単体テストは「`is-broken` が付くか」しか見られず、**L1 でもそれは正しく付いている。**

> [!IMPORTANT]
> **BUG-005 とまったく同じ形である。** あちらは `buildinfo.Environment` の単体テストが両方の枝とも緑のまま、
> 呼び出し側が常に空文字を渡していた。こちらは `markBrokenImages` が正しくクラスを付けたまま、
> **その先の描画が環境によって違う。** どちらも「**関数の正しさ**」と「**利用者に見えるもの**」の間に
> テストが 1 枚も無い。

### 4.2 自動 E2E — ウィンドウ内を操作しない（E2E-002）

`E2E-002` は自動テストを「**WebView の UI を操作しない**範囲」に限っている。画像が描かれた結果を見るには WebView の中を覗く必要があり、**構造的に対象外**である。

加えて `IMP-042` は「**リモート画像の確認は手動で行う**」と明記している。**この不具合の半分（リモート画像側）は、最初から自動化しないと決めてある。**

### 4.3 描画スモークテスト — **Chromium 系ブラウザでしか走らない**

`scripts/smoke` は同梱資産（Mermaid / KaTeX / PlantUML）が描けるかを見るものだが、**エンジン差の検出には原理的に使えない。**

```go
// scripts/smoke/browser.go
func candidates() []string {
	// linux:  google-chrome / google-chrome-stable / chromium / chromium-browser
	// windows: msedge.exe / chrome.exe
}
```

**候補はすべて Chromium 系である。Linux で実行しても Chromium が走る。WebKitGTK は一度も使われない。**

さらに、スモークテストは `testdata/smoke.md` を描くだけで、**失敗する画像を含んでいない。** 仮に WebKitGTK で走らせられたとしても、この症状は出ない。

### 4.4 リリース CI の Linux ジョブ — 起動までしか見ない

`release.yml` は `ubuntu-24.04` で `scripts/e2e binary` を実行しており、**Linux の配布物が起動して正常終了することは確かめている。** しかし E2E-002 のとおり**ウィンドウの中は見ない。** 描画結果はここに含まれない。

### 4.5 手動テスト（rc.2）— **L1 を 1 件も実施していない**

| 版 | W1 | L1 | 対象外 |
| --- | --- | --- | --- |
| rc.2 | **64** | **0** | 3 |
| rc.3 | 64（うち 32 は W1 のみ） | **34** | 1 |

**rc.2 の「OK 57」は、この不具合について何も述べていない。** 3.3 のとおり、L1 の成果物を確かめる最初の機会が rc.3 であった。

### 4.6 手動テスト（rc.3）でも、当たったケースは 1 つだけ

E2E-231 は `showcase.md` を GitHub と並べて見るケースだが、**確認内容 15 項目に画像の項目が 1 つも無い。** 実施者が気づけたのは、**GitHub と並べて見ていたから**である。ケースとしては E2E-236（確認内容 3・4・6）が本体である。

### 4.7 仕様レビューでも見つからなかった

4.31.0 までの横断レビューは「定義と参照が一致するか」「上位と下位が矛盾しないか」を機械と目で見ている。**DSP-123 と IMP-226 は矛盾していない。両方そろって同じ前提（Chromium）に立っている。** 一貫している誤りは、突き合わせでは出てこない。

### 4.8 まとめ

| 層 | この不具合を見つけられたか | 理由 |
| --- | --- | --- |
| 単体テスト | **原理的に不可** | フロントエンドは対象外（UT-002）。JS が正しくても症状が出る |
| 自動 E2E | **原理的に不可** | ウィンドウ内を操作しない（E2E-002）。リモート画像は手動と決めてある（IMP-042） |
| 描画スモーク | **原理的に不可** | **Chromium 系しか起動しない。** 失敗する画像も含まない |
| リリース CI（Linux） | 不可 | 起動と終了までしか見ない |
| 仕様レビュー | 不可 | 仕様どうしは一貫している |
| **手動テスト（L1）** | **可。実際にここで見つかった** | **E2E-236 が唯一の検証手段** |

## 5. 修正方法

### 5.1 案 1（推奨）— 失敗した画像を、代替テキストを持つ要素へ置き換える

`markBrokenImages` が `error` を受けたとき、`<img>` を**こちらが組み立てた要素**に置き換える。

```js
// frontend/js/viewer.js（案）
function replaceBroken(img) {
  const span = document.createElement("span");
  span.className = "img-broken";
  // **textContent で入れる。** alt は文書由来であり innerHTML に渡さない（IMP-220）
  span.textContent = img.alt;
  span.title = img.alt;
  img.replaceWith(span);
}
```

```css
/* frontend/css/markdown.css（案）*/
.markdown-body .img-broken {
  display: inline-block;
  padding: 8px 12px;
  border: 1px dashed var(--color-border-default);
  color: var(--color-fg-muted);
}
```

**これでエンジン依存が完全に無くなる。** 描くのはこちらであり、WebKitGTK の壊れ画像アイコンは（`<img>` ごと消えるため）そもそも現れない。

| 論点 | 判断 |
| --- | --- |
| IMP-220（`innerHTML` に渡さない） | **守れる。** `textContent` で入れる |
| IMP-226 の「DOM を組み立てない」 | **この規定を変える。** 5.5 で仕様を直す |
| `load` で復帰する経路 | **失われる。** 同じ `src` で `error` の後に `load` が来ることは無く、実害は無い。再読み込み（`F5`）では文書ごと作り直されるため E2E-236 の手順 5 も従来どおり |
| リンクで包まれた画像（`[![alt](img)](url)`） | `<a>` の中の `<img>` が `<span>` になるだけで、リンクは生きる |
| 検索（FR-080） | **`alt` の文字列が検索に当たるようになる。** 従来（Chromium）も画面には出ていた文字なので、むしろ整合する。41 章に注記を足すのが望ましい |
| `alt` が空の場合 | 空の枠が出る。**Chromium の現状と同じ**であり、変化しない |

### 5.2 案 2 — `<img>` を残し、隣に代替テキストの要素を足す

`is-broken` が付いたときに `<img>` を `display: none` にし、直後に `<span>` を挿す。

- **利点**: `<img>` が DOM に残るため、将来「再試行」を入れる余地がある
- **欠点**: 要素が 2 つになり、枠をどちらに描くかで CSS が増える。**復帰の余地は現状どこからも使われていない**

**案 1 のほうが単純である。**

### 5.3 採らない案 — `::after { content: attr(alt) }` で描く

```css
/* 採らない */
.markdown-body img.is-broken::after { content: attr(alt); }
```

`<img>` は置換要素であり、**擬似要素が描かれるかどうかがエンジンと状態に依存する。** 失敗した `img` に限って描かれる、という振る舞いを当てにするのは **2.2 と同じ誤りを別の場所で繰り返すこと**になる。

### 5.4 採らない案 — WebKitGTK の壊れ画像アイコンを CSS で消す

**消す手段が無い。** エンジンが描く既定の描画であり、CSS の届く範囲にない。仮に `content` などで潰せたとしても、5.3 と同じ理由で採らない。

### 5.5 あわせて直すべき仕様

| 文書 | 直すところ |
| --- | --- |
| `21-display-components.md` **DSP-123** | NOTE の「代替テキストの描画そのものはブラウザ既定の `alt` 表示に任せる」を**削り**、「**代替テキストは自前で描く**（`textContent`。IMP-220）」に改める。「Chromium に存在しない」も「**どちらのエンジンにも存在しない**」に改める |
| `12-impl-frontend.md` **IMP-226** | 「クラスを付けるだけで DOM を組み立てない」を、**置き換える形**に改める。IMP-220 との関係（`textContent` を使う）を明記する |
| `07-nonfunctional.md` **NFR-061** | 比較対象の一覧に「**読み込みに失敗した画像のプレースホルダと代替テキスト**」を足す。あわせて「**エンジンの既定の描画に依存する表示を作らない**」を規約として書く（2.5 の IMPORTANT） |
| `41-e2e-manual.md` **E2E-236** | 確認内容 3・4・6 に「**W1 と L1 で同じであること**」を明記する |

| `CLAUDE.md` | 「破ってはいけない規約」のフロントエンドの節に「**描画エンジンの既定の振る舞いに要求の充足を委ねない**」を足す |

### 5.6 再発防止 — 「委ねているもの」を数える

BUG-006 の `scripts/domids` のような機械的な検査は、**この種類の不具合には作れない**（エンジンを 2 つ動かす必要があり、E2E-002 / IMP-042 の線を越える）。代わりに、**仕様の側で「エンジン既定に委ねている箇所」を列挙して、手動テストで両環境を見る対象にする**のが現実的である。

現時点で判明している委ね先は 2 つある。

| 委ねているもの | どこ | 現れた不具合 |
| --- | --- | --- |
| 失敗した画像の `alt` 描画 | DSP-123 / IMP-226 | **BUG-008（本件）** |
| チェックボックスの既定の大きさ | DSP-121 / `markdown.css` | **BUG-009** |

## 6. 影響範囲

| 項目 | 内容 |
| --- | --- |
| 影響する環境 | **L1（Linux / WebKitGTK）のみ。** W1 は正しく動いている |
| 影響する機能 | 読み込みに失敗した画像（ローカル・リモートとも。MD-071） |
| 利用者への影響 | **どの画像が欠けているのか分からない。** 枠は出るので「何かがある」ことは伝わるが、`alt` が読めないため文脈が失われる |
