# BUG-023: 履歴の移動で文書を開けなかったとき、履歴の位置だけが進む

| 項目 | 内容 |

| 検出 | **v1.2.0 の実現性検討（戻る・進むボタン）で、コードを読んで見つけた**（2026-11-07）。ボタンを付けると、淡色で「戻れるか・進めるか」を見せることになり、食い違いが目に見えるようになる。**手動テストでは一度も出ていない** |

## 1. 症状（コードから導いたもの）

文書 A → B → C の順に開いた（ツリー・リンク・ファイル選択のどれでもよい）後、**B を削除する**（名前を変える・読めなくするのでも同じ）。

| # | 操作 | 履歴（`[ ]` が位置） | 画面 | 起きること |
| --- | --- | --- | --- | --- |
| 0 | A → B → C を開く | A B **[C]** | C | |
| 1 | `Alt+←` | A **[B]** C | C | ステータス領域に `File not found: …`。**画面は C のまま、履歴の位置だけが B へ進む** |
| 2 | `Alt+→` | A B **[C]** | C | **いま見ている C を開き直す。** 利用者からは、進む先が無いはずなのに `Alt+→` が効いたように見える |
| 3 | `Alt+←` | A **[B]** C | C | 1 と同じ |
| 4 | ツリーで D を開く | A B **[D]** | D | **履歴から C が消える。** 位置（B）より後ろを捨ててから積むため（ブラウザと同じ規則。FR-051） |
| 5 | `Alt+←` | A **[B]** D | D | また `File not found: …` |
| 6 | `Alt+←` | **[A]** B D | A | **C へは二度と戻れない** |

- **4〜6 が FR-051 に反する。** D の直前に表示していたのは C であり、`Alt+←` で C へ戻れなければならない。
- 1 の時点で利用者が気づいて次に `Alt+←` を押すと A へ行くため、**キーボードだけの今は気づきにくい。** v1.2.0 で戻る・進むボタンを付けると、ボタンの淡色が「履歴の位置」を見せるようになり、画面と食い違う。
- 消えた B を通るたびに `File not found` が出て、1 回余計に押すことになる（5）。

上の表は、`internal/session` の本物の `History` に、`historyStep` と `commitOpen` が行う呼び出しを同じ順で当てて確かめた（`workspace/tmp/_histstep`。2026-11-08）。

---

## 2. 原因

### 2.1 履歴の位置を、開く前に動かし、開けなくても戻さない

```go
// desktop/bind.go
func (a *App) HistoryBack() (res OpenResultDTO) {
	...
	entry, ok := a.historyStep((*session.History).Back) // ここで位置が 1 つ戻る
	if !ok {
		return OpenResultDTO{}
	}
	path = entry.Path

	return a.openHistory(entry) // 開けなくても、位置はそのまま
}
```

`openHistory` は共通の開く処理（`openLocked`。IMP-192）を通る。B が無いときの結果は **`outcomeKept`（表示を変えない失敗）** であり、画面の対象も監視も変えない（FR-110 の「直前の内容を維持」）。**履歴の位置だけが、すでに B へ動いている。** `HistoryForward` も同じ形である。

### 2.2 FR-051 が決めていない

FR-051 は、積む契機・スタック構造・記録する情報・上限を定めるが、**履歴の先の文書を開けなかったときにどうするかを定めていない。** IMP-308 は「端で呼んだら空の結果を返す」を定めるだけである。

---

## 3. 原因の分類 — 仕様か、実装か

**仕様の不足である。** FR-051・IMP-191・IMP-310 のどれも、履歴の移動が失敗する場合を扱っていない。実装は「位置を動かしてから開く」という素直な順で書かれており、仕様に反する箇所は無い。**ただし結果として、FR-051 の本文「`Alt+←` で直前に表示していたファイルへ戻る」を満たさない**（1 章の 4〜6）。

---

## 4. なぜ見つからなかったのか

| 層 | 見つからなかった理由 |
| --- | --- |
| 単体テスト | `session.History` の単体テストは、積む・戻る・進む・上限が正しいことを見る。**位置を動かす処理と開く処理の組み合わせは `desktop` にあり、単体テストの対象外**（UT-002）。BUG-005 と同じ形である |
| 手動テスト | **E2E-262 は、開ける文書だけで戻る・進むを確かめる。** 履歴の途中の文書を消してから戻る手順は、どのケースにも無い |
| 利用 | キーボードだけの今は、1 回目の `Alt+←` で `File not found` が出て、もう一度押せば A へ行く。**C が履歴から消える（1 章の 4）のは、その間に別の文書を開いたときだけ**であり、気づく機会が少ない |

---

## 5. 修正方法

### 5.1 採る案 — 開けなかった項目を履歴から取り除き、位置を元へ戻す

**利用者の判断（2026-11-08。v1.2.0 の実現性検討の 13 章の 3）。** 開けなかった理由は、今と同じくステータス領域に出す（FR-110）。

| 対象 | 変えること | 規定 |
| --- | --- | --- |
| 要求 | FR-051 に「**履歴の先の文書を開けなかった（表示を変えない失敗）ときは、その項目を履歴から取り除き、位置を移動の前へ戻す。理由はステータス領域に出す**」を足す | FR-051 |
| `internal/session` | 指定した位置の項目を取り除く処理（`Remove`）。**位置より前の項目を取り除いたら、位置も 1 つ前へずらす**（位置が指す文書を変えない） | IMP-191 |
| `desktop` | `HistoryBack` / `HistoryForward` は、開いた結果が `outcomeKept` なら、移った先の項目を取り除いて位置を戻す。**判断（何を取り除き、どこへ戻すか）は `internal/session` に置く**（IMP-012。`app.go` に判断を持たない） | IMP-310 |
| 手動テスト | E2E-262 に「途中の文書を消してから戻る」手順を足す（**4.79.0 で手順 4〜8 と確認内容 4〜6 にした**。文書は `go run ./scripts/gentestdata -edit` が作る `testdata/e2e/generated/edit/history/a.md`〜`d.md`） | E2E-262 |
| 単体テスト | `Remove` の境界（先頭・末尾・位置そのもの・位置より前・空の履歴） | UT-804 |

- **状態画面（`confirm-large` / `too-large` / `render-error`）になった場合は「開けなかった」に入れない。** 画面がその文書を対象にしており（UI-013）、位置はその項目を指すのが正しい（[BUG-024](2026-11-08-bug-024-state-screen-not-in-history.md) で状態画面も履歴に積むことにした）。
- v1.2.0 で足す `history:changed`（戻れるか・進めるかをフロントエンドへ送るイベント）は、取り除いた後の状態を送る。

### 5.2 採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| 位置を戻すだけで、項目は残す | 消えた文書が残り続け、**戻るたびにそこで止まって先へ戻れない**（1 回目は戻され、2 回目も同じ項目で止まる） |
| 開く前に、ファイルがあるかを確かめてから位置を動かす | 確かめた直後に消える場合が残る。また、権限が無い・Markdown でなくなった等の失敗は、開いてみないと分からない。**開いた結果で決めるほうが、失敗の種類を 1 か所（`classifyOpen`）で扱える** |
| 開けない項目を飛ばして、その先の文書を開く | 何回分戻ったかが利用者に分からなくなる。**1 回の操作で 1 つ戻る**ことを崩さない |

---

## 6. 影響範囲

- **文書の内容は変わらない。** 履歴の位置と、戻れる先だけの不具合である。
- **見ていた文書が履歴から消える**（1 章の 4）。消えた文書へは、ツリーやリンクから開き直せば戻れる。
- 編集モード（FR-140）・状態画面・監視には影響しない（`outcomeKept` は画面の対象を変えない）。

---

## 7. 修正の前後に確かめること

### 7.1 直す前に、v1.1.0 で症状を確かめる（W1）

`a.md` / `b.md` / `c.md` / `d.md` の 4 つを置いたフォルダーを MarkView で開く（中身は 1 行でよい）。

1. ツリーで `a.md` → `b.md` → `c.md` の順に開く
2. エクスプローラーで `b.md` を削除する
3. `Alt+←` を押す → **`File not found: …` が出て、画面は `c.md` のまま**
4. ツリーで `d.md` を開く
5. `Alt+←` を 2 回押す → **1 回目は `File not found`、2 回目は `a.md`**
6. `Alt+→` を何回押しても `c.md` へ戻れなければ、症状が出ている（直した後は、5 の 1 回目で `c.md` へ戻る）

**この手順は E2E-262 の手順 4〜8 と同じ形である**（4.79.0）。文書は `go run ./scripts/gentestdata -edit` が `testdata/e2e/generated/edit/history/a.md`〜`d.md` に作る（見出しの無い 1 行の文書）。1〜5 がケースの手順 4〜8、6 が手順 8 の後半（`Alt+→`）に当たる。**v1.1.0 で NG になるのは確認内容 5・6 である**——確認内容 4（`File not found` が出て、表示は `c.md` のまま）は v1.1.0 でも見かけは OK になる（E2E-262 の IMPORTANT）。

**結果: 症状が出た**（2026-11-08。利用者が v1.1.0 の配布物の W1 で、`generated/edit/history/` を使って行った。v1.2.0 の実装の T21-3）。

### 7.2 直した後

- 単体テスト（UT-804 に足すケース）を、**取り除く処理を空にして一度失敗させてから**通す（UT-033）。
- 7.1 の手順で、5 の 1 回目に `c.md` へ戻り、`File not found` が出ないこと。3 で `File not found` が出た後に `Alt+→` を押しても、何も起きない（進む先が無い）こと。
- v1.2.0 の戻る・進むボタンが、3 の後に「進む」を淡色にしていること。
- **rc の手動テストでは E2E-262 の確認内容 4〜6 で見る**（4 が手順 6 のボタンの淡色、5・6 が戻る先と進む先）。ボタンとマウスのサイドボタンでの移動は、同じ入口を通ることを E2E-266 が見る。
