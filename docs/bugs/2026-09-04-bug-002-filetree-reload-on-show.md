| 項目 | 内容 |
| --- | --- |
| 不具合番号 | **BUG-002** |
| 報告日 | 2026-09-04 |
| 対象 | `v1.0.0-rc.2`（`aeae862` + リリース CI の資産更新コミット） |
| 検出 | 手動テスト **E2E-244**（NG） |
| 環境 | Windows / WebView2（**Linux でも同じ**。フロントエンドの問題であり OS に依存しない） |
| 関連要求 | FR-035, FR-015, IMP-131, IMP-240, IMP-310, DSP-330 |
| 分類 | **仕様の不備（担当モジュールが未割り当て）＋ 実装の欠落** |
| 混入時期 | `5c1f34c feat: P4 フロントエンド — 表示と操作の一式`（FR-035 の 3 契機のうち 1 つしか実装されていない） |

---

## 1. 症状

1. MarkView の外で、ツリールート直下に `.md` ファイルを追加する
2. ツールバーのファイルツリーボタンでペインを閉じ、もう一度開く

**追加したファイルがツリーに現れない。** ペインは閉じる前とまったく同じ内容で戻る。

アプリを再起動するか、ディレクトリノードを折りたたんで開き直すと現れる。

---

## 2. 原因

### 2.1 直接の原因 — ペインの開閉が `loadTreeRoot` を呼んでいない

ツリーを読み直す関数は 1 つだけある。

```js
// frontend/js/filetree.js 31
export async function loadTreeRoot(root) {
  ...
  const { nodes, error } = await api.readDir("");   // Go 側の ReadDir（IMP-310）
  ...
  fill(list, nodes, 0);
  await revealCurrent();
}
```

**呼び出しは 2 か所しかない。**

```
$ grep -rn "loadTreeRoot" frontend/js/
frontend/js/filetree.js:31:export async function loadTreeRoot(root) {
frontend/js/main.js:14:import { initFileTree, loadTreeRoot, revealCurrent } from "./filetree.js";
frontend/js/main.js:160:  if (init.treeRoot) await loadTreeRoot(init.treeRoot);      <- 起動時
frontend/js/main.js:173:    await loadTreeRoot(root);                                <- tree:rootChanged
```

一方、ペインの開閉は `panes.js` の `togglePane` が処理する。

```js
// frontend/js/panes.js 53
export function togglePane(name) {
  keepScroll(() => {
    if (name === "outline") {
      state.outlineVisible = !state.outlineVisible;
    } else {
      state.fileTreeVisible = !state.fileTreeVisible;    // <- 真偽値を反転するだけ
    }
    applyResponsive();
    refresh();                                           // <- hidden 属性を書き換えるだけ
  });

  saveConfig();
}
```

**`refresh()` は `$("pane-filetree").hidden` を切り替えるだけである。** DOM は閉じる前のまま残っており、読み直しは起こらない。

### 2.2 FR-035 の 3 つの契機のうち、実装されているのは 1 つだけ

FR-035 は再読み込みの契機を 3 つ定めている。

| # | 契機 | 実装 | 場所 |
| --- | --- | --- | --- |
| 1 | **ツリーペインを非表示から表示に切り替えたとき** | **無い** | — |
| 2 | 再読み込み操作（FR-015）を行ったとき | **無い** | `main.js` の `reloadCurrent()` は `api.reload()` を呼ぶだけ。`Reload()`（`bind.go` 253）は表示中の文書を開き直すのみで、ツリーには触れない |
| 3 | ディレクトリノードを折りたたんでから再度展開したとき | **ある** | `filetree.js` の `expand()`（「子を**毎回読み直して**展開する」） |

**E2E-244 が突いたのは 1 だが、2 も同じく実装されていない。**
2 については手動ケースが無いため、今回の 67 件では検出されていない。

### 2.3 なぜ 3 だけが実装されたのか — 仕様の割り当てが 3 にしか無い

`90-traceability.md` で FR-035 を引くと、こうなっている。

```
| FR-035 | ツリーの手動更新 | IMP-131, IMP-310 | DSP-330 |
```

| ID | 内容 | 契機 1 を含むか |
| --- | --- | --- |
| IMP-131 | `filetree.ReadDir`（Go 側の読み込み） | **含まない**（読む処理そのもの） |
| IMP-310 | バインドメソッド一覧の `ReadDir` | **含まない**（呼び口の定義） |
| DSP-330 | ツリーノードの状態 | **契機 3 だけを含む**（「折りたたみ（子読込済）: 矢印 `▸`。クリックで再読み込みして展開（FR-035）」） |

**「ペインを開いたときに読み直す」を担当するフロントエンドの実装 ID が、どこにも無い。**

`12-impl-frontend.md` の IMP-240（ペインの開閉とリサイズ）は `panes.js` の全 API を列挙しているが、ツリーの読み直しに触れていない。

```js
// IMP-240 が定める panes.js の API
export function initPanes()
export function applyPanes(config)
export function togglePane(name)
export function setPaneWidth(name, px)
export function applyResponsive()
```

- IMP-240 の箇条書き 6 項目は、`hidden` 属性・幅のクランプ・通知の間引き・`requestAnimationFrame`・スクロール位置の維持だけを扱う
- **`filetree.js` の振る舞いを定める IMP は存在しない**（IMP-200 のファイル一覧に名前があるだけ）

つまり FR-035 の 3 契機のうち、**下位層へ落ちているのは DSP-330 が拾った 3 だけ**である。1 と 2 は要求のまま止まっている。

## 3. 原因の分類 — 仕様か、実装か

### 3.1 一次原因 — **仕様の不備**（担当が決まっていない）

FR-035 は 3 つの契機を明示しているが、**そのうち 2 つに実装 ID が割り当てられていない。**
90 章の対応表は「要求 ID から IMP / DSP を引く」ための表であり、ここに載っていない振る舞いは、**実装時に読まれない。**

CLAUDE.md は「実装に着手するときは `90-traceability.md` で要求 ID から `IMP` / `DSP` を引く」と定めている。**その手順どおりに作業すると、契機 1 と 2 は視界に入らない。**

### 3.2 二次原因 — **実装の欠落**

仕様に書かれている FR-035 の本文（02 章）を読めば 3 契機は分かる。実装は要求を満たしていないので、実装の誤りでもある。

**ただし「仕様どおりに作れば起きなかった不具合」ではない。** 上位（FR-035）には書いてあり、下位（IMP / DSP）には落ちていない、という**層の間の落差**が原因である。90 章の対応表はこの落差を検出するための表だが、**「要求に対して IMP が存在するか」しか見ておらず、「要求の各項目が IMP で尽くされているか」は見ていない。**

### 3.3 誤りではないもの

- `filetree.ReadDir`（Go）は正しい。毎回ディスクを読み、キャッシュを持たない
- `ReadDir` バインドメソッド（`bind.go` 271）も正しい。空文字でツリールートを読む
- 契機 3（折りたたみ→展開）の実装も正しい

**「読み直す仕組み」は全部そろっている。呼ぶ場所が 2 つ足りないだけである。**

## 4. なぜ単体テストと E2E の自動テストで見つからなかったのか

### 4.1 単体テスト — 「読む処理」は検証済み。「呼ぶ契機」は対象外

31 章 31.10 の対応表はこうなっている。

```
| FR-035 | UT-301 | 再読み込みは `ReadDir` の再呼び出し |
```

UT-301 は `filetree.ReadDir` のフィルタ規則（`.md` のみ、ドット始まりを除く、`node_modules` などを除く…）を検証するもので、**7 ケースすべてが緑である。**

備考欄の「再読み込みは `ReadDir` の再呼び出し」という一文が、**この不具合を素通りさせた。**
確かに再読み込みは `ReadDir` の再呼び出しであり、`ReadDir` は正しく動く。しかし**「いつ再呼び出しするか」は `ReadDir` のテストでは決して分からない。**

これは UT-002（フロントエンドは単体テストの対象外）に従った結果であり、**テストの書き方の誤りではない。** ただし対応表の備考が「FR-035 は UT-301 で足りている」と読めてしまう点は、UT-061（要求 ID ごとにテストがあるかで網羅性を追跡する）の運用上の弱点である。

> [!IMPORTANT]
> **「要求 ID にテストが 1 件ひも付いていること」と「要求の全項目が検証されていること」は別である。**
> FR-035 は 3 つの契機を持つ 1 つの要求であり、UT-301 が触れているのは 0 個である（`ReadDir` 自体の検証であって、契機の検証ではない）。**箇条書きが複数ある要求では、対応表の 1 行が「全部見た」に見えてしまう。**

### 4.2 E2E の自動テスト — 操作を行わない

40 章の対応表も、FR-035 の検証は手動ケースだけだと記録している。

```
| FR-035 | E2E-244 |  |
```

自動 E2E（E2E-101〜109）は配布アーカイブの検査と CLI の確認、および描画スモークテストであり、**ウィンドウを開いてツールバーを押す経路が無い。**

### 4.3 手動テストで初めて出た

E2E-244 は優先度「低」で、**FR-035 に対応する唯一のケース**である。
`v1.0.0-rc.1` を手動テストせずにリジェクトしたため、今回が初回実施である。

### 4.4 まとめ

| 層 | 捕まえられたか | 理由 |
| --- | --- | --- |
| 単体テスト | **できない** | 対象が `internal/` のみ（UT-002）。契機の判断はフロントエンドにある |
| 自動 E2E | **できない** | 配布物の検査と CLI のみ |
| 手動テスト | **できた** | E2E-244（今回が初回実施） |
| 仕様レビュー | **できたはず** | 90 章で FR-035 に IMP が 2 件しかひも付いておらず、**どちらも「読む処理」で「契機」ではない**。ここを見れば実装前に気づけた |

## 5. 修正方法

### 5.1 案 1（推奨）— `main.js` が契機を握り、`togglePane` の結果を見て読み直す

`panes.js` から `filetree.js` を直接呼ばない。**モジュール間の依存を増やさない**（IMP-201）。

```js
// frontend/js/panes.js
// togglePane は「表示になったか」を返す。呼び出し側が後続を決める。
export function togglePane(name) {
  ...
  saveConfig();
  return name === "filetree" ? state.fileTreeVisible : state.outlineVisible;
}
```

```js
// frontend/js/main.js の SHORTCUT_HANDLERS / initToolbar
// **非表示から表示になったときだけ読み直す**（FR-035）。ディスクを読むため、
// 閉じるときや既に開いているときには呼ばない。
const toggleFileTree = async () => {
  if (togglePane("filetree") && state.treeRoot) await loadTreeRoot(state.treeRoot);
};
```

- ツールバーのボタン（`initToolbar` の `onFileTree`）と `Ctrl+B` 相当（`SHORTCUT_HANDLERS.filetree`）の**両方が同じ関数を通る**ようにする。片方だけ直すと経路で挙動が変わる
- `loadTreeRoot` は末尾で `revealCurrent()` を呼ぶため、**表示中の文書までの展開と選択も復元される**（DSP-331）

### 5.2 あわせて直す — FR-035 の契機 2（再読み込み操作）

```js
// frontend/js/main.js
async function reloadCurrent() {
  await leaveDocument();
  handleResult(await api.reload());

  // 再読み込みはツリーも最新にする（FR-035 の 2 番目の契機）。
  if (state.fileTreeVisible && state.treeRoot) await loadTreeRoot(state.treeRoot);
}
```

**E2E-244 は契機 1 しか見ていない**ため、これを直しても手動テストでは確認されない。7.1 に確認手順を書く。

### 5.3 展開状態について

`loadTreeRoot` はツリーを作り直すため、**利用者が開いていたディレクトリの展開状態は失われ、表示中の文書までの経路だけが `revealCurrent()` で開き直される。**

E2E-226 の確認内容には「ファイルツリーの展開状態が保たれている」があるが、あれは**外部エディタでの保存による自動再描画（FR-014）**の話であり、ツリーの再読み込みではない（そちらは `document:changed` で本文だけを差し替える）。**混同しないこと。**

FR-035 は展開状態の保持を求めていない。**求めるなら、それは仕様の追加である。** 現状のまま（作り直す）でよい。

### 5.4 あわせて直すべき仕様

**NFR-071 に従い、同じ変更で仕様書も直す。**

| 文書 | 直す内容 |
| --- | --- |
| `12-impl-frontend.md` IMP-240 | `togglePane` の説明に、**ファイルツリーが非表示から表示になったときはツリーを読み直す**（FR-035）ことを追加する。あわせて「`panes.js` から `filetree.js` を呼ばず、契機の判断は `main.js` に置く」理由を書く（IMP-201 の依存の明示） |
| 同上 | `reloadCurrent` の経路にも FR-035 の契機 2 があることを明記する |
| `90-traceability.md` | FR-035 の行に、契機を担当する IMP を追加する。**現在は IMP-131 / IMP-310 / DSP-330 だけで、契機 1 と 2 の担当が居ない** |
| `docs/specs/README.md` | 改訂履歴に 1 行追加し、版を上げる（NFR-071） |

### 5.5 検討すべき運用の改善（本報告の範囲外）

4.1 の IMPORTANT で述べたとおり、**箇条書きを複数持つ要求は、対応表の 1 行では網羅を保証できない。**
90 章 90.1.2 と 31 章 31.10 の対応表に「**要求の各項目に担当があるか**」を確認する運用を足すことが考えられるが、これは仕様の運用規約の変更であり、**本報告では提案にとどめる。**

## 7. 修正後の検証方法

### 7.1 手動

1. **E2E-244**（W1）— 外部でルート直下に `.md` を追加 → ペインを閉じて開き直す → 現れること
2. **契機 2 の確認（E2E-244 には無い手順）** — 外部でルート直下に `.md` を追加 → ツールバーの `Reload` を押す → 現れること
3. **契機 3 の回帰** — ディレクトリを折りたたんで開き直したときも、これまでどおり最新になること（E2E-243）
4. **ペインを閉じるときに読み直しが走らないこと** — 閉じる操作のたびにディスクを読むと、大きなディレクトリで引っかかる（NFR-020）
5. **表示中の文書の選択と展開が復元されること**（DSP-331）。読み直したあとも、開いている文書がツリー上で選択されたままであること

### 7.2 機械的な確認

```bash
# 読み直しの契機が 4 か所（起動・rootChanged・ペイン表示・Reload）になっていること
grep -rn "loadTreeRoot" frontend/js/
```

```bash
go test ./...          # Go 側に変更は無い。緑のままであること
go vet ./...
```

## 8. 調査の記録

| 確かめたこと | 結果 |
| --- | --- |
| `loadTreeRoot` の呼び出し箇所 | **2 か所だけ**（起動時と `tree:rootChanged`）。ペインの開閉からは呼ばれない |
| `togglePane` が何をするか | `state.*Visible` の反転 → `applyResponsive()` → `refresh()`（`hidden` 属性の書き換え）→ `saveConfig()`。**ツリーには触れない** |
| `Reload()`（Go）がツリーに触れるか | **触れない**（`bind.go` 253。`a.openResult(current.Path, ...)` のみ） |
| 折りたたみ → 再展開は読み直すか | **読み直す**（`filetree.js` の `expand`。「子を毎回読み直して展開する」） |
| `filetree.ReadDir`（Go）はキャッシュを持つか | **持たない**。毎回 `os.ReadDir` する |
| FR-035 に紐づく IMP / DSP | `IMP-131` / `IMP-310` / `DSP-330`。**契機 1・2 の担当が居ない** |
| `panes.js` の仕様（IMP-240）がツリーに触れるか | **触れない**。6 項目のいずれにも再読み込みの記述が無い |
| `filetree.js` の振る舞いを定める IMP | **存在しない**（IMP-200 のファイル一覧に名前があるのみ） |
