## 1. 症状

`testdata/e2e/plantuml-limits.md` の **6 節「4096 px を超える図」**に、**大きさの制限とは無関係な構文エラーの図**が出る。

実施者の記録（E2E-240）:

```
4096 px を超える図
-------
PlantUML version $version$ / $git.commit.id$ [Unknown compile time]
[From textarea (line 23) ]

@startuml
skinparam dpi 300
class A0
...
class B9
A0 --> A1 --> A2 --> A3 --> A4 --> A5 --> A6 --> A7 --> A8 --> A9
 Syntax Error? (Assumed diagram type: class)
-------
```

**`Syntax Error?` である。** 期待していたのは「大きさの制限で描画を拒まれた」ことの表示であった。

> [!NOTE]
> **`PlantUML version $version$ / $git.commit.id$` の `$...$` が展開されていないのは、同梱資産（TeaVM 移植版）側の
> ビルドの都合であり、MarkView の不具合ではない。** BUG-006 でステータス領域に出ていた文字列と同じ出所である。
> **資産は改変できない**（BR-042）。

---

## 2. 原因

### 2.1 6 節のソースが、PlantUML の class 図として文法違反である

```plantuml
@startuml
skinparam dpi 300
class A0
...（class A1〜A9、class B0〜B9）
A0 --> A1 --> A2 --> A3 --> A4 --> A5 --> A6 --> A7 --> A8 --> A9   ← 23 行目
B0 --> B1 --> B2 --> B3 --> B4 --> B5 --> B6 --> B7 --> B8 --> B9
A9 --> B0
@enduml
```

**`A --> B --> C` の連鎖は、class 図では書けない。** 行を数えると

| 行 | 内容 |
| --- | --- |
| 1 | `@startuml` |
| 2 | `skinparam dpi 300` |
| 3〜12 | `class A0` 〜 `class A9` |
| 13〜22 | `class B0` 〜 `class B9` |
| **23** | **`A0 --> A1 --> ... --> A9`** |

であり、**エラー図が名指しした `line 23` は、まさにこの連鎖の行である。**

### 2.2 実測 — 同梱資産に直接投げて確かめた

`frontend/vendor/plantuml/` の `viz-global.js` と `plantuml.js` をそのまま使い、`js/lazy.js` の `waitForPlantUML` と同じ判定（`MutationObserver` ＋ 300 ms の猶予）で 7 通りを描かせた。

| 投げたソース | 結果 | 大きさ |
| --- | --- | --- |
| **6 節そのまま**（連鎖、`dpi 300`） | **SVG。`Syntax Error`（line 23）** | 430 × 560 |
| 連鎖を 1 行 1 関係へ開く（20 クラス、`dpi 300`） | SVG。正常 | 65 × **2116** |
| 同（20 クラス、`dpi` 無し） | SVG。正常 | 65 × **2116** |
| 同（30 クラス、`dpi` 無し） | SVG。正常 | 73 × **3196** |
| **同（40 クラス、`dpi` 無し）** | **SVG が返らない。`java.lang.RuntimeException: Diagram too large for browser rendering: 72x4276 (max 4096)`** | — |
| 同（40 クラス、`dpi 300`） | 同上。**`72x4276` で完全に同じ** | — |
| 同（60 クラス、`dpi` 無し） | 同上。`72x6436` | — |

**3 つのことが分かった。**

#### (a) 6 節は大きさの制限に達していない

430 × 560 px であり、**4096 px の 1/7 にも満たない。** 連鎖の行で解析が止まっているため、図はエラー表示だけの小さなものになる。

#### (b) **`skinparam dpi 300` は、この移植版では大きさに影響しない**

40 クラスの連鎖で **`dpi` の有無にかかわらず `72x4276`** であった。**6 節が大きさを稼ぐために置いていた仕掛けは、そもそも効いていない。** 仮に連鎖を直しても、20 クラスでは 2116 px にしかならず、**制限には届かなかった。**

#### (c) 4096 px の拒否は**例外を投げない**

制限に達したとき、`render()` は例外を投げず、**出力先の要素へ例外のテキストを書き込む。** `js/lazy.js` の判定では `catch` ではなく **`waitForPlantUML` が `"other"` を返す経路**に入る。

```js
// frontend/js/lazy.js
  } catch {
    // 処理系が走ったうえで拒んだ。4096 px 超えはここへ来る（MD-083, IMP-233）。   ← **この記述は誤り**
    restorePlantUML(block, holder, S.pumlUnsupported);
    return;
  }

  const outcome = await waiting;
  ...
  restorePlantUML(block, holder, outcome === "other" ? S.pumlUnsupported : S.pumlFailed);
  //                             ^^^^^^^^^^^^^^^^^^^ 4096 px 超えは実際にはこちら
```

**表示は変わらない。** どちらの経路も `S.pumlUnsupported`（理由と元のソース）になるため、**利用者に見える不具合ではない。** 仕様の側は正しく書けている。

- `DSP-272` の表: 「**処理系が図を返さなかった** ／ 4096 px 超え、未対応の図種別 ／ `pumlUnsupported`」— **正しい**
- `IMP-233`: 「**4096 px を超える図は SVG ではなく例外のテキストが返る**」— **正しい**（「返る」＝ 出力先へ書き込まれる）
- **`lazy.js` のコメントだけが「ここ（`catch`）へ来る」と誤っている**

### 2.3 それでも「確認内容 3」は字面上は満たされている

`E2E-240` の確認内容 3:

> 3. 4096 px 超えと `salt` のブロックは、**PlantUML がエラー図を返せばその図、返さなければ理由と元のソース**が出る（判定は「SVG が得られたか」だけで行うため。DSP-272）。**どちらであっても空白にならない**

**6 節はエラー図（SVG）を返している。空白にもなっていない。** つまり**アプリケーションは確認内容 3 のとおりに振る舞っている。**

**NG の本体は「アプリが期待どおりに動かなかった」ではなく、「ケースが意図した検証を一度も行えていない」ことである。** 実施者の判断は正しい。

### 2.4 確認内容 3 の書き方が、この誤りを見えなくしていた

確認内容 3 は「**エラー図でも、理由の表示でも、どちらでもよい**」と書いてある。これは `DSP-272` の設計（**判定は「SVG が得られたか」だけで行う**）を忠実に反映したもので、**表示仕様としては正しい。**

しかし**テストの確認内容としては、何を見ても OK になる。**

| 実際に起きたこと | 確認内容 3 での判定 |
| --- | --- |
| 4096 px の制限で拒まれ、理由と元のソースが出た（**意図した状態**） | OK |
| **文法違反で解析が止まり、構文エラーの図が出た**（**現状**） | **OK になってしまう** |
| 20 クラスでは制限に届かず、**普通のクラス図が描けた** | **図が出ているので OK になってしまう** |

**rc.2 では実際に OK が付いている。** 実施者を責められない——**確認内容がそう書いてある。**

## 3. 原因の分類 — 仕様か、実装か

### 3.1 一次原因 — **テストデータの誤り**（＝ E2E テスト仕様の一部）

`testdata/e2e/plantuml-limits.md` は `E2E-012`（検証用データ）が定めるものであり、**40 章にファイル名と内容が列挙されている。** その 6 節が、意図した状態（4096 px 超え）を作れていない。

**2 つの誤りが重なっている。**

| # | 誤り | 影響 |
| --- | --- | --- |
| 1 | **`A --> B --> C` の連鎖を class 図に書いた** | 解析が 23 行目で止まり、以降が図にならない |
| 2 | **`skinparam dpi 300` で大きさを稼ごうとした** | **この移植版では効かない。** 1 を直しても 20 クラスでは 2116 px にしかならず、制限に届かない |

### 3.2 二次原因 — **仕様の不明瞭**（E2E-240 の確認内容 3）

2.4 のとおり、確認内容 3 は**どの結果でも OK になる書き方**である。`DSP-272` の設計をそのまま持ち込んだために、**「このブロックがどちらになるはずか」が誰にも分からない状態**になっていた。

> [!IMPORTANT]
> **表示仕様が「どちらでもよい」と定めていることと、テストの確認内容が「どちらでもよい」と書くことは別である。**
> 前者はフロントエンドに図種別の判定を持ち込まないための設計判断であり、正しい。
> 後者は**検証を放棄している。** 検証用データは**こちらが作るもの**であり、
> **どちらになるかを実測して確定させたうえで、片方を期待値として書ける。**

### 3.3 三次原因 — `lazy.js` のコメントの誤り

2.2 (c) のとおり。**利用者に見える不具合ではない**が、**「4096 px 超えは `catch` に来る」という誤った理解が残っていると、次に読んだ人が同じ前提で判断する。** BUG-005 で「Wails から取得できない」という誤ったコメントを直したのと同じ理由で、あわせて直す。

### 3.4 分類の結論

| 問い | 答え |
| --- | --- |
| **仕様が不明瞭か** | **はい。** E2E-240 の確認内容 3 が「どちらでもよい」と書かれ、**誤りを見分けられない** |
| **仕様が間違いか** | **はい。** 検証用データ（E2E-012 の一部）の 6 節が、意図した状態を作れていない |
| 実装が間違いか | **いいえ。** `lazy.js` も `renderer` も、確認内容 3 のとおりに振る舞っている。**誤っているのはコメント 1 行だけ**で、動作には現れない |

## 4. なぜ単体テストと E2E の自動テストで見つからなかったのか

### 4.1 単体テスト — 対象外（UT-002）

PlantUML の描画はフロントエンドで動く。**Go 側が持つのは「取り込み指令を弾く」ところまで**（IMP-119, UT-216）であり、**大きさの制限は処理系の内側**である。

`testdata/` そのものも単体テストの対象ではない。**`plantuml-limits.md` の内容が意図どおりかを検査するテストは存在しない。**

> [!IMPORTANT]
> **「テストデータが正しいことは、誰も検証していない。」**
> ゴールデンファイル（UT-039）には「差分を読まずに `-update` しない」という規律があるが、
> **手動テストの検証用データには、それに当たる規律が無い。** 一度書いたら、
> **実施者が現物を見て気づくまで誤りが残る。**

### 4.2 自動 E2E — ウィンドウ内を操作しない（E2E-002）

図を描かせて結果を見るには WebView の中を覗く必要があり、**構造的に対象外**である。

### 4.3 描画スモークテスト — **`plantuml-limits.md` を描かない**

`scripts/smoke` が描くのは `testdata/smoke.md` だけである（BR-054, E2E-109）。**見ているのは「同梱資産が描けるか」であって、「描けないものが正しく描けないか」ではない。**

**ここは広げる余地がある**（5.4 で述べる）。**`plantuml-limits.md` を投げて 6 節が `.plantuml-error` になることは、ブラウザ 1 つで機械的に確かめられる。** 本報告の調査そのものが、それを使い捨てのハーネスで実演している（2.2）。

### 4.4 手動テスト（rc.2）— **OK が付いていた**

rc.2 の E2E-240 は **W1 で OK** である。2.4 のとおり、**確認内容 3 の書き方では OK になる。**

**「rc.2 で OK だった」は、この不具合について何も述べていない。** BUG-006 / BUG-007 と同じ形である。

### 4.5 手動テスト（rc.3）で見つかった理由 — 確認内容に番号を振ったから

4.31.0 までの改訂で、41 章の確認内容を**番号付きの箇条書き**に改めた（E2E-200, E2E-204）。**1 項目ずつ照合する形になったことで、「3 番は本当に何を見ればよいのか」が問われた。**

**改訂の副作用として見つかった不具合**であり、**41 章の改訂が rc.3 で全 67 件をやり直す理由になっていたこと（E2E-201）を裏づけている。**

### 4.6 仕様レビューでも見つからなかった

4.31.0 までの横断レビューは、**仕様書どうしの整合**を見ている。`plantuml-limits.md` は**仕様書ではなく検証用データ**であり、**中身が仕様の意図を満たすかは、レビューの対象になっていなかった。**

`40-e2e-auto.md` はこのファイルを次のように列挙している。

> | `e2e/plantuml-limits.md` | **PlantUML の描けないもの**を集めた文書（E2E-240）。構文エラー・`!include`・標準ライブラリ・**4096 px 超え**・`salt` |

**「4096 px 超えが入っている」と書いてあるだけで、入っていることを誰も確かめていない。**

### 4.7 まとめ

| 層 | 見つけられたか | 理由 |
| --- | --- | --- |
| 単体テスト | **原理的に不可** | フロントエンドも `testdata/` も対象外 |
| 自動 E2E | **原理的に不可** | ウィンドウ内を操作しない（E2E-002） |
| 描画スモーク | **不可（現状）。ただし広げられる** | `smoke.md` しか描かない。**`plantuml-limits.md` を足せば機械で捕まえられる** |
| 仕様レビュー | 不可 | 検証用データの中身はレビュー対象外 |
| 手動テスト（rc.2） | **不可** | **確認内容 3 が「どちらでもよい」と書かれており、OK になる** |
| **手動テスト（rc.3）** | **可。実際にここで見つかった** | **確認内容に番号を振り、1 項目ずつ照合したため** |

## 5. 修正方法

### 5.1 検証用データの 6 節を差し替える（**実測で確定した内容**）

**連鎖をやめ、1 行 1 関係にし、クラスを 40 個にする。`skinparam dpi` は効かないので消す。**

````markdown
## 6. 4096 px を超える図

処理系が描画を拒みます（MD-083）。**Java 版の PlantUML には無い制限**です。

**縦に 40 個つないで 4276 px にしています。** 30 個（3196 px）では制限に届きません。
`skinparam dpi` はこの移植版では大きさに影響しないため、置いていません。

```plantuml
@startuml
class A0
class A1
（… class A39 まで）
A0 --> A1
A1 --> A2
（… A38 --> A39 まで）
@enduml
```
````

**実測: `java.lang.RuntimeException: Diagram too large for browser rendering: 72x4276 (max 4096)`（516 ms）。**

> [!NOTE]
> **`plantuml-limits.md` は人が読むファイルでもある。** 41 行の `class` と 39 行の関係が並ぶのは冗長だが、
> **「どうすれば制限に達するか」は自明ではない**（`dpi` が効かないこと、30 個では足りないこと）ため、
> **文書側に理由を書き添える。** 上の案はそのように書いている。

### 5.2 `E2E-240` の確認内容 3 を、期待値が 1 つに定まる形へ書き直す

現状（**どちらでもよい**）:

> 3. 4096 px 超えと `salt` のブロックは、PlantUML がエラー図を返せばその図、返さなければ理由と元のソースが出る（判定は「SVG が得られたか」だけで行うため。DSP-272）。どちらであっても空白にならない

案（**実測で確定させる**）:

> 3. **6 節（4096 px 超え）は図にならず、理由と元のソースが出る。** 図が出ていたら NG——制限に達していないか、ソースが文法違反になっている（BUG-010）
> 4. **7 節（`salt`）と 8 節（`ditaa`）は、エラー図が出るか、理由と元のソースが出るかのどちらかである**（判定は「SVG が得られたか」だけで行うため。DSP-272）。**どちらであっても空白にならない**

**6 節と 7・8 節を分ける。** 6 節はこちらが大きさを決められる（＝期待値を確定できる）が、`salt` / `ditaa` は**処理系の版によって返し方が変わりうる**ため、「どちらでもよい」のままが正しい。

> [!IMPORTANT]
> **`salt` / `ditaa` の側は BR-043 の自動更新で振る舞いが変わりうる。** ここを断定的に書くと、
> **資産が更新されるたびに手動テストが誤って NG になる。** 確認内容の書き方を分ける根拠がここにある。

### 5.3 `lazy.js` のコメントを直す

```js
  } catch {
    // 処理系が例外を投げた。**4096 px 超えはここへ来ない**——制限に達した場合、
    // 処理系は例外を投げずに出力先へ例外のテキストを書くため、waitForPlantUML が
    // "other" を返す経路に入る（実測。BUG-010）。文言はどちらも pumlUnsupported。
    restorePlantUML(block, holder, S.pumlUnsupported);
```

**動作は変えない。** `IMP-233` と `DSP-272` は正しいので、仕様の改訂は不要である。

### 5.4 再発防止（案）— 描画スモークテストに `plantuml-limits.md` を足す

4.3 のとおり、**この不具合は機械で捕まえられる。**

```
6 節を描かせて .plantuml-error になること（.plantuml-rendered に SVG が入らないこと）
2 節を描かせて .plantuml-rendered に SVG が入ること（構文エラーは図で出る）
1 節が描けていること（他のブロックの失敗が波及していない）
```

| 論点 | 判断 |
| --- | --- |
| E2E-002 に抵触するか | **しない。** `scripts/smoke` は `frontend/` を配って描かせるだけで、**ウィンドウの操作をしない。** BUG-006 に対する `scripts/domids` と同じ位置づけ |
| BR-043 の自動更新で壊れないか | **6 節だけを見るなら壊れにくい。** `salt` / `ditaa` は 5.2 の理由で対象にしない |
| 実行時間 | 実測 516 ms。**現状のスモークテストに足しても支障は無い** |
| 仕様の改訂 | **`BR-054` / `E2E-109` / `E2E-020` を同じ変更で改訂する。** 範囲を広げるのは**仕様の判断として明示的に行う**（E2E-020 の IMPORTANT） |

**採否は別途判断する。** 本報告は「できる」ことと「どこを直す必要があるか」までを示す。
