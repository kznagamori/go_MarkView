# 30. 単体テスト仕様: 方針と禁止事項

> 索引: [README](README.md) | 単体テスト: **30** / [31](31-test-cases.md)

本文書は、MarkView の単体テスト（`UT-nnn`）に関する方針を定める。**何をテストするか**の一覧は [31. テストケース](31-test-cases.md) にある。

## 30.1 位置づけ

### UT-001: 目的 **MUST**

単体テストの目的は、**仕様書に書かれた振る舞いが実装によって満たされていることを、変更のたびに機械的に確かめられる状態にすること**である。

この目的に照らして、次の 2 つを等しく重要とする。

1. 有効なテストを書くこと。
2. **有効でないテストを書かないこと。** 無意味なテストは、通っているという事実によって「検証されている」という誤った安心を生み、変更のたびに保守コストだけを課す。テストがないことより悪い状態になりうる。

本文書の 30.3 節（禁止事項）は、2 のために置く。

### UT-002: 対象と対象外 **MUST**

| 区分 | 対象 | 根拠 |
| --- | --- | --- |
| **対象** | `internal/` 配下の全パッケージ（`session` を含む） | IMP-012, IMP-040 |
| 対象外 | `main.go` と `app.go` | Wails に依存するため。**判断を伴うロジックはここに置かず `internal/session` へ切り出す**（IMP-012） |
| 対象外 | フロントエンド（JavaScript） | 開発ホストに Node.js を要求しないため（BR-001）。**描画**は描画スモークテスト（BR-054）、**操作**は手動テスト（41 章）が受け持つ。**スモークテストはクリックもキー入力も行わない** |
| 対象外 | WebView を起動する経路 | CI での安定性が確保できないため（IMP-042） |
| 対象外 | ネットワークアクセスを伴う処理 | IMP-042 |
| 対象外 | ビルド・CI の設定 | 仕組みそのものが CI の実行で検証される |

この範囲設定は、**ロジックの置き場所に関する設計判断の裏返し**である。

- フロントエンドを対象外とできるのは、そこにロジックが無いからではなく、壊れると影響の大きいロジックをすべて Go 側へ寄せているためである（AR-031: 変換・ハイライト・サニタイズは Go 側、IMP-300: 判断は Go 側）。
- `app.go` を対象外とできるのは、判断を伴う処理を `internal/session` へ切り出しているためである（IMP-012）。`app.go` にロジックを書くと、テストが `package main` に属し、テストバイナリに Wails（Linux では cgo と WebKitGTK）がリンクされる。軽いロジックの検証に GUI の依存が付いてくる状態は避ける。

**この配置が崩れると単体テストの守備範囲も崩れる。** フロントエンドや `app.go` に判断ロジックを移す変更を行う場合は、本文書の対象範囲もあわせて見直す。

## 30.2 有効なテストの指針（UT-010 系）

### UT-010: テストは仕様に対応させる **MUST**

各テストは、**要求仕様または実装仕様のどの項目を検証しているか**を明示する。

```go
// TestNormalize_BOMAndNewlines は FR-021 / IMP-103 を検証する。
func TestNormalize_BOMAndNewlines(t *testing.T) { … }
```

- 対応する仕様 ID をコメントに記す。31 章のケース表と ID で結び付ける。
- **仕様に書かれていない振る舞いをテストで固定しない。** 実装の都合で決まっただけの挙動をテストで縛ると、正当なリファクタリングが失敗するようになる。仕様として必要なら、まず仕様書に書く。

### UT-011: 内部構造ではなく振る舞いをテストする **MUST**

テストは「パッケージの外から観測できること」だけを対象とする。

| テストしてよいもの | テストしてはいけないもの |
| --- | --- |
| 公開関数の戻り値 | 非公開フィールドの値 |
| 返されたエラーの種別（`errors.Is`） | 内部で何回関数が呼ばれたか |
| 出力された HTML の構造 | 内部で使っているデータ構造の形 |
| 状態を変える関数の、変更後の観測結果 | 中間変数の内容 |

判定の基準は「**実装を書き換えても振る舞いが同じなら、テストは通り続けるか**」である。通らなくなるテストは、振る舞いではなく実装をテストしている。

### UT-012: 1 つのテストは 1 つの主張をする **SHOULD**

- テスト名から、何が保証されるのかが読み取れること。`TestLoad` ではなく `TestLoad_ReturnsErrTooLarge_WhenOver50MB`。
- 複数の観点を 1 つのテスト関数に詰め込まない。失敗したときにどの観点が壊れたのか分からなくなる。
- ただしテーブル駆動（UT-014）で同じ観点の入力を並べるのは、1 つの主張の範囲内とする。

### UT-013: 境界値と異常系を優先する **MUST**

正常系だけのテストは、書いた本人が既に確信していることを確認するだけに終わりやすい。**壊れる可能性が高いところから書く。**

優先順位:

1. **境界値** — 閾値のちょうど上・ちょうど下（10 MiB / 10 MiB + 1 など）
2. **異常系** — 存在しないパス、権限なし、壊れたデータ、空入力
3. **仕様上の例外規定** — 「〜の場合は〜しない」と書かれている箇所
4. 正常系の代表例

MarkView の場合、「壊れても落ちない」（FR-111, NFR-050）が要求にあるため、**異常入力で `panic` しないことの確認は特に重要**である。

### UT-014: テーブル駆動テストを基本とする **SHOULD**

同じ関数に対する複数の入力は、テーブル駆動で書く。

```go
func TestSlug(t *testing.T) {
    tests := []struct {
        name string
        in   string
        want string
    }{
        {"英字は小文字化", "Hello World", "hello-world"},
        {"記号は除去", "What's New?", "whats-new"},
        {"日本語は保持", "概要", "概要"},
        {"空白 1 つにつきハイフン 1 つ", "a   b", "a---b"},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) { … })
    }
}
```

- ケース名は日本語でよい。`t.Run` のサブテスト名として失敗時に表示され、何が壊れたかが読める。
- 31 章のケース表は、この `tests` スライスにそのまま対応する形で書いてある。

### UT-015: 期待値を具体的に書く **MUST**

```go
// 悪い: 何を保証しているのか分からない
if len(result.Headings) == 0 {
    t.Error("headings is empty")
}

// 良い: 期待する内容が読める
want := []renderer.Heading{
    {Level: 1, Text: "MarkView", ID: "markview"},
    {Level: 2, Text: "概要", ID: "概要"},
}
if diff := cmp.Diff(want, result.Headings); diff != "" {
    t.Errorf("Headings mismatch (-want +got):\n%s", diff)
}
```

- 「空でない」「エラーでない」だけを見るアサーションは、ほとんどの変更を検出できない。
- 期待値はテスト内にリテラルで書く。実装と同じロジックで計算して比較しない（UT-031）。

### UT-016: 失敗したときに原因が分かるメッセージを書く **MUST**

- 失敗メッセージには「期待値」と「実際の値」を両方含める。
- 差分比較には `go-cmp` を用いてよい。構造体やスライスの比較で、どのフィールドが違うかが読める。
- `t.Fatal` と `t.Error` を使い分ける。以降のアサーションが無意味になる場合のみ `t.Fatal`。

### UT-017: テストは独立かつ再現可能にする **MUST**

- テストの実行順序に依存しない。`go test -shuffle=on` で通ること。
- グローバル変数を書き換えない。やむを得ない場合は `t.Cleanup` で必ず戻す。
- 一時ファイルは `t.TempDir()` を使う。テスト終了時に自動で消える。固定パス（`/tmp/test.md` 等）を使わない。
- 環境変数を変更する場合は `t.Setenv` を使う。

### UT-018: テストデータの置き場所 **MUST**

| 種類 | 置き場所 |
| --- | --- |
| 数行程度の入力 | テスト関数内のリテラル |
| Markdown 文書、期待 HTML | `testdata/` 配下のファイル |
| 描画の網羅確認用（BR-053） | `testdata/showcase.md` |

- `testdata/` は Go のツールチェインが無視する特別なディレクトリであり、ビルド対象に含まれない。
- ゴールデンファイル（期待 HTML）は整形して保存し、差分がレビューで読める状態を保つ（IMP-041）。

### UT-019: 並行性を持つ処理のテスト **SHOULD**

`watcher`（IMP-140）のようにゴルーチンとチャネルを使う処理では、

- **`time.Sleep` で待たない。** チャネルからの受信と `select` + `time.After` によるタイムアウトで待つ。
- タイムアウトは十分に長く取る（2 秒程度）。CI の負荷で揺れるため、ぎりぎりの値にしない。
- `go test -race` で通ること。データ競合の検出は、この種のコードで最も価値が高い。

## 30.3 禁止事項（UT-030 系）

以下は「書いてはいけないテスト」である。レビューで見つけた場合は、修正するか削除する。

### UT-030: カバレッジのためのテストを書かない **MUST**

**カバレッジ率を上げること自体を目的としたテストを書かない。**

```go
// 禁止例: 呼ぶだけで何も主張していない
func TestNew(t *testing.T) {
    r := renderer.New()
    if r == nil {
        t.Error("nil")
    }
}
```

- 本仕様はカバレッジに数値目標を置かない（UT-060）。率を満たすために書かれたテストは、行を通過させるだけで振る舞いを検証せず、保守コストだけが残る。
- 「まだテストがないから」ではなく「壊れたら困るから」を書く理由とする。

### UT-031: 実装のロジックをテスト側で再現しない **MUST**

```go
// 禁止例: 実装と同じ計算をして比較している。実装が間違っていても通る
want := strings.ToLower(strings.ReplaceAll(input, " ", "-"))
if got := Slug(input); got != want { … }
```

期待値は**人が考えて書いたリテラル**とする。実装を写した式で期待値を作ると、実装の誤りをそのまま是とするテストになる。

### UT-032: アサーションのないテストを書かない **MUST**

```go
// 禁止例: エラーが出ないことしか見ていない
func TestRender(t *testing.T) {
    _, err := r.Render([]byte("# hello"), "")
    if err != nil {
        t.Fatal(err)
    }
}
```

「落ちないこと」だけを確かめるテストが有効なのは、**それ自体が仕様である場合に限る**（FR-111 の異常入力での非クラッシュなど）。その場合はテスト名とコメントで「落ちないことが仕様である」ことを明示する。それ以外では、出力に対する主張を必ず置く。

### UT-033: 常に成功するテストを書かない **MUST**

- 条件式が必ず偽になる、`if` の中身が空、`t.Skip` が無条件で先頭にある、といったテストを残さない。
- **書いたテストは、一度は失敗させて確かめる。** 実装をわざと壊してテストが赤くなることを確認してから、実装を戻す。この手順を踏まないテストは、何も検出しない可能性がある。

### UT-034: 標準ライブラリと外部ライブラリをテストしない **MUST**

```go
// 禁止例: goldmark の表の仕様を網羅している（それは goldmark の責務）
func TestTable_Alignment(t *testing.T)      { … :--- / :---: / ---: を全部試す … }
func TestTable_EscapedPipe(t *testing.T)    { … セル内の \| の扱い … }
func TestTable_InlineInCell(t *testing.T)   { … セル内の強調・リンク・コード … }
```

- テストするのは**自分たちが書いたコード**である。`filepath.Join` や `json.Unmarshal` の動作を確認しない。
- ただし、**自分たちの設定・組み合わせ方が正しいこと**の検証は対象である。「goldmark に GFM 拡張を渡し忘れていないか」は自分たちの責務であり、**代表的な記法 1 つが変換されることを見れば足りる**（UT-201）。記法ごとの網羅は goldmark 側に任せる。
- この線引きは「壊れたときに直すのは誰か」で決まる。表のアラインメントが効かなければ goldmark の不具合であり、こちらのテストで検出しても直せない。一方、拡張の登録漏れはこちらの不具合である。
- 同様に、`chroma` の各言語の色分けを網羅しない。「言語指定が解決され、クラス名が出力される」ことまでを見る（UT-208）。

### UT-035: 実行環境に依存するテストを書かない **MUST**

| 依存してはいけないもの | 代わりに |
| --- | --- |
| 実行マシンの絶対パス | `t.TempDir()` |
| 現在時刻 | 時刻を引数・フィールドとして注入する |
| ロケール・タイムゾーン | 影響を受けない実装にする |
| 実行順序 | `-shuffle=on` で通るようにする |
| ネットワーク | テストしない（IMP-042） |
| ユーザのホームディレクトリ・実際の `%TEMP%` | `t.Setenv` で差し替える |

`config` の保存先（IMP-152）のように OS 依存の分岐を持つコードは、**パス解決の関数を分離し、環境変数を差し替えて検証できる形にする**（UT-501）。

### UT-036: テスト間で状態を共有しない **MUST**

- パッケージレベルの変数にテストの結果を溜めない。
- 前のテストが作ったファイルに依存しない。
- `TestMain` での初期化は、全テストに共通で無害なものに限る。

### UT-037: 時間に依存する待ち方をしない **MUST**

```go
// 禁止例: 環境によって成功したり失敗したりする
go doSomething()
time.Sleep(100 * time.Millisecond)
if !done { t.Error("not done") }
```

CI の負荷で揺れるテスト（flaky test）は、失敗しても「また揺れたのだろう」と無視されるようになり、**本物の不具合を見逃す原因になる**。チャネルによる同期（UT-019）で書く。

### UT-038: GUI・WebView を起動しない **MUST**

- `wails` パッケージを import するテストを書かない。`internal/` は Wails に依存しない設計になっている（IMP-012）ため、この禁止は設計の維持でもある。
- 描画結果の目視確認が必要なものは、単体テストではなくスモークテスト（BR-054）と手動確認で扱う。

### UT-039: ゴールデンファイルを無検証で更新しない **MUST**

`-update` フラグ（IMP-041）で期待 HTML を再生成できるが、

- **差分を読まずに更新しない。** 更新の前後で差分を確認し、その変更が意図したものであることを確かめる。
- 意図しない差分が混ざったまま更新すると、以後その誤りが「期待値」になる。
- レビューでは、ゴールデンファイルの差分もコードと同じ厳しさで見る。

### UT-040: モックで固めすぎない **SHOULD**

- MarkView の `internal/` は外部サービスに依存しないため、モックが必要な場面はほとんどない。ファイルシステムは `t.TempDir()` の実ファイルで足りる。
- インタフェースを「テストのためだけに」導入しない。実装が 1 つしかないインタフェースは、抽象化ではなく間接化にすぎない。
- モックを使うと、**モックの振る舞いをテストしているだけ**の状態になりやすい。実物で書けるなら実物で書く。

### UT-041: 非公開関数を直接テストすることに頼らない **SHOULD**

- 同一パッケージ内のテストからは非公開関数を呼べるが、それに依存すると内部構造の変更でテストが壊れる（UT-011）。
- 公開関数経由で到達できないロジックがあるなら、それは切り出すべき責務である可能性が高い。まず設計を見直す。
- 複雑なアルゴリズム（スラッグ生成、デバウンス判定など）を非公開のまま直接テストすることは許容する。その場合も、公開関数経由のテストを別に用意する。

### UT-042: 仕様にない挙動を固定しない **MUST**

- 「たまたま今こう動く」ことをテストで固定しない。将来の変更を不当に縛る。
- マップの反復順序、スライスの並び順（仕様で定めていない場合）、エラーメッセージの文字列そのものに依存しない。エラーは `errors.Is` で種別を見る（IMP-021）。

## 30.4 命名と配置（UT-050 系）

### UT-050: ファイルの配置 **MUST**

- テストは対象と同じパッケージ・同じディレクトリに `*_test.go` として置く。
- パッケージ名は `package document`（内部テスト）を基本とする。公開 API のみを使う場合は `package document_test` としてもよい。

### UT-051: 命名規則 **SHOULD**

```
Test<対象><_条件><_期待>
```

| 例 | 意味 |
| --- | --- |
| `TestNormalize_StripsBOM` | BOM を除去すること |
| `TestLoad_ReturnsErrTooLarge_WhenOver50MB` | 50 MB 超で `ErrTooLarge` を返すこと |
| `TestReadDir_ExcludesDotDirectories` | ドットで始まるディレクトリを除外すること |

- サブテスト名（`t.Run` の第 1 引数）は日本語でよい。31 章のケース表の「観点」列と対応させる。

### UT-052: ヘルパ関数 **SHOULD**

- 複数のテストで使う組み立て処理はヘルパにまとめ、先頭で `t.Helper()` を呼ぶ。失敗行がヘルパ内ではなく呼び出し元として報告される。
- ヘルパにアサーションを詰め込みすぎない。何を検証しているかがテスト本体から読めなくなる。

## 30.5 実行とカバレッジ（UT-060 系）

### UT-060: カバレッジの扱い **MUST**

- **カバレッジに数値目標を置かない。** 率を合否の基準にしない（BR-052 の検査項目にも含めない）。
- CI では `go test -cover` の結果を記録し、パッケージごとの推移を見えるようにする（**SHOULD**）。極端に低いパッケージは、テストの要否を検討する契機として扱う。
- 数値の代わりに、**要求 ID ごとにテストが存在するかを追跡する**（UT-061）。これが本仕様における網羅性の指標である。

> [!NOTE]
> カバレッジ率は「実行された行の割合」であって「検証された振る舞いの割合」ではない。アサーションのないテスト（UT-032）でも率は上がる。率を目標にすると、UT-030 で禁止したテストを書く動機が生まれる。この構造を避けるため、率は参考値に留める。

### UT-061: 要求とテストの対応の追跡 **MUST**

- 31 章の末尾に「要求 → テストケース」の対応表を置き、**テストが存在しない要求を可視化する**（[31 章 31.10](31-test-cases.md)）。
- 対応表には**すべての要求 ID が 1 行ずつ現れる**。範囲表記で省略しない（UT-902）。省略すると、要求が追加されたときに漏れが検出できない。
- 要求を追加・変更した場合、この表を同じ変更で更新する（NFR-071）。
- テストが存在しない要求があること自体は問題ではない。単体テストに馴染まない要求（画面の見た目、ビルド設定、「行わないこと」の要求）が存在するためである。**分類記号を付し、意図的な不在であることを示す**（UT-901）。
- **E2E テストにも同じ形の対応表がある**（40 章 40.5、E2E-030 系）。**2 つの表は互いを埋め合う。** ここで `— (GUI)` とした要求の多くは、E2E 側にケースを持つ。逆に E2E 側で `— (INTERNAL)` とした要求は、ここにテストがある。**片方だけを見て「検証されていない」と判断しない。**

### UT-062: 実行方法 **MUST**

| 目的 | コマンド |
| --- | --- |
| 通常の実行 | `go test ./...` |
| 競合検出 | `go test -race ./...` |
| 順序依存の検出 | `go test -shuffle=on ./...` |
| カバレッジの記録 | `go test -cover ./...` |
| ゴールデンの更新 | `go test ./internal/renderer -update` |

CI では最低限 `go test -race ./...` を実行する（BR-052）。

## 30.6 レビュー観点（UT-070）

### UT-070: テストをレビューするときの確認項目 **SHOULD**

新しいテストを含む変更をレビューする際、以下を確認する。

- [ ] このテストは、実装を壊したら失敗するか（UT-033）
- [ ] 期待値は人が書いたリテラルか。実装を写していないか（UT-031）
- [ ] アサーションは具体的か。「空でない」で終わっていないか（UT-015, UT-032）
- [ ] 境界値・異常系が含まれているか（UT-013）
- [ ] 検証しているのは振る舞いか。内部構造ではないか（UT-011）
- [ ] 実行順序・時刻・実行マシンに依存していないか（UT-035, UT-037）
- [ ] 対応する仕様 ID がコメントにあるか（UT-010）
- [ ] ゴールデンファイルの差分を読んだか（UT-039）
