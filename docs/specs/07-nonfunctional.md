# 07. 非機能要求

> 索引: [README](README.md) | 前: [06. ビルド・配布](06-build-release.md)

本文書は、性能・資源・安全性・保守性に関する要求と、その測定条件を定義する。

## 7.1 測定の前提条件

特に断りのない限り、以下の条件で測定した値を基準とする。

| 項目 | 条件 |
| --- | --- |
| ハードウェア | 4 コア以上の CPU、8 GB 以上のメモリ、SSD |
| OS | **性能の目標値は Windows 11（amd64）を基準とする**。Ubuntu 24.04（amd64）でも動作を確かめるが、性能の目標は課さない |
| **標準文書** | 約 100 KB、見出し 50 個、コードブロック 30 個、ローカル画像 5 枚を含む Markdown。**Mermaid 図・PlantUML 図・数式は含まない** |
| **図表入り文書** | 標準文書に Mermaid 図 2 個、数式 10 個、**PlantUML 図 2 個（うち 1 個は Graphviz を要する class 図）**を加えたもの |
| **大規模文書** | 約 1 MB の Markdown（Mermaid 図・PlantUML 図・数式は含まない） |
| 測定回数 | 5 回測定し中央値を採る。初回起動（WebView の初期化を含む）と 2 回目以降を区別して記録する |

> [!NOTE]
> 標準文書から Mermaid・PlantUML・数式を外しているのは、遅延ロード（AR-021）の効果を測るためである。これらを含む場合の値は「図表入り文書」で別に測る。

> [!IMPORTANT]
> **性能の基準環境は Windows 11 / amd64（E2E-010 の W1）とする。** Linux は描画エンジンが異なり（WebKitGTK）、同じ目標値を課す根拠が無い。**Linux では性能を測らず、目標も課さない。**
>
> **ただし「描けること」は別である。** FR-024 と MD-083 は **MUST** であり、対象環境を限定していない。Linux で描けない記法があれば、それは性能ではなく**機能の不具合**である（NFR-061）。

## 7.2 性能（NFR-010 系）

### NFR-010: 起動時間 **MUST**

| 条件 | 目標 |
| --- | --- |
| 標準文書を引数に指定して起動し、本文が描画されるまで（2 回目以降） | **1.0 秒以内** |
| 同上（OS 起動後の初回。WebView の初期化を含む） | 2.5 秒以内 |
| 引数なしで起動し、操作案内が表示されるまで | 0.8 秒以内 |

- 上表の計測終点は**本文テキストの描画が完了した時点**とする。Mermaid 図・PlantUML 図・数式は本文表示より後に非同期で描画されるため（NFR-012）、その完了時刻は含めない。
- 図表入り文書を指定して起動した場合も、上表の値を満たすこと。Mermaid・KaTeX・PlantUML の読み込みが本文描画の完了を妨げてはならない。**PlantUML の資産は 5 MiB を超え、Graphviz 系の図は 1 枚 1 秒近くかかる（NFR-011）。本文の表示をこれに待たせてはならない。**
- 起動時にディレクトリツリーの再帰走査を行わないこと（FR-032）。
- Mermaid・KaTeX・PlantUML は、それを含む文書を開いた場合を除いて読み込まないこと（AR-021）。標準文書はこれらを含まないため、読み込みが発生してはならない。
- **上表の目標値は 7.1 の基準環境（Windows 11 / amd64）に対するものである。** この節の以降の目標値（NFR-011、NFR-020）も同じである。

### NFR-011: 変換・描画性能 **MUST**

| 処理 | 目標 |
| --- | --- |
| 標準文書の Markdown → HTML 変換（Go 側） | 50 ms 以内 |
| 標準文書の表示切り替え（クリックから描画完了まで） | 300 ms 以内 |
| 大規模文書（1 MB）の表示 | 2.0 秒以内 |
| 図表入り文書の Mermaid 図の描画完了（本文表示後、非同期） | 1.5 秒以内 |
| **PlantUML 図 1 枚の描画完了**（Graphviz を要さない図。sequence / activity / mindmap 等） | **100 ms 以内** |
| **PlantUML 図 1 枚の描画完了**（Graphviz を要する図。class / component / state 等） | **1.0 秒以内** |
| ファイル更新検知から再描画完了まで（標準文書） | 500 ms 以内 |
| 文書内検索の初回ハイライト（標準文書） | 150 ms 以内 |

> [!NOTE]
> **PlantUML だけ「1 枚あたり」で目標を置いている。** Graphviz を要する図は 1 枚 400〜700 ms かかり、枚数に比例して伸びる（実測: 5 枚 2,136 ms、10 枚 7,104 ms）。文書単位の秒数にすると、**測定用文書に何枚入れるかで目標値が動き**、文書の定義を変えるたびに秒数を決め直すことになる。枚数は文書側の都合であり、目標に織り込まない。
>
> **文書全体の描画が何秒で終わるかは目標にしない。** 代わりに、**描画中も UI が固まらないこと**（NFR-012）で利用者への影響を押さえる。同梱する処理系は細切れに実行されるため、400 ms かかる図でもメインスレッドの停止は 4 ms 以下であった。
>
> 将来、並ぶ図の枚数が問題になる場合は、**見えている図から描く**（`IntersectionObserver`）併用を検討する。

### NFR-012: 操作の応答性 **MUST**

- スクロールは 60 fps を維持し、視認できるカクつきを生じないこと。
- ペイン幅のドラッグ操作、テーマ切り替え、ペインの表示・非表示の切り替えは、いずれも 100 ms 以内に画面へ反映されること。
- Mermaid 図・PlantUML 図の描画中も、UI 操作（スクロール、ボタン操作）が阻害されないこと。図の描画は本文表示より後に非同期で完了してよい。**PlantUML は 1 枚に 1 秒近くかかりうるため（NFR-011）、この条件がとりわけ重い。**
- 100 ms を超える処理を行う場合、処理中であることを利用者に示すこと（**SHOULD**）。

### NFR-013: 遅延ロードの徹底 **MUST**

- Mermaid 記法を含まない文書を表示する限り、`mermaid.min.js` は評価されないこと。
- 数式を含まない文書を表示する限り、KaTeX は評価されないこと。
- **PlantUML 記法を含まない文書を表示する限り、`plantuml.js` と `viz-global.js` は評価されないこと。**
- この 3 点は、起動時のメモリ使用量と表示完了時間に直接影響するため、実装上の必須条件とする。**中でも PlantUML は資産が最も大きい（5.09 MiB。Mermaid と KaTeX の合計を上回る）。**

## 7.3 資源使用量（NFR-020 系）

### NFR-020: メモリ **MUST**

WebView のプロセスを含むアプリケーション全体の常駐サイズ（RSS / ワーキングセット）について、以下を目標とする。

| 状態 | 目標 |
| --- | --- |
| 起動直後（操作案内の表示のみ） | 180 MB 以下 |
| 標準文書の表示中 | 250 MB 以下 |
| 図表入り文書の表示中（Mermaid・KaTeX・**PlantUML** の読み込みを含む） | **420 MB 以下** |
| Go プロセス側のみ（WebView を除く） | 60 MB 以下 |

- 文書を 20 回連続で切り替えた後も、メモリ使用量が単調増加しないこと（リークがないこと）。
- ファイル監視のウォッチャは常に 1 つ以下であること（AR-070）。
- ファイルツリーはディレクトリを展開した分だけメモリを消費する。ツリールート以下の全階層を保持してはならない（FR-032）。

> [!NOTE]
> WebView は Chromium / WebKit ベースであり、それ自体が 100 MB 前後を占める。本アプリで制御可能なのは主に Go 側と描画内容であるため、目標値はこのベースラインを前提としている。
>
> 図表入り文書を 350 MB から 420 MB へ引き上げたのは PlantUML の分である。JS ヒープの実測は読み込み後 16 MB、描画後 39 MB、Graphviz 系を 10 枚描いて 53 MB であった。**遅延ロード（NFR-013）が効いている限り、標準文書と起動直後の目標は変わらない。**

### NFR-021: ファイルサイズ **SHOULD**

| 対象 | 目標 |
| --- | --- |
| 実行ファイル単体（Windows / amd64） | **30 MB 以下** |
| 実行ファイル単体（Linux / amd64） | 30 MB 以下 |
| 配布アーカイブ（zip / tar.gz） | 12 MB 以下 |

- 上表は**目標値**であり、超過をもってリリースを中止する基準ではない。サイズは CI で常に計測して記録し、超過時は警告として可視化する（BR-060）。
- 目標値を SHOULD としているのは、埋め込み資産（Mermaid / KaTeX / PlantUML）がリリース時に自動更新される運用（BR-043）を採っており、外部の資産サイズの増加によってリリースが機械的に止まる事態を避けるためである。ただし「小さく保つ」こと自体は本アプリの中心的な価値（[01-overview](01-overview.md) 1.3.2）であり、超過した状態を放置してはならない。
- 依存ライブラリや埋め込み資産の追加は、サイズへの寄与を評価したうえで判断する。
- サイズ削減のために実行ファイル圧縮（UPX 等）を用いてはならない（BR-010, NFR-052）。この点は **MUST** とする。

> [!IMPORTANT]
> **25 MB から 30 MB へ引き上げたのは PlantUML を同梱するためである**（**+5.09 MB**）。同梱前の実測は **20.86 MB**、同梱後の実測は **26.02 MB** である（2026-09-03）。**残りは 3.98 MB。**
>
> 数値はすべて 2 進接頭辞である（`1 MB = 1,048,576 バイト`。[README](README.md) の「単位の表記」）。
>
> Mermaid・KaTeX・PlantUML はいずれも BR-043 で自動更新されるため、**上流が太るだけで目標を割りうる**。BR-060 の計測と警告が実質的な歯止めになる。**サイズを戻すために `viz-global.js` を圧縮・結合することはできない**（BR-042。EPL-2.0 の条件に触れる）。
>
> 配布アーカイブは目標を変えない。同梱後の**実測は 9.52 MB**であり、12 MB に収まる（2026-09-03）。

### NFR-022: CPU 使用率 **SHOULD**

- 文書を表示して操作していない状態（アイドル時）の CPU 使用率は 1 % 未満であること。ポーリングによるファイル監視やアニメーションの常時実行を行わない。
- 常駐プロセス、バックグラウンドでの定期処理は持たない。

## 7.4 安全性（NFR-030 系）

MarkView は「第三者から受け取った Markdown ファイルを開く」ことを前提とするため、文書は信頼できない入力として扱う。

### NFR-030: 文書由来のコード実行の禁止 **MUST**

- Markdown 中の `<script>` およびイベントハンドラ属性は、サニタイズにより確実に除去される（MD-072）。
- Mermaid は `securityLevel: strict` 相当で動作させ、図の定義からスクリプトが実行されないようにする（MD-081）。
- KaTeX は信頼できない入力を前提とした設定（`trust: false` 相当）で動作させる。
- **PlantUML は、外部を取り込むプリプロセッサ指令を含むブロックを Go 側で描画対象から外す**（MD-084, IMP-119）。PlantUML には Mermaid の `securityLevel` に相当する設定が無く、**入力側で制限する以外の手段が無い**。
- WebView 内で実行される JavaScript は、実行ファイルに埋め込まれた自前の資産に限る。文書から供給されたコードを評価してはならない。

### NFR-031: ファイルアクセスの制限 **MUST**

- 内部アセットサーバがローカルファイルを配信する経路は、画像として扱える拡張子に限定する（AR-041）。
- パスは正規化・シンボリックリンク解決を行ったうえで検査し、意図しないファイルの読み出しを防ぐ。
- アプリケーションはファイルの**読み取りのみ**を行う。次の 2 つを除き、いかなるファイルも作成・変更・削除しない。表示中の Markdown ファイルを書き換える経路を持たない。

| 例外 | 書く主体 | 位置 |
| --- | --- | --- |
| 設定ファイル | アプリケーション | UI-112 |
| WebView のユーザデータ領域 | **WebView ランタイム**（WebView2 / WebKitGTK） | AR-004 |

  後者はアプリケーションが直接書くものではないが、**位置を決めるのはアプリケーション側の責任**であるため例外として明記する（AR-004）。数十 MB 規模になりうる。

> [!NOTE]
> **これは「MarkView 自身が書かない」という規定である。** 外部エディタで開く機能（[FR-090](02-functional.md)）は、利用者が選んだ別のプログラムへ絶対パスを渡すものであり、そこで書き込みが起きるとすれば責任はエディタ側にある。既定ブラウザに URL を渡した先で何が起きるかを MarkView が制御しないのと同じである（NFR-035）。**MarkView が表示中の Markdown ファイルを書き換える経路は、依然として存在しない。**

### NFR-032: ネットワーク **MUST**

- アプリケーション自身は、起動時・実行中を通じて外部へ通信しない。更新確認、利用統計の送信、クラッシュレポートの送信のいずれも行わない。
- 発生しうる外部通信は、表示中の文書が `http(s)` 画像を参照している場合の画像取得のみである（MD-071）。
- **PlantUML の取り込み指令（`!include` / `!includeurl` / `!includesub` / `!import` / `from` を伴う `!theme`）を含むブロックは、Go 側で描画対象から外す**（MD-084, IMP-119）。

> [!NOTE]
> **同梱する版は、これらの指令で実際には通信しないことを実測で確かめている**（記録用のローカルサーバへのアクセス 0 件）。それでも Go 側で塞ぐのは次の 2 つのためである。
>
> 1. `XMLHttpRequest` の経路がバンドルに残っており、**将来の版で有効化される余地がある**。資産は BR-043 で自動更新されるため、こちらが気づかないまま振る舞いが変わりうる。
> 2. **どうせ描けない**（標準ライブラリも URL も失敗する。MD-083）。PlantUML の読みにくいエラー図を出すより、こちらで理由を書いたほうが親切である（FR-110）。
- 内部アセットサーバは外部ネットワークインターフェースにバインドしない（AR-041）。

### NFR-033: 権限 **MUST**

- 管理者権限・root 権限を必要としない。
- レジストリ、システムディレクトリ、ユーザのホームディレクトリ配下の設定領域（`%APPDATA%`, `~/.config` 等）に書き込まない。書き込みはテンポラリディレクトリ内に限る（UI-112, AR-004）。
- **WebView のユーザデータ領域も、位置を指定できる OS ではテンポラリディレクトリ配下へ寄せる**（AR-004）。Windows で指定を怠ると `%APPDATA%\MarkView.exe` が使われ、この要求に反する。

> [!IMPORTANT]
> **Linux は例外とする。** Wails v2.15.0 に WebKitGTK のデータ領域を指定する手段が無く、`$XDG_DATA_HOME` / `$XDG_CACHE_HOME` の配下（既定では `~/.local/share` / `~/.cache`）に作られる。これはこの要求が禁じる領域に当たるが、**アプリケーション側に回避手段が存在しない**ため、例外として認める（AR-004）。
>
> 環境変数を書き換えて移す方法は、GTK / GLib 全体に波及するため採らない。実際の位置は E2E-313 で実測し、判明した内容を AR-004 の表へ反映する。

### NFR-034: 依存の健全性 **SHOULD**

- 依存ライブラリの既知脆弱性を CI で検査する（`govulncheck` 等）。
- 埋め込む JavaScript 資産（Mermaid、KaTeX、PlantUML と、`viz-global.js` が同梱する Viz.js / Graphviz / Expat）は、公式配布物のリリース版をそのまま使用し、改変しない。**すべて `vendor.json` に記録する**（BR-042）。**このうちアプリケーション情報ウィンドウの `Bundled` 行に出るのは最上位の 3 件だけ**であり（UI-100）、同梱物の中に含まれるものは `Third-party licenses` に全文とともに現れる（FR-101）。
- リリース時に資産を自動更新する運用（BR-043）を採るため、取得元は公式レジストリまたは公式 CDN に限定し、取得したファイルは改変せずコミットする。取得元が改竄された場合の影響を限定するため、取得元 URL を `vendor.json` に記録し、更新差分がコミットとして可視化される状態を保つ。
- 自動更新はリリース時のみ行い、**利用者の実行環境で更新が起きることはない**（NFR-032）。

### NFR-035: 外部プログラムの起動 **MUST**

MarkView が外部プログラムを起動する経路は、次の 3 つに限る。**これ以外を作らない。**

| 経路 | 起動するもの | 引数 | 根拠 |
| --- | --- | --- | --- |
| 本文中の `http(s)` / `mailto` リンク | OS の既定ハンドラ | URL | [FR-050](02-functional.md) |
| 本文中の画像・その他のファイルへのリンク | OS の既定アプリケーション | 絶対パス | [FR-053](02-functional.md) |
| **エディタで開く** | **利用者が選んだ実行ファイル** | **画面が対象にしているファイルの絶対パス**（`App.target`。下記 2） | [FR-090](02-functional.md) |

3 つ目は、**この製品で唯一「任意の実行ファイルを起動する」経路**である。以下をすべて満たすこと。

1. **起動するプログラムは、利用者が明示的に選んだものだけとする。** 文書の内容・ファイル名・リンク先・ツリーの状態から起動対象が決まる経路を作らない（NFR-030）。
2. **引数は、画面が対象にしているファイルの絶対パス 1 つのみとする**（FR-090, [IMP-190](11-impl-backend.md)）。利用者が編集できるコマンドテンプレート、起動オプション、行番号のいずれも持たない。**「表示中の文書」を渡してはならない。** 状態画面の表示中はそれが前の文書のまま残っており、画面と食い違う。
3. **フロントエンドから実行ファイルのパスを受け取らない。** 選択はプリセットの識別子で伝え、パスは Go 側で解決する（[IMP-300](13-impl-interface.md), [IMP-309](13-impl-interface.md)）。
4. **シェルを経由しない。** 引数は可変長引数として個別に渡す（[IMP-170](11-impl-backend.md)）。
5. **絶対パスでないものを起動しない。** 相対パスやコマンド名を許すと、`$PATH` や作業ディレクトリの内容によって起動されるプログラムが変わる。
6. **MarkView 自身を起動しない。** 実行ファイルのパスを `os.Executable()` と比較して拒否する。許すと、押すたびにウィンドウが増える。

> [!IMPORTANT]
> **設定ファイルにエディタのパスが入ることの意味を認識する。** 従来、設定ファイル（[UI-112](03-ui.md)）には実行に繋がる値が 1 つも含まれていなかった。[UI-116](03-ui.md) を加えた時点で、**設定ファイルを書き換えられれば任意のプログラムが起動する**状態になる。
>
> これを防いでいるのは保存先の権限である（Windows は利用者専用の `%TEMP%`、Linux は `0700` / `0600`。UI-112）。**この権限規定を緩めてはならない。** 上記 5 の絶対パス限定と 6 の自己起動の拒否は、その前提が崩れた場合に備えた二重の防御である。

## 7.5 プライバシー（NFR-040 系）

### NFR-040: 収集しない情報 **MUST**

利用統計、ファイルパス、文書の内容、環境情報のいずれも、外部に送信しない。

### NFR-041: ログ **MUST**

- 通常動作においてログファイルを出力しない。
- 診断が必要な場合に備え、環境変数によって標準エラー出力へのログを有効にしてもよい（**MAY**）。この場合もファイルには出力しない。

### NFR-042: 閲覧の痕跡を残さない **MUST**

- 開いたファイルのパス、ツリールート、表示履歴、検索文字列を、ディスク上のいかなる場所にも保存しない（UI-111）。
- 保存する設定は「表示の快適性に関わる値」に限る（UI-110）。共有 PC で利用しても、直前の利用者が何の文書を読んでいたかが残らないこと。
- **エディタの実行ファイルパス（[UI-116](03-ui.md)）はこの規定の対象外とする。** 「何を読んだか」ではなく「何で開くか」を示す値であり、残っても直前の利用者が読んでいた文書は分からない。保存先と権限の扱いは他の設定と同じとする（UI-112, NFR-035）。

## 7.6 堅牢性（NFR-050 系）

### NFR-050: 異常系での継続動作 **MUST**

- FR-110 に列挙した事象のいずれにおいても、アプリケーションは異常終了しない。
- Markdown の解析・描画で想定外のエラーが発生した場合も、エラーを表示して動作を継続する（FR-111）。
- 不正な UTF-8、極端に深い入れ子、巨大な表、循環するリンク参照といった入力に対して、無限ループやスタック超過を起こさない。
- 設定ファイルが破損していても既定値で起動する（UI-113）。

### NFR-051: ライセンス適合 **MUST**

- 本体は MIT ライセンスで配布する。
- 依存するすべてのソフトウェア（Go モジュール、埋め込み JavaScript / CSS / フォント / アイコン）は、再配布可能なライセンス（MIT、BSD、Apache-2.0、ISC、SIL OFL、**EPL-2.0** 等）のものに限る。GPL 系のライセンスのライブラリを実行ファイルに静的リンクしない。
- すべての依存のライセンス全文をアプリケーション内で表示する（FR-101）。
- **許容するかどうかの判定は機械的に行う。** 埋め込み資産については `vendor.json` の `spdx`（BR-042）を上記の一覧と突き合わせ、一覧に無いものが現れたら**その資産を更新せずリリースを継続する**（BR-043）。

> [!NOTE]
> Linux 版が動的リンクする WebKitGTK は LGPL であり、動的リンクである限り本体のライセンスに影響しない。静的リンクは行わない。

> [!IMPORTANT]
> **EPL-2.0 を許容するのは Graphviz のためである。** PlantUML の Graphviz 系の図（MD-083）を描く `viz-global.js` には、Viz.js（MIT）の他に **Graphviz 本体（EPL-2.0）**と Expat（MIT）が**オブジェクトコードで**含まれている（AR-032）。
>
> EPL-2.0 のコピーレフトは**ファイル単位**であり、改変したファイルに限って同ライセンスでの提供義務が生じる。**改変しなければ他へ伝播せず、MIT での本体配布に影響しない。** その条件は BR-042 の「改変は一切行わない」が既に担保している。**裏を返せば、これは破ってはいけない条件になった。**
>
> 配布に際しては**著作権表示とライセンス全文の保持**が条件となる。これは FR-101 と BR-040 で既に満たす形になっているが、**Viz.js / Graphviz / Expat の全文はどちらのバンドルにも入っていない**ため、`frontend/vendor/plantuml/licenses/` に置いて `vendor.json` から参照する（BR-042）。**他の資産とまったく同じ経路で一覧に載る**（BR-040）。
>
> **一方で `@plantuml/core` の 1.2026.5 以前は GPL-3.0-or-later であり、これは許容しない。** 取得する版のライセンス検査を BR-043 に定めている。

### NFR-052: 配布物の信頼性 **SHOULD**

- 実行ファイル圧縮を行わず、ウイルス対策ソフトによる誤検知の可能性を下げる。
- リリース成果物に SHA-256 チェックサムを添付する（BR-020）。

## 7.7 互換性（NFR-060 系）

### NFR-060: 対応 OS **MUST**

| OS | バージョン | アーキテクチャ |
| --- | --- | --- |
| Windows | 11（21H2 以降） | amd64, arm64 |
| Ubuntu | 24.04 LTS 以降 | amd64, arm64 |

- Windows 10 は動作対象外とする。WebView2 が導入されていれば動作する可能性はあるが、検証は行わない。
- Ubuntu 以外のディストリビューションは、WebKitGTK 4.1 と glibc の要件を満たせば動作しうるが、検証は行わない。

### NFR-061: 表示の互換性 **SHOULD**

Windows の WebView2（Chromium）と Linux の WebKitGTK では描画エンジンが異なるため、細部に差異が生じうる。以下は両環境で同等であること。

- 本文のレイアウト（見出し・表・コードブロック・リストの構造と余白）
- テーマの配色
- Mermaid 図・PlantUML 図・数式の描画結果。**PlantUML は性能の目標を Windows のみに課す（7.1）が、描けることは両環境で同等とする。** Graphviz は WebAssembly で動くため、WebKitGTK で描けなければ不具合として扱う。**描けること自体は FR-024 / MD-083 の MUST であり、本項の SHOULD より上位である**
- コピーボタンの位置と動作

### NFR-062: 表示言語の一貫性 **MUST**

- 表示言語は OS のロケール設定に依存しない。日本語環境・英語環境・その他の環境のいずれでも同一の文言を表示する（UI-024）。
- ツールチップの英日併記は、日本語フォントが導入されていない環境では日本語部分が正しく描画されない可能性がある。この場合も英語部分だけで機能が伝わる語順・書式（英語を先に置く）とすることで、実用上の支障を生じさせない。
- 言語リソースファイル、翻訳の仕組み、ロケール判定処理をいずれも持たない。これにより、翻訳漏れによる表示崩れや、環境ごとの検証パターンの増加を構造的に排除する。

## 7.8 保守性（NFR-070 系）

### NFR-070: コード品質 **SHOULD**

- `gofmt` による整形と `go vet` による静的解析を CI で強制する（BR-052）。
- Markdown の変換、アウトライン抽出、パスの解決、設定の読み書きといった純粋なロジックには、GUI に依存しないユニットテストを用意する。
- フロントエンドのロジックは、機能ごとにファイルを分割し、グローバル変数の使用を最小限にする。

### NFR-071: 仕様との整合 **MUST**

機能を追加・変更する場合、本仕様書の該当箇所を同一の変更で更新する。実装と仕様の乖離を残さない。

### NFR-072: 文書のドッグフーディング **SHOULD**

本仕様書自体を MarkView で表示し、相対リンク・Mermaid 図・表・GitHub Alerts の描画確認に用いる。仕様書が動作確認の題材を兼ねる状態を維持する。
