# 07. 非機能要求

> 索引: [README](README.md) | 前: [06. ビルド・配布](06-build-release.md)

本文書は、性能・資源・安全性・保守性に関する要求と、その測定条件を定義する。

## 7.1 測定の前提条件

特に断りのない限り、以下の条件で測定した値を基準とする。

| 項目 | 条件 |
| --- | --- |
| ハードウェア | 4 コア以上の CPU、8 GB 以上のメモリ、SSD |
| OS | **性能の目標値は Windows 11（amd64）を基準とする**。Ubuntu 24.04（amd64）でも動作を確かめるが、性能の目標は課さない |
| **標準文書** | 約 100 KB、見出し 50 個、コードブロック 30 個、ローカル画像 5 枚を含む Markdown。**Mermaid 図・PlantUML 図・数式は含まない** |
| **図表入り文書** | 標準文書に Mermaid 図 2 個、数式 10 個、**PlantUML 図 2 個（うち 1 個は Graphviz を要する class 図）**を加えたもの |
| **大規模文書** | 約 1 MB の Markdown（Mermaid 図・PlantUML 図・数式は含まない） |
| 測定回数 | 5 回測定し中央値を採る。初回起動（WebView の初期化を含む）と 2 回目以降を区別して記録する |

> [!NOTE]
> 標準文書から Mermaid・PlantUML・数式を外しているのは、遅延ロード（AR-021）の効果を測るためである。これらを含む場合の値は「図表入り文書」で別に測る。

> [!IMPORTANT]
> **性能の基準環境は Windows 11 / amd64（E2E-010 の W1）とする。** Linux は描画エンジンが異なり（WebKitGTK）、同じ目標値を課す根拠が無い。**Linux では性能を測らず、目標も課さない。**
>
> **ただし「描けること」は別である。** FR-024 と MD-083 は **MUST** であり、対象環境を限定していない。Linux で描けない記法があれば、それは性能ではなく**機能の不具合**である（NFR-061）。

## 7.2 性能（NFR-010 系）

### NFR-010: 起動時間 **MUST**

| 条件 | 目標 |
| --- | --- |
| 標準文書を引数に指定して起動し、本文が描画されるまで（2 回目以降） | **1.0 秒以内** |
| 同上（OS 起動後の初回。WebView の初期化を含む） | 2.5 秒以内 |
| 引数なしで起動し、操作案内が表示されるまで | 0.8 秒以内 |

- 上表の計測終点は**本文テキストの描画が完了した時点**とする。Mermaid 図・PlantUML 図・数式は本文表示より後に非同期で描画されるため（NFR-012）、その完了時刻は含めない。
- 図表入り文書を指定して起動した場合も、上表の値を満たすこと。Mermaid・KaTeX・PlantUML の読み込みが本文描画の完了を妨げてはならない。**PlantUML の資産は 5 MiB を超え、Graphviz 系の図は 1 枚 1 秒近くかかる（NFR-011）。本文の表示をこれに待たせてはならない。**
- 起動時にディレクトリツリーの再帰走査を行わないこと（FR-032）。
- Mermaid・KaTeX・PlantUML は、それを含む文書を開いた場合を除いて読み込まないこと（AR-021）。標準文書はこれらを含まないため、読み込みが発生してはならない。
- **上表の目標値は 7.1 の基準環境（Windows 11 / amd64）に対するものである。** この節の以降の目標値（NFR-011、NFR-020）も同じである。

### NFR-011: 変換・描画性能 **MUST**

| 処理 | 目標 |
| --- | --- |
| 標準文書の Markdown → HTML 変換（Go 側） | 50 ms 以内 |
| 標準文書の表示切り替え（クリックから描画完了まで） | 300 ms 以内 |
| 大規模文書（1 MB）の表示 | 2.0 秒以内 |
| 図表入り文書の Mermaid 図の描画完了（本文表示後、非同期） | 1.5 秒以内 |
| **PlantUML 図 1 枚の描画完了**（Graphviz を要さない図。sequence / activity / mindmap 等） | **100 ms 以内** |
| **PlantUML 図 1 枚の描画完了**（Graphviz を要する図。class / component / state 等） | **1.0 秒以内** |
| ファイル更新検知から再描画完了まで（標準文書） | 500 ms 以内 |
| 文書内検索の初回ハイライト（標準文書） | 150 ms 以内 |

> [!NOTE]
> **PlantUML だけ「1 枚あたり」で目標を置いている。** Graphviz を要する図は 1 枚 400〜700 ms かかり、枚数に比例して伸びる（実測: 5 枚 2,136 ms、10 枚 7,104 ms）。文書単位の秒数にすると、**測定用文書に何枚入れるかで目標値が動き**、文書の定義を変えるたびに秒数を決め直すことになる。枚数は文書側の都合であり、目標に織り込まない。
>
> **文書全体の描画が何秒で終わるかは目標にしない。** 代わりに、**描画中も UI が固まらないこと**（NFR-012）で利用者への影響を押さえる。**ただし、PlantUML の処理系は図 1 枚の計算の間メインスレッドを止める**（NFR-012 の例外。4.96.0 で実測して改めた。[BUG-030](../bugs/2026-11-11-bug-030-plantuml-size-limit.md)）。4.95.0 までは「細切れに実行されるため、400 ms かかる図でもメインスレッドの停止は 4 ms 以下」としていたが、**Graphviz を使わない図（シーケンス・アクティビティ・JSON など）は計算の全体が 1 つのタスク**であり、v1.0.0 の資産から成り立っていなかった（Graphviz を使う図は一部が細切れになる）。
>
> **大きな図の時間**（4.96.0。利用者の判断）: 利用者は、**図 1 枚が出るまでが 5 秒を超えると止まったと感じる**。開発機（7.1 の基準環境より速い）で 3.5 秒に届く大きさは、JSON・YAML が約 24,000 px、縦に長いアクティビティ図が約 52,000 px、シーケンス図が約 470,000 px である（実測。BUG-030 の 5.2）。**上限（MD-083）では縛れない**——処理系は配置を計算し終えてから大きさを確かめるため、上限を下げても待ち時間は減らない。上限より小さくても、これより大きな JSON などは 5 秒を超えて画面が止まりうる。
>
> 将来、並ぶ図の枚数が問題になる場合は、**見えている図から描く**（`IntersectionObserver`）併用を検討する。

### NFR-012: 操作の応答性 **MUST**

- スクロールは 60 fps を維持し、視認できるカクつきを生じないこと。
- ペイン幅のドラッグ操作、テーマ切り替え、ペインの表示・非表示の切り替えは、いずれも 100 ms 以内に画面へ反映されること。
- Mermaid 図・PlantUML 図の描画中も、UI 操作（スクロール、ボタン操作）が阻害されないこと。図の描画は本文表示より後に非同期で完了してよい。**PlantUML は 1 枚に 1 秒近くかかりうるため（NFR-011）、この条件がとりわけ重い。**
  - **例外: PlantUML の処理系が図 1 枚を計算している間は、操作が効かない**（4.96.0。[BUG-030](../bugs/2026-11-11-bug-030-plantuml-size-limit.md)）。処理系が計算の間メインスレッドを止めるためであり、処理系を改変することも（BR-042）、別スレッドへ移すことも（処理系は出力先を要素の id で受け取り、`document` へ直接書く。IMP-233）できない。**止まるのは図 1 枚ずつであり、図と図の間では操作が効く**（図は逐次描く。IMP-233）。止まる時間は図の大きさと種類で決まる（NFR-011 の注記）
- 表の並べ替え（FR-130）、右クリックメニューの表示（FR-063）、拡大画面の拡大・縮小（FR-122）は、いずれも 100 ms 以内に画面へ反映されること。**拡大画面のドラッグによる移動は、スクロールと同じく 60 fps を維持すること。**
- **編集モードの操作（FR-141 のチェックボックスの反転、FR-142 のセルの確定、FR-145 のコードブロックと図の確定、FR-146 / FR-147 の修飾）は、見た目を 100 ms 以内に画面へ反映すること。** ファイルから読み直した再描画は FR-014 の経路で行い、その時間は NFR-011 の「ファイル更新検知から再描画完了まで」に従う。**見た目の反映を、書き込みや再描画の完了に待たせない。** **ただし取り消し線を外す操作は例外とし、書き込みの後の再描画で外れて見えればよい**（祖先の `<del>` が引いた線は子孫の要素から消せない。FR-146。4.81.0。利用者の判断）。
- 100 ms を超える処理を行う場合、処理中であることを利用者に示すこと（**SHOULD**）。
- **戻る・進むのボタン（FR-051）、ファイルツリーの右クリックメニューの表示（FR-036）、フィルターの枚の開閉（FR-037）は、100 ms 以内に画面へ反映すること**（4.73.0）。フィルターの切り替えに伴うツリーの読み直しは、FR-035 の読み直しと同じ扱いとする。

### NFR-013: 遅延ロードの徹底 **MUST**

- Mermaid 記法を含まない文書を表示する限り、`mermaid.min.js` は評価されないこと。
- 数式を含まない文書を表示する限り、KaTeX は評価されないこと。
- **PlantUML 記法を含まない文書を表示する限り、`plantuml.js` と `viz-global.js` は評価されないこと。**
- この 3 点は、起動時のメモリ使用量と表示完了時間に直接影響するため、実装上の必須条件とする。**中でも PlantUML は資産が最も大きい（5.09 MiB。Mermaid と KaTeX の合計を上回る）。**
- **「記法を含む」は、Go 側が変換で出した図のブロック（鍵の合う目印を持つもの。IMP-120）があることをいう。** 生 HTML で図のブロックを偽装しても、資産を評価する契機にならないこと（MD-082, MD-085, NFR-030）。

## 7.3 資源使用量（NFR-020 系）

### NFR-020: メモリ **MUST**

WebView のプロセスを含むアプリケーション全体の常駐サイズ（RSS / ワーキングセット）について、以下を目標とする。

| 状態 | 目標 |
| --- | --- |
| 起動直後（操作案内の表示のみ） | 180 MB 以下 |
| 標準文書の表示中 | 250 MB 以下 |
| 図表入り文書の表示中（Mermaid・KaTeX・**PlantUML** の読み込みを含む） | **420 MB 以下** |
| Go プロセス側のみ（WebView を除く） | 60 MB 以下 |

- 文書を 20 回連続で切り替えた後も、メモリ使用量が単調増加しないこと（リークがないこと）。
- ファイル監視のウォッチャは常に 1 つ以下であること（AR-070）。
- ファイルツリーはディレクトリを展開した分だけメモリを消費する。ツリールート以下の全階層を保持してはならない（FR-032）。
- **編集の取り消し履歴は、文書の大きさに比例して増やさない**（FR-144）。**例外として、コードブロックと図の書き換え（FR-145）では 1 回の記録がそのブロック（Mermaid ファイルではファイル全体）の大きさになり、上限は設けない**（4.73.0。利用者の判断）。巨大なブロックを何度も書き換えると、Go 側の目標を超えうることを受け入れる。

> [!NOTE]
> WebView は Chromium / WebKit ベースであり、それ自体が 100 MB 前後を占める。本アプリで制御可能なのは主に Go 側と描画内容であるため、目標値はこのベースラインを前提としている。
>
> 図表入り文書を 350 MB から 420 MB へ引き上げたのは PlantUML の分である。JS ヒープの実測は読み込み後 16 MB、描画後 39 MB、Graphviz 系を 10 枚描いて 53 MB であった。**遅延ロード（NFR-013）が効いている限り、標準文書と起動直後の目標は変わらない。**

### NFR-021: ファイルサイズ **SHOULD**

| 対象 | 目標 |
| --- | --- |
| 実行ファイル単体（Windows / amd64） | **30 MB 以下** |
| 実行ファイル単体（Linux / amd64） | 30 MB 以下 |
| 配布アーカイブ（zip / tar.gz） | 12 MB 以下 |

- 上表は**目標値**であり、超過をもってリリースを中止する基準ではない。サイズは CI で常に計測して記録し、超過時は警告として可視化する（BR-060）。
- 目標値を SHOULD としているのは、埋め込み資産（Mermaid / KaTeX / PlantUML）がリリース時に自動更新される運用（BR-043）を採っており、外部の資産サイズの増加によってリリースが機械的に止まる事態を避けるためである。ただし「小さく保つ」こと自体は本アプリの中心的な価値（[01-overview](01-overview.md) 1.3.2）であり、超過した状態を放置してはならない。
- 依存ライブラリや埋め込み資産の追加は、サイズへの寄与を評価したうえで判断する。
- サイズ削減のために実行ファイル圧縮（UPX 等）を用いてはならない（BR-010, NFR-052）。この点は **MUST** とする。

> [!IMPORTANT]
> **25 MB から 30 MB へ引き上げたのは PlantUML を同梱するためである。** 資産そのものは **5.09 MiB**（`plantuml.js` 約 3.7 MB + `viz-global.js` 約 1.4 MB。AR-020）だが、**実行ファイルの増分は 5.16 MB** である（同梱前の実測 **20.86 MB**、同梱後 **26.02 MB**。2026-09-03）。差は埋め込みに伴う付随分である。**残りは 3.98 MB。**
>
> 数値はすべて 2 進接頭辞である（`1 MB = 1,048,576 バイト`。[README](README.md) の「単位の表記」）。
>
> Mermaid・KaTeX・PlantUML はいずれも BR-043 で自動更新されるため、**上流が太るだけで目標を割りうる**。BR-060 の計測と警告が実質的な歯止めになる。**サイズを戻すために `viz-global.js` を圧縮・結合することはできない**（BR-042。EPL-2.0 の条件に触れる）。
>
> 配布アーカイブは目標を変えない。同梱後の**実測は 9.52 MB**であり、12 MB に収まる（2026-09-03）。

### NFR-022: CPU 使用率 **SHOULD**

- 文書を表示して操作していない状態（アイドル時）の CPU 使用率は 1 % 未満であること。ポーリングによるファイル監視やアニメーションの常時実行を行わない。
- 常駐プロセス、バックグラウンドでの定期処理は持たない。

## 7.4 安全性（NFR-030 系）

MarkView は「第三者から受け取った Markdown ファイルを開く」ことを前提とするため、文書は信頼できない入力として扱う。

### NFR-030: 文書由来のコード実行の禁止 **MUST**

- Markdown 中の `<script>` およびイベントハンドラ属性は、サニタイズにより確実に除去される（MD-072）。
- Mermaid は `securityLevel: strict` 相当で動作させ、図の定義からスクリプトが実行されないようにする（MD-081）。
- KaTeX は信頼できない入力を前提とした設定（`trust: false` 相当）で動作させる。
- **PlantUML は、外部を取り込むプリプロセッサ指令を含むブロックを Go 側で描画対象から外す**（MD-084, IMP-119）。PlantUML には Mermaid の `securityLevel` に相当する設定が無く、**入力側で制限する以外の手段が無い**。
- WebView 内で実行される JavaScript は、実行ファイルに埋め込まれた自前の資産に限る。文書から供給されたコードを評価してはならない。
- **ファイルへの書き込みは、編集モード（FR-140）の中で利用者が明示的に操作したときだけ起きる。** 文書の内容（生 HTML・リンク・図の定義）を契機に書き込みが起きる経路を作らない。**文書の書き手が、書き換えの対象を偽装できる経路も作らない**——生 HTML の `input` をタスクリストの項目に見せかける、生 HTML の表を GFM の表に見せかける、といったことで対象を変えられてはならない（FR-141, FR-142, MD-072）。
- **文書の書き手が、MarkView の後処理の対象を生 HTML で偽装できてはならない。** サニタイズは属性の形しか見られず、GFM に由来する要素と、同じ属性を書いた生 HTML の要素を見分けられない（MD-072 の NOTE）。次のものは、**変換のたびに作る鍵と目印を照合して**、Go 側が変換で出した要素だけを対象にする（IMP-120）。

| 対象 | 偽装されると起きること | 根拠 |
| --- | --- | --- |
| 書き換えの対象（タスク・表のセル） | 利用者が意図しない箇所を書き換える | FR-141, FR-142 |
| 並べ替えの対象（GFM の表） | 生 HTML の表の行が並び替わる | FR-130 |
| 書かれたとおりのリンク先（`Copy link address`） | 見えている遷移先と違う文字列がコピーされる | FR-063 |
| **図として描画する原文**（Mermaid / PlantUML のブロック） | **取り込み指令の検査（MD-084）を通らない原文が処理系へ渡る。** 図を含まない文書で資産が読み込まれる（NFR-013） | MD-082, MD-084, MD-085 |
| **コピーボタンがコピーする原文**（図のブロックの `data-source`） | **画面に見えているコードと違う文字列がコピーされる**（`npm install` と見せて別のコマンドを貼らせる） | FR-060, FR-061 |
| **書き換えるコードブロックと図**（4.73.0） | 利用者が意図しないブロックを書き換える | FR-145 |
| **修飾するブロック**（4.73.0） | 選んだのと違う文字に修飾が付く | FR-146, FR-147 |

**偽装されても害の無いもの**（数式の `.math-*`、Alerts と脚注のクラス、コピーボタンそのもの）は照合しない。数式は書き手がそもそも書けるものであり、偽装で新しくできることが無い。**コピーボタンは、鍵の合わないブロックでは画面に見えているコードの文字列をコピーする**ため、見えている内容とコピーされる内容が食い違わない（[BUG-014](../bugs/2026-09-14-bug-014-diagram-marker-spoofing.md)）。

### NFR-031: ファイルアクセスの制限 **MUST**

- 内部アセットサーバがローカルファイルを配信する経路は、画像として扱える拡張子に限定する（AR-041）。
- パスは正規化・シンボリックリンク解決を行ったうえで検査し、意図しないファイルの読み出しを防ぐ。
- アプリケーションはファイルの**読み取りのみ**を行う。次の 3 つを除き、いかなるファイルも作成・変更・削除しない。**表示中のファイルを書き換える経路は、編集モードの書き込み（FR-141〜FR-147）だけとする。**

| 例外 | 書く主体 | 位置 |
| --- | --- | --- |
| 設定ファイル | アプリケーション | UI-112 |
| WebView のユーザデータ領域 | **WebView ランタイム**（WebView2 / WebKitGTK） | AR-004 |
| **表示中の文字のファイル**（Markdown・図のファイル。[1.7](01-overview.md)）と、**置き換えのために同じディレクトリへ作る一時ファイル**（成功しても失敗しても残さない） | アプリケーション。**編集モードの中で、利用者が操作したときだけ** | 表示中のファイルの実体があるディレクトリ。FR-140〜FR-147。書き込みの規則は FR-143 |

  2 つ目はアプリケーションが直接書くものではないが、**位置を決めるのはアプリケーション側の責任**であるため例外として明記する（AR-004）。数十 MB 規模になりうる。

  3 つ目で書き込むのは、**表示中の 1 ファイルの、書き換える箇所だけ**である（FR-143）。置き換えのための一時ファイルも、終わった後に残さない。**それ以外のファイル（同じディレクトリの他の文書、画像、リンク先）を書き換えない。**

> [!NOTE]
> **これは「MarkView 自身が何を書くか」の規定である。** 外部エディタで開く機能（[FR-090](02-functional.md)）は、利用者が選んだ別のプログラムへ絶対パスを渡すものであり、そこで書き込みが起きるとすれば責任はエディタ側にある。既定ブラウザに URL を渡した先で何が起きるかを MarkView が制御しないのと同じである（NFR-035）。
>
> **4.38.0 までは「MarkView が表示中の Markdown ファイルを書き換える経路は存在しない」としていた。** 4.39.0 で編集モード（FR-140）を加え、その経路を**構造を変えない 2 種類の書き換え**に限って設けた。**4.73.0 で 4 種類に広げた**（コードブロックと図の中身、選んだ文字の取り消し線と文字色。どれも文書のブロックの数と種類を変えず、書く内容を解き直して確かめる。FR-143）。書き換える先は今と同じく表示中の 1 ファイルだけであり、**画像ファイル（FR-027）は書き換えない。** 範囲を広げるときは、この表と 2.14 の IMPORTANT（FR-140 の前）を同時に改訂する。

### NFR-032: ネットワーク **MUST**

- アプリケーション自身は、起動時・実行中を通じて外部へ通信しない。更新確認、利用統計の送信、クラッシュレポートの送信のいずれも行わない。
- 発生しうる外部通信は、表示中の文書が `http(s)` 画像を参照している場合の画像取得のみである（MD-071）。
- **PlantUML の取り込み指令（`!include` / `!includeurl` / `!includesub` / `!import` / `from` を伴う `!theme`）を含むブロックは、Go 側で描画対象から外す**（MD-084, IMP-119）。**生 HTML で PlantUML のブロックを偽装して、この検査を迂回できてはならない**（フロントエンドは鍵の合うブロックだけを描く。MD-084, NFR-030）。

> [!NOTE]
> **同梱する版は、これらの指令で実際には通信しないことを実測で確かめている**（記録用のローカルサーバへのアクセス 0 件）。それでも Go 側で塞ぐのは次の 2 つのためである。
>
> 1. `XMLHttpRequest` の経路がバンドルに残っており、**将来の版で有効化される余地がある**。資産は BR-043 で自動更新されるため、こちらが気づかないまま振る舞いが変わりうる。
> 2. **どうせ描けない**（標準ライブラリも URL も失敗する。MD-083）。PlantUML の読みにくいエラー図を出すより、こちらで理由を書いたほうが親切である（FR-110）。
- 内部アセットサーバは外部ネットワークインターフェースにバインドしない（AR-041）。

### NFR-033: 権限 **MUST**

- 管理者権限・root 権限を必要としない。
- レジストリ、システムディレクトリ、ユーザのホームディレクトリ配下の設定領域（`%APPDATA%`, `~/.config` 等）に書き込まない。**アプリケーションが自分のために書くもの**（設定・WebView のデータ）は、テンポラリディレクトリ内に限る（UI-112, AR-004）。
- **例外は、編集モードで利用者が書き換えた文字のファイル（Markdown・図のファイル）**（FR-140〜FR-147）である。書き込むのは表示中のファイルそのものであり、その場所は利用者が開いたファイルの場所で決まる。置き換えのための一時ファイルは**同じディレクトリ**に作り（リネームで置き換えるため。FR-143）、**終わった後に残さない**（NFR-031）。
- **WebView のユーザデータ領域も、位置を指定できる OS ではテンポラリディレクトリ配下へ寄せる**（AR-004）。Windows で指定を怠ると `%APPDATA%\MarkView.exe` が使われ、この要求に反する。

> [!IMPORTANT]
> **Linux は例外とする。** Wails v2.15.0 に WebKitGTK のデータ領域を指定する手段が無く、`$XDG_DATA_HOME` / `$XDG_CACHE_HOME` の配下（既定では `~/.local/share` / `~/.cache`）に作られる。これはこの要求が禁じる領域に当たるが、**アプリケーション側に回避手段が存在しない**ため、例外として認める（AR-004）。
>
> 環境変数を書き換えて移す方法は、GTK / GLib 全体に波及するため採らない。実際の位置は E2E-313 で実測し、判明した内容を AR-004 の表へ反映する（4.71.0 で `v1.1.0-rc.2` の E2E-313 の手順 8 の記録から反映した。AR-004）。

### NFR-034: 依存の健全性 **SHOULD**

- 依存ライブラリと標準ライブラリの既知脆弱性を CI で検査する（`govulncheck`。BR-052。**Linux と Windows の両方で、見つかれば失敗**）。**v1.0.0 の CI には入っていなかった**（2026-09-14 に確認。4.62.0 で足した）。**標準ライブラリの脆弱性は、ビルドに使う Go の版で決まる**——`go.mod` に `toolchain` が無く Go 1.25.0 でビルドしていたため、足した時点で 33 件が見つかった（BR-001）。
- 埋め込む JavaScript 資産（Mermaid、KaTeX、PlantUML と、`viz-global.js` が同梱する Viz.js / Graphviz / Expat）は、公式配布物のリリース版をそのまま使用し、改変しない。**すべて `vendor.json` に記録する**（BR-042）。**このうちアプリケーション情報ウィンドウの `Bundled` 行に出るのは最上位の 3 件だけ**であり（UI-100）、同梱物の中に含まれるものは `Third-party licenses` に全文とともに現れる（FR-101）。
- リリース時に資産を自動更新する運用（BR-043）を採るため、取得元は公式レジストリまたは公式 CDN に限定し、取得したファイルは改変せずコミットする。取得元が改竄された場合の影響を限定するため、取得元 URL を `vendor.json` に記録し、更新差分がコミットとして可視化される状態を保つ。
- 自動更新はリリース時のみ行い、**利用者の実行環境で更新が起きることはない**（NFR-032）。

### NFR-035: 外部プログラムの起動 **MUST**

MarkView が外部プログラムを起動する経路は、次の 4 つに限る（4.73.0 で 3 つ目を足した）。**これ以外を作らない。**

| 経路 | 起動するもの | 引数 | 根拠 |
| --- | --- | --- | --- |
| 本文中の `http(s)` / `mailto` リンク | OS の既定ハンドラ | URL | [FR-050](02-functional.md) |
| 本文中の、開けるファイル以外のファイルへのリンク | OS の既定アプリケーション | 絶対パス | [FR-050](02-functional.md) |
| **ファイルツリーで選んだディレクトリ**（`Open in file manager` / `Open containing folder`） | **OS の既定のファイルマネージャ**（2 つ目と同じ既定のアプリケーションの経路に、ディレクトリを渡す） | **ツリーに出ている（ツリールートの中か、ツリールートそのもの）と確かめたディレクトリの絶対パス**（下記。FR-036） | [FR-036](02-functional.md) |
| **エディタで開く** | **利用者が選んだ実行ファイル** | **画面が対象にしているファイルの絶対パス**（`App.target`）、**またはファイルツリーで選び、確かめた文字のファイルの絶対パス**（下記 2） | [FR-090](02-functional.md), [FR-036](02-functional.md) |

**OS の設定の問い合わせは、この表に含めない。** Linux で OS のテーマを読むために起動する `gsettings`（IMP-175）は、**コマンドも引数も固定**であり、文書・ファイル名・リンク先・利用者の入力で起動するものも引数も変わらない。シェルを経由せず、応答を待つ上限を持つ（4.81.0 で例外として書いた。利用者の判断）。**ここに当たる起動を足すときは、この条件を満たすものに限り、本項を改める。**

**4.72.0 までは、2 つ目の経路に画像ファイルへのリンクも入っていた。** 4.73.0 で画像ファイルを MarkView で開くようにした（FR-053）ため、外した。

**3 つ目（ディレクトリ）は、Go 側でディレクトリであることを確かめてから渡す**（FR-036）。既定のアプリケーションの経路はファイルの種類で動きを変え、**実行ファイルを渡せば実行する**ためである。あわせて、ツリールートの中にあること・ツリーに表示する規則に当てはまることを確かめる。確かめてから起動するまでの間にディレクトリがファイルへすり替わる余地は残るが、利用者自身のディスクの上の操作であり、許容する（NFR-030 が想定するのは文書の書き手である）。名前の変わったディレクトリ（空白・`,`・`&`・`.exe` で終わる名前・日本語・UNC パスなど）でも正しいディレクトリが開くことを、W1 / L1 の実機で確かめた（2026-11-08）。

4 つ目は、**この製品で唯一「任意の実行ファイルを起動する」経路**である。以下をすべて満たすこと。

1. **起動するプログラムは、利用者が明示的に選んだものだけとする。** 文書の内容・ファイル名・リンク先・ツリーの状態から起動対象が決まる経路を作らない（NFR-030）。
2. **引数は、絶対パス 1 つのみとする。渡すのは、エディタ選択ウィンドウを開いた時点の画面の対象**（ツールバーと `Ctrl+E`。FR-090, [IMP-190](11-impl-backend.md)）**か、ファイルツリーで選び確かめた文字のファイル**（FR-036）である。利用者が編集できるコマンドテンプレート、起動オプション、行番号のいずれも持たない。**「表示中の文書」を渡してはならない。** 状態画面の表示中はそれが前の文書のまま残っており、画面と食い違う。**ファイルツリーの右クリックメニュー（FR-036。4.73.0）から開く場合は、ツリーで選んだファイルの絶対パス 1 つとする。** そのパスは、Go 側でツリールートの中の文字のファイルであることを確かめてから控え、エディタ選択ウィンドウで `Open` を選んだときに渡す。**フロントエンドから受け取ったパスを確かめずに渡さない。**
3. **フロントエンドから実行ファイルのパスを受け取らない。** 選択はプリセットの識別子で伝え、パスは Go 側で解決する（[IMP-300](13-impl-interface.md), [IMP-309](13-impl-interface.md)）。
4. **シェルを経由しない。** 引数は可変長引数として個別に渡す（[IMP-170](11-impl-backend.md)）。
5. **絶対パスでないものを起動しない。** 相対パスやコマンド名を許すと、`$PATH` や作業ディレクトリの内容によって起動されるプログラムが変わる。
6. **MarkView 自身を起動しない。** 実行ファイルのパスを `os.Executable()` と比較して拒否する。許すと、押すたびにウィンドウが増える。

> [!IMPORTANT]
> **設定ファイルにエディタのパスが入ることの意味を認識する。** 従来、設定ファイル（[UI-112](03-ui.md)）には実行に繋がる値が 1 つも含まれていなかった。[UI-116](03-ui.md) を加えた時点で、**設定ファイルを書き換えられれば任意のプログラムが起動する**状態になる。
>
> これを防いでいるのは保存先の権限である（Windows は利用者専用の `%TEMP%`、Linux は `0700` / `0600`。UI-112）。**この権限規定を緩めてはならない。** 上記 5 の絶対パス限定と 6 の自己起動の拒否は、その前提が崩れた場合に備えた二重の防御である。

## 7.5 プライバシー（NFR-040 系）

### NFR-040: 収集しない情報 **MUST**

利用統計、ファイルパス、文書の内容、環境情報のいずれも、外部に送信しない。

### NFR-041: ログ **MUST**

- 通常動作においてログファイルを出力しない。
- 診断が必要な場合に備え、環境変数によって標準エラー出力へのログを有効にしてもよい（**MAY**）。この場合もファイルには出力しない。

### NFR-042: 閲覧の痕跡を残さない **MUST**

- 開いたファイルのパス、ツリールート、表示履歴、検索文字列を、ディスク上のいかなる場所にも保存しない（UI-111）。
- 保存する設定は「表示の快適性に関わる値」に限る（UI-110）。共有 PC で利用しても、直前の利用者が何の文書を読んでいたかが残らないこと。
- **編集の取り消し履歴（FR-144）は文書の断片を含むため、メモリ上だけに持つ。** 編集モードの状態・表の並べ替え・原寸表示・拡大画面の状態も保存しない（UI-111）。
- **編集モードで書き込んだファイルは、内容と更新日時が変わる。** これは利用者が明示的に書き換えた結果であり、本要求が禁じる「閲覧の痕跡」には当たらない。**書き込まなかったファイル（読んだだけのファイル）には、何の変化も残さない**——編集モードに入っただけでは書き込まず（FR-140）、内容が変わらない確定・修飾では書き込まない（FR-142, FR-143）。
- **WebView が自身のデータ領域（AR-004）に持つリモートの資源のキャッシュは、この規定の対象外とする。** 文書に `http(s)` の画像（MD-071）があると、WebView はその応答をキャッシュに書くことがあり、そこから直前に読まれた文書の手掛かり（画像の URL）が分かりうる。**MarkView 自身は、ファイルのパスも文書の内容もキャッシュへ書かない。** ローカル画像は `Cache-Control: no-store` で配信し、キャッシュさせない（IMP-162）。
  - 対象外とする理由: **Wails v2.15.0 には WebView のキャッシュを止める手段（起動引数など）が無く**、データ領域は複数起動（UI-115）で共有されるため、**終了時に安全に消すこともできない**（他のインスタンスが使っており、WebView2 はファイルを開いたままにする）。Linux ではデータ領域の位置も指定できない（AR-004）。
  - 利用者向け文書（`docs/settings.md` / `docs/troubleshooting.md`）に、消し方を載せる——Windows は `%TEMP%\MarkView` を丸ごと、Linux は `~/.cache` と `~/.local/share` の下の WebKitGTK が作ったディレクトリ（AR-004）。**MarkView を終了してから消す。**
- **エディタの実行ファイルパス（[UI-116](03-ui.md)）はこの規定の対象外とする。** 「何を読んだか」ではなく「何で開くか」を示す値であり、残っても直前の利用者が読んでいた文書は分からない。保存先と権限の扱いは他の設定と同じとする（UI-112, NFR-035）。
- **ツリーのフィルター（FR-037。4.73.0）として保存するのは、図と画像をツリーに表示するかの 2 つの真偽値だけ**であり、パス・ツリールート・展開の状態は保存しない。**編集欄の入力**（FR-142, FR-145）も保存しない（UI-111）。

## 7.6 堅牢性（NFR-050 系）

### NFR-050: 異常系での継続動作 **MUST**

- FR-110 に列挙した事象のいずれにおいても、アプリケーションは異常終了しない。
- Markdown の解析・描画で想定外のエラーが発生した場合も、エラーを表示して動作を継続する（FR-111）。
- 不正な UTF-8、極端に深い入れ子、巨大な表、循環するリンク参照といった入力に対して、無限ループやスタック超過を起こさない。
- 設定ファイルが破損していても既定値で起動する（UI-113）。

### NFR-051: ライセンス適合 **MUST**

- 本体は MIT ライセンスで配布する。
- 依存するすべてのソフトウェア（Go モジュール、埋め込み JavaScript / CSS / フォント / アイコン）は、再配布可能なライセンス（MIT、BSD、Apache-2.0、ISC、SIL OFL、**EPL-2.0** 等）のものに限る。GPL 系のライセンスのライブラリを実行ファイルに静的リンクしない。
- すべての依存のライセンス全文をアプリケーション内で表示する（FR-101）。
- **許容するかどうかの判定は機械的に行う。** 埋め込み資産については `vendor.json` の `spdx`（BR-042）を、**SPDX の識別子の閉じた一覧 `MIT` / `BSD-2-Clause` / `BSD-3-Clause` / `Apache-2.0` / `ISC` / `OFL-1.1` / `EPL-2.0`**（大文字小文字を区別しない。UT-818 のケース 3。4.81.0 で書き写した）と突き合わせ、一覧に無いものが現れたら**その資産を更新せず、リリースを中止する**（BR-043 の `license-rejected`。上流のライセンスの変更は人が判断する）。

> [!NOTE]
> Linux 版が動的リンクする WebKitGTK は LGPL であり、動的リンクである限り本体のライセンスに影響しない。静的リンクは行わない。

> [!IMPORTANT]
> **EPL-2.0 を許容するのは Graphviz のためである。** PlantUML の Graphviz 系の図（MD-083）を描く `viz-global.js` には、Viz.js（MIT）の他に **Graphviz 本体（EPL-2.0）**と Expat（MIT）が**オブジェクトコードで**含まれている（AR-032）。
>
> EPL-2.0 のコピーレフトは**ファイル単位**であり、改変したファイルに限って同ライセンスでの提供義務が生じる。**改変しなければ他へ伝播せず、MIT での本体配布に影響しない。** その条件は BR-042 の「改変は一切行わない」が既に担保している。**裏を返せば、これは破ってはいけない条件になった。**
>
> 配布に際しては**著作権表示とライセンス全文の保持**が条件となる。これは FR-101 と BR-040 で既に満たす形になっているが、**Viz.js / Graphviz / Expat の全文はどちらのバンドルにも入っていない**ため、`frontend/vendor/plantuml/licenses/` に置いて `vendor.json` から参照する（BR-042）。**他の資産とまったく同じ経路で一覧に載る**（BR-040）。
>
> **一方で `@plantuml/core` の 1.2026.5 以前は GPL-3.0-or-later であり、これは許容しない。** 取得する版のライセンス検査を BR-043 に定めている。

### NFR-052: 配布物の信頼性 **SHOULD**

- 実行ファイル圧縮を行わず、ウイルス対策ソフトによる誤検知の可能性を下げる。
- リリース成果物に SHA-256 チェックサムを添付する（BR-020）。

## 7.7 互換性（NFR-060 系）

### NFR-060: 対応 OS **MUST**

| OS | バージョン | アーキテクチャ |
| --- | --- | --- |
| Windows | 11（21H2 以降） | amd64, arm64 |
| Ubuntu | 24.04 LTS 以降 | amd64, arm64 |

- Windows 10 は動作対象外とする。WebView2 が導入されていれば動作する可能性はあるが、検証は行わない。
- Ubuntu 以外のディストリビューションは、WebKitGTK 4.1 と glibc の要件を満たせば動作しうるが、検証は行わない。

### NFR-061: 表示の互換性 **SHOULD**

Windows の WebView2（Chromium）と Linux の WebKitGTK では描画エンジンが異なるため、細部に差異が生じうる。以下は両環境で同等であること。

- 本文のレイアウト（見出し・表・コードブロック・リストの構造と余白）
- テーマの配色
- Mermaid 図・PlantUML 図・数式の描画結果。**PlantUML は性能の目標を Windows のみに課す（7.1）が、描けることは両環境で同等とする。** Graphviz は WebAssembly で動くため、WebKitGTK で描けなければ不具合として扱う。**描けること自体は FR-024 / MD-083 の MUST であり、本項の SHOULD より上位である**
- コピーボタンの位置と動作
- **読み込みに失敗した画像のプレースホルダと代替テキスト**（FR-022, DSP-123, IMP-226）。**枠が出ることだけでなく、`alt` の文字列が読めることまでを同等とする**
- **右クリックメニュー（FR-063）。** WebView の標準メニューが両環境とも出ないこと、`Copy` で格納される内容が `Ctrl+C` と同じであること。**標準メニューを出さないことは AR-060 の MUST であり、本項の SHOULD より上位である**
- **拡大画面（FR-122）。** 図が輪郭をぼやけさせずに拡大されること、ホイール・ドラッグ・キーの操作が同じように効くこと
- **画像ファイルの表示（FR-027）。** 固有の大きさを持たない SVG を、読み込みの失敗と取り違えず、拡大画面でも中身を見せること（WebView が `naturalWidth` を 0 と返す。IMP-226, IMP-228。4.81.0 で書き足した）
- **編集モードの操作（FR-141, FR-142, FR-145〜FR-147）。** チェックボックスのクリックと、セル・コードブロック・図のダブルクリックが同じように効くこと。**コードブロックの編集欄の `Tab` / `Ctrl+Enter` / IME と、修飾の選択範囲の扱い（L1 はフォーカスの移動で選択を解除する。[BUG-019](../bugs/2026-09-21-bug-019-context-menu-copy-webkitgtk.md)）、見える文字の数え方（BR-054 の照合はエンジン差を見ない）も、両エンジンで確かめる**（4.73.0）。**マウスのサイドボタン（FR-051）、ファイルツリーの右クリックメニュー（FR-036）、ディレクトリをファイルマネージャで開く操作も同じ**（L1 でサイドボタンが届くかは未確認であり、SHOULD に留めている）。**書き込まれるバイト列は Go 側で決まり、エンジンに依存しない**

> [!IMPORTANT]
> **描画エンジンの既定の振る舞いに、要求の充足を委ねない。**
>
> 「ブラウザが既定でこう描くから」を根拠に実装を省くと、**その既定が違う環境で要求が満たされなくなる。**
> [BUG-008](../bugs/2026-09-06-bug-008-broken-image-alt-webkitgtk.md) は、代替テキストの描画を既定に委ねたために
> **`FR-022`（MUST）が Linux で満たされていなかった。** 枠（こちらが CSS で描くもの）は両環境で出ており、
> **中身（エンジンに任せたもの）だけが欠けていた。**
>
> **委ねてよいのは、差が出ても要求が壊れないものだけである。** 下の許容差はその線引きである。

**次のものは差を許容する。**

| 対象 | 許容する差 | 根拠 |
| --- | --- | --- |
| **タスクリストのチェックボックス**（MD-022, DSP-121）の寸法と、それに伴う左位置のずれ | **2px 以内** | OS / エンジンが描く部品であり（DSP-011）、`github-markdown-css`（DSP-001）も寸法を定めていない。実測は WebView2 が 13px、WebKitGTK が 12px（[BUG-009](../bugs/2026-09-06-bug-009-task-checkbox-size-webkitgtk.md)）|

### NFR-062: 表示言語の一貫性 **MUST**

- 表示言語は OS のロケール設定に依存しない。日本語環境・英語環境・その他の環境のいずれでも同一の文言を表示する（UI-024）。
- ツールチップの英日併記は、日本語フォントが導入されていない環境では日本語部分が正しく描画されない可能性がある。この場合も英語部分だけで機能が伝わる語順・書式（英語を先に置く）とすることで、実用上の支障を生じさせない。
- 言語リソースファイル、翻訳の仕組み、ロケール判定処理をいずれも持たない。これにより、翻訳漏れによる表示崩れや、環境ごとの検証パターンの増加を構造的に排除する。

## 7.8 保守性（NFR-070 系）

### NFR-070: コード品質 **SHOULD**

- `gofmt` による整形と `go vet` による静的解析を CI で強制する（BR-052）。
- Markdown の変換、アウトライン抽出、パスの解決、設定の読み書きといった純粋なロジックには、GUI に依存しないユニットテストを用意する。
- フロントエンドのロジックは、機能ごとにファイルを分割し、グローバル変数の使用を最小限にする。

### NFR-071: 仕様との整合 **MUST**

機能を追加・変更する場合、本仕様書の該当箇所を同一の変更で更新する。実装と仕様の乖離を残さない。

### NFR-072: 文書のドッグフーディング **SHOULD**

本仕様書自体を MarkView で表示し、相対リンク・Mermaid 図・表・GitHub Alerts の描画確認に用いる。仕様書が動作確認の題材を兼ねる状態を維持する。

| 3 | 埋め込み資産のメジャーバージョン自動追随 | 常に最新安定版を取得し、破壊的変更はスモークテスト（BR-054）で検出する。**PlantUML はライセンスの検査も伴う**（BR-043） | スモークテストの失敗が繰り返される場合、版を固定する手段を `scripts/vendorupdate` に足し、メジャーを固定する運用へ切り替える（BR-043 の改訂を伴う。いまは `vendor.json` に版を書いても固定にならない——BR-043 の NOTE。4.81.0 で直した） |
| 4 | タグ付け替え運用の周知 | **rc のタグは作業ブランチ（`develop/work`）の先端に打ち**、push した後に `git fetch --tags --force` でタグが動いたかを確かめ、**動いていればそのコミットを作業ブランチへ fast-forward で取り込む**（`main` の先端とタグが違うため、資産の更新はタグの側にだけ残る。BR-043）。手動テストがすべて OK なら、作業ブランチを `main` へ PR でマージし、**マージしたコミットに本タグを打つ**。本タグの前に rc のタグとの差が手動テストの記録だけであることを確かめる（BR-043, BR-080, E2E-205。**4.96.0 で利用者の手順に合わせた**。4.95.0 までは「rc のタグは `main` の先端に打つ」としていた） | — |
| 5 | バイナリサイズ超過時の扱い | CI は計測値を記録して**警告するに留め、ビルドもリリースも止めない**（BR-060） | 恒常的に目標を超える状態が続く場合、資産構成を見直す |
