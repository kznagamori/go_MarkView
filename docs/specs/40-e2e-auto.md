# 40. E2E テスト仕様: 方針と自動テスト

> 索引: [README](README.md) | E2E テスト: **40** / [41](41-e2e-manual.md)

本文書は、MarkView の E2E テスト（`E2E-nnn`）の方針と、**CI で自動実行するテスト**を定める。人が操作して確認する手動テストは [41. 手動テスト](41-e2e-manual.md) にある。

> [!NOTE]
> 本文書の節は「方針 → 環境 → 禁止事項 → ケース → 対応表」という順に並べており、ID の番号順とは一致しない。**要求と E2E テストの対応表（E2E-030 系）は 40.5 節**にあり、自動テストのケース（E2E-1xx、40.4 節）より後に置いている。対応表は本文書と 41 章の**両方のケースから作る**ため、ケースを定義したあとに置くのが読む順序として自然だからである。

## 40.1 位置づけ

### E2E-001: 目的 **MUST**

E2E テストの目的は、**利用者が実際に受け取る配布物が、想定した環境で想定どおりに動くことを確かめること**である。

単体テスト（[30](30-test-policy.md) / [31](31-test-cases.md)）が「部品が正しいか」を見るのに対し、E2E テストは「組み上がったものが動くか」を見る。両者は代替関係にない。

| 観点 | 単体テスト | E2E テスト |
| --- | --- | --- |
| 対象 | `internal/` のパッケージ | ビルドされた実行ファイル |
| 実行 | `go test` | 配布物の起動、および人の操作 |
| 検出できるもの | ロジックの誤り | 組み合わせの誤り、環境依存、配布物の欠落 |
| 検出できないもの | 結合・配置・環境の問題 | 内部の境界値の誤り |

### E2E-002: 自動と手動の分担 **MUST**

| 区分 | 対象 | 実行 | 文書 |
| --- | --- | --- | --- |
| **自動テスト** | 配布物の構成、起動と終了、CLI の出力、依存ライブラリ、描画スモーク | リリース CI（BR-050）のビルド後 | 本文書 40.4 節 |
| **手動テスト** | UI の操作を伴うすべての振る舞い | プレリリースの成果物に対して人が実施（E2E-205） | [41 章](41-e2e-manual.md) |

いずれも**ビルドされた成果物を必要とする**ため、PR 単位の検証（BR-052）では実行しない。例外は描画スモークテスト（E2E-109）で、これは描画に関わるパスを変更する PR でも実行する。配布物ではなく `frontend/` をそのまま配って描かせるため、ビルドを必要としない。

分担の基準は「**CI で安定して繰り返せるか**」である。

- 自動テストは、**WebView の UI を操作しない**範囲に限る。ウィンドウ内の要素をクリックする、描画完了を待つ、といった操作は環境によって成否が変わり、失敗しても「また揺れたのだろう」と無視されるようになる（UT-037 と同じ理由）。
- 起動そのもの（プロセスが立ち上がり、異常終了しないこと）は自動テストの対象とする。これは配布物の検証として価値が高く、判定も明確である。
- UI の操作は手動テストに委ねる。回数は減るが、判断の伴う確認は人のほうが確実である。

> [!NOTE]
> `IMP-042` と `UT-038` は「WebView を起動する自動テストを行わない」と定めている。本文書の自動テストは、**起動と終了までを確認し、ウィンドウ内の操作を行わない**。この線引きにより既存方針と矛盾しない。線を越える変更を行う場合は、両方の文書を同時に改訂する。

## 40.2 検証環境（E2E-010 系）

### E2E-010: 対象環境 **MUST**

| コード | 環境 | 自動 | 手動 |
| --- | --- | --- | --- |
| **W1** | Windows 11 / amd64 | ○ | **全項目**（主環境） |
| **L1** | Ubuntu 24.04 / amd64 | ○ | OS 差の出る項目 |
| **WA** | Windows 11 / arm64 | ○（ビルドのみ） | 起動確認（入手できた場合） |
| **LA** | Ubuntu 24.04 / arm64 | ○ | 起動確認（入手できた場合） |

- 主環境を W1 とするのは、開発ホストが Windows 11 であり（01 章 1.6）、最も頻繁に動かされる環境だからである。
- L1 で確認する「OS 差の出る項目」は、41 章の各ケースに環境コードで示す。
- arm64（WA / LA）は実機の入手性に依存するため、**起動確認のみを必須とし、それ以外は任意**とする。CI ではビルドと自動テストが通ることをもって最低限の担保とする。

### E2E-011: 検証に用いる配布物 **MUST**

E2E テストは、**開発ビルドではなくリリースと同じ手順で作られた成果物**に対して行う（BR-010, BR-020）。

- 自動テストは、リリース CI がビルドした成果物（zip / tar.gz）を展開して実行する。
- 手動テストは、**プレリリースタグから CI が作った成果物**を用いる。手順は E2E-205 に定める。
- `wails dev` で起動したものや、手元でビルドしたものを検証の対象にしない。開発ビルドは開発者ツールが有効（BR-012）であり、またローカルビルドには埋め込み資産の自動更新（BR-043）が反映されないため、配布物と内容が食い違いうる。

- `-edit` は `generated/edit/` の**中身だけ**を作り直し、**ディレクトリそのものは消さない**（10 MiB 超などの大きなファイルも作り直さない）。**MarkView が `generated/edit/` の中の文書を表示したまま `-edit` を実行する手順がある**（E2E-381 の手順 10、E2E-386 の手順 6）——ディレクトリごと消すと、Windows では監視のハンドルが残って消せないか作り直せず、Linux では監視が切れて、以降の自動の読み直しを確かめられなくなる。**読み取り専用のファイルと、書き込めなくしたディレクトリ（E2E-386 の `locked/`）も消せるよう、先にファイルの属性とディレクトリの権限を戻してから消す。** `-clean` は `generated/edit/` を含めて消す。
- **`generated/edit/` に `README.md` を置かない。** E2E-381 は、このディレクトリを引数にして起動したときに操作案内が出ることを使う（FR-013）。
- 巨大ファイルはリポジトリに含めない。検証のたびに生成する。生成は `scripts/gentestdata` が行う。

  ```bash
  go run ./scripts/gentestdata          # testdata/e2e/generated/ に作る
  go run ./scripts/gentestdata -edit    # generated/edit/ の中身だけを作り直す（G18 の各ケースの前）
  go run ./scripts/gentestdata -clean   # 消す
  ```

- **`.git` はリポジトリに入れられない。** Git がその名前を予約しているため、検証用データとして置けない。除外の規則は「名前が `.` で始まる」であり `.git` に固有ではないので、`.hidden/` を代わりに置いて同じ規則を確かめる。
- 除外されるディレクトリは `node_modules` / `vendor` / `.git` / `target` / `dist` / `build` である（IMP-132）。このうち **2 つを実際に置く**。一覧の全部を並べても、確かめているのは同じ 1 つの規則である。
- `e2e/generated/` は**除外の対象ではない**。ツリーに現れ、そこから大きなファイルを選んで E2E-322 を実施できる。
- この一式は自動テストと手動テストの両方で使う。用途ごとに別のデータを用意しない。

## 40.3 自動テストで行わないこと（E2E-020 系）

### E2E-020: 禁止事項 **MUST**

| 禁止 | 理由 |
| --- | --- |
| ウィンドウ内の要素をクリック・入力する | 描画完了の判定が環境依存であり、flaky になる（E2E-002） |
| スクリーンショットを撮って画像比較する | フォント・DPI・OS のテーマで差が出て、意味のない失敗が続く |
| 固定時間の `sleep` で描画完了を待つ | 環境で揺れる（UT-037 と同じ） |
| ネットワークにアクセスする | リモート画像の確認は手動で行う（IMP-042） |
| 実際のリリースを作成して確認する | 検証のために公開してはならない |

> [!IMPORTANT]
> **この禁止は「自動テストで見つからない不具合の範囲」をそのまま定めている。**
>

>
> **範囲を広げる場合は、本要求（E2E-020）と E2E-002 / IMP-042 / BR-054 を同じ変更で改訂する。** 4.21.0 で使い捨てのハーネス（`element.click()` と `document.elementFromPoint`）を書いて不具合を再現させた実績があり、**技術的に不可能なのではなく、常設していないだけ**である。**常設するなら、それは仕様の判断として明示的に行う。**

### E2E-021: 失敗したときの扱い **MUST**

- 自動テストが失敗した場合、**リリースを中止する**（E2E-100 の表に従う）。失敗を承知でリリースしない。
- 失敗が環境の一時的な問題と判断される場合も、原因を特定してから再実行する。理由を確かめずに再実行を繰り返さない。繰り返しで通ったテストは、次に本物の不具合が出たときにも同じ扱いをされる。

## 40.4 自動テストのケース（E2E-1xx）

### E2E-100: 実行の位置づけ **MUST**

自動テストは、プレリリースタグと本タグのどちらでも同じ内容を実行する。プレリリースで通ったものが本リリースでも通ることを確かめる意味を持つ。

| ケース | 実行タイミング | 失敗時 |
| --- | --- | --- |
| E2E-101〜E2E-103 | リリース CI（BR-050）のビルド後 | リリースを中止 |
| E2E-104〜E2E-106 | 同上 | リリースを中止 |
| E2E-107 | 同上 | 記録のみ（BR-060） |
| E2E-108 | 同上 | リリースを中止 |
| E2E-109 | リリース CI および描画に関わるパスを変更する PR（契機のパスは BR-052、内容は BR-054） | リリースを中止 |

実装は `scripts/e2e` とする。**要求する環境が違うため 2 つに分ける。**

```bash
go run ./scripts/e2e archives -dir dist -version v1.0.0-rc.1
go run ./scripts/e2e binary   -archive dist/MarkView-v1.0.0-rc.1-linux-amd64.tar.gz -version v1.0.0-rc.1
```

| サブコマンド | 担当するケース | 実行できる場所 |
| --- | --- | --- |
| `archives` | E2E-101 / E2E-107 / E2E-108 | どの OS でも。アーカイブを読むだけで実行しない |
| `binary` | E2E-102 / E2E-103 / E2E-104 / E2E-105 / E2E-106 | **対象 OS の上だけ** |

- `binary` は `-archive` を渡すと自分で展開してから実行する（E2E-011）。展開の経路まで含めて確かめる。
- **対象 OS が食い違ったら中断する。** 実行ファイルの先頭 4 バイトで ELF / PE を見分け、走っている OS と合わなければエラーで止める。そのまま走らせると実行を伴う確認がすべて失敗し、「配布物が壊れている」のか「ジョブの割り当てを誤っている」のか読み取れなくなる。`-allow-foreign` を付けた場合だけ、実行を伴う確認を SKIP として飛ばし、E2E-106 の ELF 検査だけを行う。
- 判定は合否（`NG`）・警告（`WARN`。E2E-107 のみ）・実施不可（`SKIP`）・記録（`--`）に分ける。**飛ばした行も表から消さない。** 消すと「確かめたつもり」が生まれる。
- E2E-109（描画スモークテスト）は `scripts/smoke` が担当する（BR-054）。配布物ではなく `frontend/` を直接描かせるため、ここには含めない。

| 5 | 起動時の標準エラー出力 | MarkView 自身のログ出力がない（NFR-041。`MARKVIEW_DEBUG` は未設定）。GTK・WebKitGTK など OS 側のライブラリが出す警告は対象外とする。**GLib の既定のログの形（`(<プログラム名>:<pid>): <ドメイン>-<LEVEL> **: …`。例 `(MarkView:12345): Gtk-WARNING **: …`）の行は、プログラム名としてアプリ名を含んでも対象外とする**——アプリ名を含むかどうかだけで判定すると、GTK が 1 行警告しただけでリリースが止まる |

> [!IMPORTANT]
> ケース 6 は、**`WebviewUserDataPath` の指定漏れ（IMP-193）を機械的に検出する唯一の手段**である。指定を落としても画面上は何も壊れず、`%APPDATA%` に数十 MB が書かれるだけなので、人が見て気づくことはまずない。
>
> 見るのは**実行ファイル名と同じ名前のディレクトリ**である。go-webview2 の既定値が `%APPDATA%\<実行ファイル名>` であり、配布物の名前は `MarkView.exe` だが、検証時のファイル名から組み立てて判定する。Linux は指定手段が無いため（AR-004）、このケースを実行しない。

実行方法:

| OS | 方法 |
| --- | --- |
| Linux | `xvfb-run` で仮想ディスプレイ上に起動し、**MarkView のプロセスへ** `SIGTERM` を送って終了させる。**`xvfb-run` のシェルへ送らない**——シェルだけが終わると、MarkView が残ったまま「正常に終了した」と判定しうる |

### E2E-031: E2E で確かめない要求の扱い **MUST**

上表で `—` となっている要求には、次の分類記号を付している。**E2E の不足ではない。**

| 記号 | 分類 | 検証手段 |
| --- | --- | --- |
| INTERNAL | 内部構造の要求 | **配布物の外から観測できない。** 単体テスト（31 章）とレビューで担保する |
| BUILD | ビルド・CI・リリース運用の要求 | CI の実行そのものが検証となる（BR-052, BR-050） |
| PERF | 性能・資源の目標 | 測定条件（07 章 7.1）に基づく計測。W1 を基準とする |
| VISUAL | 見た目の細部 | **全ケースの実施中に常に目に入る**ため、個別のケースを設けない。期待値は表示仕様書（20〜22）が定める |
| ABSENCE | 「行わないこと」の要求 | 実装の不在で満たされる。テストでの証明は困難であり、レビューで担保する |
| DESIGN | 設計判断・運用の記録 | 検証対象を持たない |
| TBD | **要求を追加したが、まだケースが無い** | 41 章（または 40 章）のケースを書く段階で、ケースの ID か上の記号へ置き換える。**一時的な記号であり、残っている間はその要求の実装に着手せず、rc を打つ前には必ず無くす**（[90.6.5](90-traceability.md), E2E-205） |

> [!NOTE]
> **UT-901 の記号と同じではない。** あちらの `GUI`（画面の振る舞いだから単体テストにしない）は、こちらでは**むしろ E2E の主題**であり存在しない。代わりに `INTERNAL`（外から見えないから E2E にしない）と `VISUAL` がある。**2 つの表は互いを埋め合う関係にある**ため、片方で `—` の要求がもう片方で確かめられていることが多い。

### E2E-032: 対応表の網羅性 **MUST**

- 本表には**要求仕様書に定義されたすべての ID が 1 行ずつ現れる**。範囲表記を用いない（UT-902 と同じ理由）。省略すると、要求が追加されたときに漏れが検出できなくなる。
- 要求を追加・削除した場合、本表を同じ変更で更新する（NFR-071）。
- ケースの「関連要求」を書き換えた場合も本表を更新する。**本表はそこから作れる**ため、機械的に照合できる。
- 網羅性は機械的に検査できる。要求仕様書の見出しから抽出した ID の集合と、本表の第 1 列の集合が一致すること、および第 2 列に現れる `E2E-` の ID が実在することを確認する。
