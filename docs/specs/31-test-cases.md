# 31. 単体テスト仕様: テストケース

> 索引: [README](README.md) | 単体テスト: [30](30-test-policy.md) / **31**

本文書は、パッケージごとの単体テストケースを定める。書き方の規範と禁止事項は [30. 方針と禁止事項](30-test-policy.md) にある。

## 31.1 読み方

### UT-090: 表の形式 **MUST**

各ケースは以下の形式で記す。

```
### UT-nnn: <観点>
対象: <パッケージ>.<関数>   根拠: <要求 ID> / <実装 ID>

| # | 入力 | 期待 |
```

- 「根拠」に挙げた仕様が変わったら、そのケースも見直す（UT-010）。
- 表の各行は、テーブル駆動テスト（UT-014）の 1 ケースに対応する。行の説明文をそのままサブテスト名にしてよい。
- ここに挙げたものは**最低限**であり、これで十分という意味ではない。実装中に気づいた境界値は追加してよい。逆に、ここにないケースを削る場合は理由を残す。

## 31.2 document パッケージ（UT-1xx）

### UT-101: BOM と改行コードの正規化
対象: `document.Normalize`　根拠: FR-021 / IMP-103

| # | 入力（バイト列） | 期待 |
| --- | --- | --- |
| 1 | `EF BB BF` + `"# A"` | `"# A"`（BOM 除去）、`replaced=false` |
| 2 | `"# A"`（BOM なし） | `"# A"` そのまま |
| 3 | `"a\r\nb"` | `"a\nb"` |
| 4 | `"a\rb"` | `"a\nb"` |
| 5 | `"a\nb"` | `"a\nb"`（変化なし） |
| 6 | `"a\r\n\r\nb"` | `"a\n\nb"` |
| 7 | `EF BB BF` のみ | `""` |
| 8 | 中間に現れる `EF BB BF` | 除去しない（先頭のみが BOM） |
| 9 | 空のバイト列 | `""`、`replaced=false` |

### UT-102: 不正な UTF-8 の置換
対象: `document.Normalize`　根拠: FR-021 / IMP-103

| # | 入力 | 期待 |

### UT-104: サイズ閾値の判定
対象: `document.Load`　根拠: FR-016 / IMP-101, IMP-102

| # | ファイルサイズ | `Confirmed` | 期待 |
| --- | --- | --- | --- |
| 1 | 1 KB | false | 正常に読み込む |
| 2 | ちょうど 10 MiB | false | 正常に読み込む（**閾値ちょうどは超過ではない**） |
| 3 | 10 MiB + 1 バイト | false | `ErrNeedsConfirm`。`*SizeError` に実サイズと閾値が入る |
| 4 | 10 MiB + 1 バイト | **true** | 正常に読み込む |
| 5 | ちょうど 50 MiB | true | 正常に読み込む |
| 6 | 50 MiB + 1 バイト | true | `ErrTooLarge`（`Confirmed` でも読み込まない） |
| 7 | 0 バイト | false | 正常に読み込む。空の HTML を返す |

> [!NOTE]
> ケース 2 と 5（閾値ちょうど）、ケース 6（`Confirmed` でも拒否）が、この機能で最も間違えやすい箇所である（UT-013）。

### UT-106: 読み込みエラーの種別
対象: `document.Load`　根拠: FR-110 / IMP-021, IMP-102

| # | 状況 | 期待 |
| --- | --- | --- |
| 1 | 存在しないパス | `errors.Is(err, ErrNotFound)` が true |
| 2 | 読み取り権限のないファイル | `errors.Is(err, ErrPermission)` が true |
| 3 | 拡張子が Markdown でない | `errors.Is(err, ErrNotMarkdown)` が true |
| 4 | ディレクトリのパス | エラーを返す（`ErrNotMarkdown` または `ErrNotFound`） |

- エラーメッセージの文字列を比較しない。種別のみを `errors.Is` で判定する（UT-042）。
- ケース 2 は Windows では再現が難しい。`runtime.GOOS` で分岐し、Linux でのみ実行してよい。

### UT-107: 生バイト列と正規化後の位置の対応
対象: `document.PlanTask` / `document.PlanCell` / `document.CellSource`（IMP-106 の手順 1 と 3）　根拠: FR-141, FR-142, FR-143, FR-021 / IMP-106

**位置の対応は、LF だけの文書では壊れていても見えない。** 改行コードと BOM の組み合わせを先に置く（UT-013）。

`- [ ] a` / `- [ ] b` / `- [ ] c` の 3 行（各行の後に改行）を、改行コードと BOM を変えて与え、**最後のタスクをオンにする** `Patch` を見る。

| # | 入力 | 期待 |
| --- | --- | --- |
| 1 | LF | `Offset` が **19**、`Old` が半角空白、`New` が `x` |
| 2 | CRLF | `Offset` が **21**（前の 2 行の CR の分だけ後ろ） |
| 3 | CR だけ | `Offset` が **19** |
| 4 | 先頭に BOM + LF | `Offset` が **22**（BOM の 3 バイトの分だけ後ろ） |
| 5 | 先頭に BOM + CRLF | `Offset` が **24** |
| 6 | 1 行目だけ CRLF、残りは LF | `Offset` が **20**（除いた CR は 1 つ） |
| 7 | 不正な UTF-8 を含む文書 | `ErrNotEditable`（置き換えが長さを変え、位置を対応させられない） |
| 8 | 1〜6 の `Patch` を適用した結果 | **括弧の中の 1 バイト以外は、入力と 1 バイトも違わない**（BOM・CR・末尾の改行を含む） |
| 9 | 先頭に BOM、CRLF で `+++` / `a = 1` / `+++` の TOML の Front Matter、続けて `- [ ] a` をオンにする | `Offset` が **23**（BOM 3 と CR 3 つの分だけ後ろ。Front Matter の位置の補正と組み合わせる） |
| 10 | BOM + CRLF で書いた UT-110 の基本の文書（1〜3 行目だけ）で、本体の `1` を `9` にする `PlanCell` | `Offset` が **31** |
| 11 | 10 の文書の `CellSource` | `1`（CR を含まない） |

> [!IMPORTANT]
> **ケース 2〜6 と 9〜10 を欠かさない。** 対応表を持たない実装（正規化後の位置をそのまま使う実装）は、ケース 1 と 3 を通る。**CRLF の文書で、書き換える位置が前（上）へずれ、別の箇所を書き換える**形で現れ、利用者の Windows の文書で最初に壊れる（FR-143）。**セルの書き換え（ケース 10）も同じ対応表を通る**ことを、タスクとは別に確かめる。

### UT-108: 目印の値の解読
対象: `document.ParseRef`　根拠: FR-141, FR-142, NFR-030 / IMP-106, IMP-120

鍵は `0123456789abcdef` とする。

| # | 入力 | 期待 |
| --- | --- | --- |
| 1 | `0123456789abcdef:task:3` | `Kind` がタスク、`Index` が 3、`Key` が鍵 |
| 2 | `0123456789abcdef:cell:1:0:2` | `Kind` がセル、`Index` が 1、`Row` が 0、`Col` が 2 |
| 3 | `0123456789abcdef:table:1` | `ErrBadRef`（**表の目印は書き込みの対象ではない**） |
| 4 | 鍵が 15 文字 / 17 文字 / 大文字の 16 進 | `ErrBadRef` |
| 5 | `0123456789abcdef:task:-1` / `0123456789abcdef:task:+3` | `ErrBadRef`（**`strconv.Atoi` は `+3` を受け付けるが、IMP-116 の正規表現は受け付けない。** 形を揃える） |
| 6 | `0123456789abcdef:task:3:9`（区切りが多い） | `ErrBadRef` |
| 7 | `0123456789abcdef:cell:1:0`（数が足りない） | `ErrBadRef` |
| 8 | 空文字 | `ErrBadRef` |
| 9 | `0123456789abcdef:task:99999999999999999999`（int に収まらない） | `ErrBadRef`。**panic しない** |

### UT-109: チェックボックスの書き換え
対象: `document.PlanTask`　根拠: FR-141, MD-022 / IMP-106, IMP-121

| # | 入力 | 期待 |
| --- | --- | --- |
| 1 | `- [ ] a` をオンにする | `Old` が半角空白、`New` が `x`、`changed` が真 |
| 2 | `- [x] a` をオフにする | `Old` が `x`、`New` が半角空白 |
| 3 | `- [X] a` をオフにする | `Old` が `X`、`New` が半角空白（FR-141） |
| 4 | `- [X] a` をオンにする | `changed` が**偽**（大文字もオンとみなす） |
| 5 | `- [x] a` をオンにする / `- [ ] a` をオフにする | どちらも `changed` が偽（**反転ではなく「この状態にする」**） |
| 6 | 括弧の中がタブの項目 / 改ページ（`\f`）の項目をオンにする | `Old` がタブ / 改ページ、`New` が `x`（どちらもオフとみなす。goldmark の `\s`。IMP-106） |
| 7 | 引用の中のリスト（`> - [ ] a`） | 引用記号の後ろの、括弧の中を指す |
| 8 | 入れ子のリストの内側と、ゆるいリスト（項目の間に空行） | 文書の中の出現順で数えた番号の項目を指す |
| 9 | コードブロックの中の `- [ ] x` の後に本物のタスク | コードブロックの中を数えない（本物のタスクが 0 番） |
| 10 | 生 HTML の `<input type="checkbox">` の後に本物のタスク | 生 HTML を数えない（本物のタスクが 0 番） |
| 11 | 番号がタスクの数を超える | `ErrRefNotFound` |
| 12 | `-` とタブの後の `[ ] a` / `- [ ] a` の次の行にタブ 1 つで字下げした `- [ ] b`（入れ子の内側）を、それぞれオンにする | どちらも `raw[Offset-1]` が `[`、`raw[Offset+1]` が `]` で、`Old` が半角空白（**括弧の外を書き換えない**。タブの字下げで位置がずれる実装を捕まえる。IMP-106） |

### UT-110: セルの書き換えとソースの取得
対象: `document.PlanCell` / `document.CellSource`　根拠: FR-142, MD-024 / IMP-106, IMP-121

**縦棒を含む入力は、表の形を壊す境界である。** 表のセルを割らないため、表中では縦棒を「縦棒」、バックスラッシュを「`\`」と書く。

基本の文書は次の表とする（区切り行の後に本体が 2 行。2 行目はセルが 1 つしかない）。

```
| a | b |
| --- | --- |
| 1 | 2 |
| x |
```

| # | 入力 | 期待 |
| --- | --- | --- |
| 1 | 本体 1 行目 1 列目を `9` にする | `Old` が `1`、`New` が `9`。**前後の空白と区切りの縦棒は `Patch` に含まれない** |
| 2 | `  hello  `（前後に空白） | `New` が `hello` |
| 3 | `a` + 縦棒 + `b` | `New` が `a` + `\` + 縦棒 + `b`（区切りにならないようエスケープする） |
| 4 | `a` + `\` + 縦棒 + `b`（エスケープ済み） | そのまま（直前の 1 文字が `\`） |
| 5 | `a` + `\` 2 つ + 縦棒 + `b` | **そのまま**（直前の 1 文字が `\`。**goldmark は `\` の個数を数えない**。IMP-106） |
| 6 | 末尾が `\` の `abc\` を、基本の文書（内容と区切りの間に空白がある）へ | そのまま（**何も足さない**） |
| 7 | 改行（`\r\n` / `\n` / `\r`）を含む `a` + 改行 + `b` | `New` が `a b` |
| 8 | 元と同じ `1` | `changed` が偽 |
| 9 | 空文字 | `Old` が `1`、`New` が空（空のセルになる） |
| 10 | 空のセル（縦棒 2 つの間に半角空白 2 つ）を `x` にする | `x` が区切りの間の空白の 1 文字目の直後へ入り、**空白の数が変わらない** |
| 11 | 空白の無い空のセル（縦棒が 2 つ並ぶ）を `x` にする | 前の縦棒の直後へ入る |
| 12 | 補われたセル（本体 2 行目の 2 列目） | `ErrRefNotFound`（**区切りを足すことになり、表の形を変える**） |
| 13 | 見出し行のセル（`Row` が 0） | 書き換えられる |
| 14 | 桁揃えの空白を持つセル（`1` の後に空白が 4 つ） | `Old` は `1` だけ。**空白を詰め直さない** |
| 15 | `**太字**` のセルの `CellSource` | `**太字**`（記法を含み、前後の空白を除いたもの） |
| 16 | エスケープした縦棒を含むセルの `CellSource` | `\` を含んだまま返す（IMP-121） |
| 17 | 行頭に縦棒が無い行の最初のセル | その行の最初のセルが書き換わる |
| 18 | 引用の中の表 | 引用記号の外の、正しいセルが書き換わる |
| 19 | 生 HTML の `<table>` の後に GFM の表 | 生 HTML を数えない（GFM の表が 0 番） |
| 20 | **空白の無い表**（区切りの縦棒とセルの間に空白を置かない 2 列の表。本体の 1 列目は `1`）の本体 1 列目を `abc\` にする | **末尾に半角空白を 1 つ足して書く**（`\` が区切りの縦棒をエスケープしないように。IMP-106） |
| 21 | 3〜6・10・11・20 の各ケースで、`Patch` を適用した内容を `renderer.Locate` で解き直す | **表の行数・各行のセルの数が書き換える前と同じで、書き換えたセル以外のセルについて `Content` の区間が指すバイト列が書き換える前と同じ**（区間そのものは、書き換えたセルより後ろでずれてよい） |
| 22 | 表の番号が表の数以上 / 行が行数以上 / 列が見出しの列数以上 | `ErrRefNotFound`。panic しない |

> [!IMPORTANT]
> **ケース 3〜6・12・20 は、表の形が変わる境界である。** どれか 1 つを落とすと、**書き込んだ後の文書で列がずれ、別のセルの内容が隣へ移る。** 利用者は再描画の結果を見るまで気づけない。
>
> **ケース 5 はパーサの規則そのものである。** goldmark v1.8.5 は `|` の直前の 1 文字だけを見る（4.43.0 のレビューで実測）。「`\` の数が偶数ならエスケープされていない」と数える実装は、ケース 5 で `\` を足してしまい、**表示が変わる。**
>
> **ケース 21 が要である。** エスケープの規則を手で書いても、パーサと食い違えば形は変わる。**書き換えた結果をパーサに通して、形が変わっていないことを確かめる**のが、規則の誤りを捕まえる唯一の手段である（IMP-106 はこの確かめを書き込みの前にも行う）。

### UT-111: Patch の適用と逆
対象: `document.Patch`　根拠: FR-143, FR-144 / IMP-106

| # | 入力 | 期待 |
| --- | --- | --- |
| 1 | `Offset` と `Old` が一致する | `New` に置き換えたバイト列 |
| 2 | `Old` が一致しない | `ErrChanged`。**書き換えたものを返さない** |
| 3 | `Offset + len(Old)` が長さを超える | `ErrChanged`。panic しない |
| 4 | `Offset` が負 | `ErrChanged`。panic しない |
| 5 | 長さの違う置き換え（`1` → `123`） | 後ろのバイト列が正しく続く |
| 6 | 適用した結果に `Inverse` を適用する | **元のバイト列と一致する** |
| 7 | 適用の前後で、渡したバイト列 | 内容が変わっていない（新しいバイト列を返す） |
| 8 | `Old` が空で `Offset` が長さと等しい（末尾への挿入） | `New` を末尾に足したバイト列（`Old` が空の形は、`PlanCell` が空のセルに書き込むときに作る。ここでは末尾の境界を見る） |
| 9 | `Old` が空で `Offset` が長さを超える | `ErrChanged`。panic しない |

### UT-112: 置き換えによる書き込み
対象: `document.Replace`　根拠: FR-143, NFR-031, NFR-033 / IMP-107

**書き込まないことを確かめるケースを先に書く**（UT-013）。すべて `t.TempDir()` の実ファイルで行う。

| # | 状況 | 期待 |
| --- | --- | --- |
| 1 | 読み取り専用のファイル（Windows は読み取り専用属性、Linux は `0444`）。**ディレクトリは書き込める** | `ErrPermission`。**内容が変わらない** |
| 2 | 1 の後のディレクトリ | 一時ファイル（`.<名前>.markview-` で始まるもの）が残っていない |
| 3 | ディレクトリに書き込めない（Linux。`0555`） | `ErrPermission`。元のファイルは変わらない |
| 4 | 存在しないパス | `ErrNotFound`。ファイルを作らない |
| 5 | 通常のファイル | 内容が渡したバイト列と一致する |
| 6 | 5 の後のディレクトリ | 一時ファイルが残っていない。**ファイルの数が書き込みの前と同じ** |
| 7 | 別のディレクトリの実体を指すシンボリックリンク（Linux） | **実体の内容が変わり、リンクはシンボリックリンクのまま**（`os.Lstat` で確かめる） |
| 8 | 権限ビットが `0640` のファイル（Linux） | 書き込みの後も `0640` |
| 9 | 空のバイト列 | 空のファイルになる |
| 10 | 宛先の無いシンボリックリンク（Linux） | `ErrNotFound`。**リンクの宛先にファイルを作らない** |

> [!NOTE]
> **ケース 1 が要である。** ディレクトリに書き込めれば、リネームは読み取り専用のファイルも置き換えてしまう（IMP-107 の手順 3）。**「書き込めた」だけを見るテストでは、読み取り専用を無視する実装が緑になる。**
>
> ハードリンクが切れること、Windows でファイル個別に設定したアクセス制御が引き継がれないことは、FR-143 が許容しているため検査しない（UT-042）。ケース 3・7・8・10 は Windows では `t.Skip` し、**Linux の CI で必ず実行する**（BR-052）。**ケース 1 と 3 は root で実行すると成立しない**（root は権限を無視して書ける）ため、実行ユーザが root なら `t.Skip` し、理由をメッセージに残す。

### UT-113: 取り消し履歴
対象: `document.EditLog`　根拠: FR-144 / IMP-108

| # | 操作 | 期待 |
| --- | --- | --- |
| 1 | 作ったばかり | `Undo` も `Redo` も `ok` が偽。`Known` は作るときに渡した値 |
| 2 | `Record(p, h1)` の後に `Undo` | `p.Inverse()` と等しい `Patch`、`ok` が真。**`Known` は `h1` のまま**（`Record` が `Known` を `after` へ進め、`Undo` は確定していないため動かさない。IMP-108） |
| 3 | 2 の後に `CommitUndo(h0)` | `Known` が `h0`。`Redo` で `p` が取り出せる |
| 4 | `Undo` で取り出して確定せず、もう一度 `Undo` | **同じ `Patch`**（履歴が動いていない） |
| 5 | 取り消して確定した後に `Record` | `Redo` の `ok` が偽（やり直しの履歴を捨てた） |
| 6 | ちょうど 100 回 `Record` し、`Undo` と確定を繰り返す | **100 回**取り出せる。101 回目は `ok` が偽 |
| 7 | 101 回 `Record` し、`Undo` と確定を繰り返す | 100 回取り出せる。**最初に記録したものは取り出せない**（古いものから捨てる） |
| 8 | `Redo` の後に `CommitRedo(h)` | `Known` が `h`。`Undo` で再び取り出せる |

> [!IMPORTANT]

| 12 | 生 HTML の `<object>` の中に `# A`（`<object>` の行・空行・`# A`・空行・`</object>` の行）を書き、その後に `<div id="statusbar">x</div>` を書く | 出力に `id="statusbar"` が**無く**、`user-content-statusbar` がある（**`id` の数を数えて走査を省く実装を捕まえる**。bluemonday は `object` を中身ごと捨てるため、Go が出した見出しの `id` 1 つが消え、生 HTML の `id` 1 つと数が合う。IMP-116） |
| 13 | 自己終了タグで書いた生 HTML の `<div id="status"/>` | `user-content-status`（**開始タグだけを組み立て直す実装を捕まえる**。bluemonday は自己終了タグのまま出し、ブラウザは開始タグとして扱う。IMP-116） |

> [!IMPORTANT]
> **ケース 7 が要である。** 1〜6 は経路ごとの確認であり、**接頭辞を付け忘れた経路が 1 つ残っても 7 だけが落ちる。** 画面の要素を乗っ取る id は 1 つあれば足りる（[BUG-011](../bugs/2026-09-14-bug-011-document-id-collision.md)）。
>
> **ケース 8 は逆向きの確認である。** スラッグの関数の中で接頭辞を付けると、UT-202 が落ちる（IMP-117 の IMPORTANT）。
>
> **ケース 12 と 13 は、ケース 7 を通り抜ける。** 7 の文書は数も合わず、自己終了タグも含まないためである。どちらも**接頭辞の無い `id` が 1 つ残る**だけで BUG-011 が再発する（4.44.0 のレビュー）。

## 31.5 watcher パッケージ（UT-4xx）

対象: `watcher`　根拠: FR-014 / IMP-140, IMP-141

| # | 操作 | 期待 |
| --- | --- | --- |
| 1 | 監視中のファイルへ追記 | `Modified` イベントが 1 件届く |
| 2 | 同じディレクトリの**別**ファイルを変更 | イベントが届かない（IMP-141） |

### UT-403: リネーム型の保存
対象: `watcher`　根拠: FR-014 / IMP-142

| # | 操作 | 期待 |
| --- | --- | --- |
| 1 | 一時ファイルを作り、監視対象へ `os.Rename` | `Modified` が届く（`Removed` ではない） |
| 2 | 同操作の後、さらに追記 | 再び `Modified` が届く（監視が張り直されている） |

ケース 2 は、エディタの保存方式で監視が外れる問題（FR-014）を検出する。

### UT-404: 削除の検知
対象: `watcher`　根拠: FR-014 / IMP-142

| # | 操作 | 期待 |
| --- | --- | --- |
| 1 | 監視対象を削除して復活させない | `Removed` が届く |
| 2 | 削除直後（150 ms 以内）に同名で再作成 | `Modified` が届く（`Removed` ではない） |

### UT-405: 監視対象の切り替え
対象: `watcher.Watch`　根拠: NFR-020 / IMP-140

| # | 操作 | 期待 |
| --- | --- | --- |
| 1 | A を監視 → B を監視 → A を変更 | イベントが届かない（A の監視が解除されている） |
| 2 | 同上 → B を変更 | `Modified` が届く |
| 3 | `Watch` を 10 回繰り返し、最後に監視した 1 つ以外をすべて変更 | いずれのイベントも届かない |

ケース 3 は、ウォッチャのリーク（NFR-020）を検出する。**内部のウォッチャ数を直接数えるのではなく、「解除されたはずの対象からイベントが来ないこと」という観測可能な振る舞いで確かめる**（UT-011）。内部の数を見るテストは、実装の持ち方を変えただけで壊れる。

> [!NOTE]
> **このケースは「OS への監視登録を解除しているか」までは検出しない。** 実装は監視対象のパスでイベントを絞り込む（IMP-141）ため、登録を解除し忘れてもイベントは届かず、上の 3 ケースは通ってしまう。2026-08-31 に実装時の破壊テストで確認済み（`fsnotify.Watcher.Remove` の呼び出しを外しても全ケースが通る）。
> 
> 解除漏れが表面化するのは OS の監視数の上限に達したときであり、テストで再現するのは現実的でない。監視中のディレクトリを削除できるかでも判別できない（fsnotify は削除を許す共有モードでハンドルを開く）。**この 1 点はレビューで担保する。**

### UT-406: 終了処理
対象: `watcher.Close` / `context` キャンセル　根拠: IMP-024, IMP-140

| # | 操作 | 期待 |
| --- | --- | --- |
| 1 | `Close` を呼ぶ | イベントチャネルが閉じる。ゴルーチンが終了する |
| 2 | `context` をキャンセル | 同上 |
| 3 | `Close` を 2 回呼ぶ | panic しない |

### UT-407: シンボリックリンクの実体の監視
対象: `watcher.Watch`　根拠: FR-014, AR-070 / IMP-141

**Linux でだけ実行する**（シンボリックリンクの作成に Windows では権限が要る。UT-602 の IMPORTANT と同じ扱い。CI の Linux ジョブで必ず走る。BR-052）。

別のディレクトリにある実体と、それを指すリンクを `t.TempDir()` に作り、**リンクのパスを `Watch` に渡す。**

| # | 操作 | 期待 |
| --- | --- | --- |
| 1 | 実体へ追記する | `Modified` が届く |
| 2 | 1 のイベントの `Path` | **`Watch` に渡したリンクのパス**（実体のパスではない） |
| 3 | 実体の置き場所で、一時ファイルを作ってリネームで実体を置き換える | `Modified` が届く（`Removed` ではない） |
| 4 | **実体のディレクトリに、リンクと同じ名前**（実体とは違う名前）のファイルを作って書く | イベントが届かない（**実体の名前と比べている**。IMP-141） |

> [!IMPORTANT]
> **ケース 1 が要である。** リンクの置き場所を監視する実装（v1.0.0 の実装）では、実体への書き込みが一度も届かない。**外部のエディタで保存しても、編集モードで書き込んでも（IMP-107 は実体を書き換える）、表示が更新されない。**
>
> **ケース 2 を落とすと**、再読み込みでウィンドウタイトルとステータスのパスがリンクから実体へ変わる（IMP-141, IMP-190）。

> **ケース 14 と 15 が [BUG-014](../bugs/2026-09-14-bug-014-diagram-marker-spoofing.md) そのものである**（v1.0.0 から）。v1.0.0 の `lazy.js` と `copy.js` は `data-plantuml` / `data-source` の有無だけで判断していた。**15 は `!include` を含むブロックでも、同梱の PlantUML が通信しないため「待たされる」症状として出ない。** 図の器ができたかで見る。
>
> **この検査は鍵の「推測できなさ」を見ていない。** 鍵が変換のたびに作られること（IMP-102）は UT-116 が見る。ここで見るのは、**フロントエンドが鍵を照合していること**である。

### UT-901: テストを持たない要求の扱い **MUST**

上表で `—` となっている要求には、次の分類記号を付している。**単体テストの不足ではない。**

| 記号 | 分類 | 検証手段 |
| --- | --- | --- |
| GUI | GUI・フロントエンドの振る舞い | **描画**は描画スモークテスト（BR-054）、**操作は手動テスト（41 章）**。表示仕様書（20〜22）が期待する見た目を定める |
| PERF | 性能目標 | 測定条件（07 章 7.1）に基づく計測。単体テストで代替しない |
| ABSENCE | 「行わないこと」の要求 | 実装の不在で満たされる。テストでの証明は困難であり、レビューで担保する |
| BUILD | 構成・ビルド・CI の要求 | CI の実行そのものが検証となる |
| DESIGN | 設計判断・運用の記録 | 検証対象を持たない |
| TBD | **要求を追加したが、まだテストケースを書いていない** | 実装仕様（10〜13）が揃った後、テストケースを書く段階で、テストの ID か上の記号へ置き換える。**一時的な記号であり、実装に着手する前に残してはならない**（[90.6.5](90-traceability.md)） |

> [!NOTE]
> 性能目標（PERF）を単体テストで測ろうとすると、実行環境に依存する不安定なテスト（UT-035, UT-037）になる。ベンチマーク（`go test -bench`）を参考値として置くことは妨げないが、**合否の基準にはしない**。

> [!IMPORTANT]
> **`GUI` の検証手段を「描画スモークテストと手動確認」とひとまとめに書かない。**
> 描画スモークテスト（BR-054, E2E-109）が見るのは **BR-054 の表に挙げた描画の結果**（図・数式・画像・PlantUML の制限・本文の id・並べ替えの比較・目印の照合）だけであり、
> **クリックもキー入力もスクロールも行わない。** 検索バーのように「操作したときの振る舞い」を持つ
> 要求は、**手動テスト（41 章）だけが唯一の検証機会**である。
>
> ひとまとめに書くと、**手動テストのケース定義に穴があっても「スモークが見ているはず」と
> 誤解される。** 実際に FR-080 のボタン経路がそのまま通り抜けた
> （[調査報告](../bugs/2026-09-03-search-jump-buttons.md)）。

### UT-902: 対応表の網羅性 **MUST**

- 本表には**要求仕様書に定義されたすべての ID が 1 行ずつ現れる**。範囲表記（`FR-010〜FR-016` のような省略）を用いない。省略すると、要求が追加されたときに漏れが検出できなくなるためである。
- 要求を追加・削除した場合、本表を同じ変更で更新する（NFR-071）。
- 網羅性は機械的に検査できる。要求仕様書の見出しから抽出した ID の集合と、本表の第 1 列の集合が一致することを確認する。
