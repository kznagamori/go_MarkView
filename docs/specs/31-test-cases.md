# 31. 単体テスト仕様: テストケース

> 索引: [README](README.md) | 単体テスト: [30](30-test-policy.md) / **31**

本文書は、パッケージごとの単体テストケースを定める。書き方の規範と禁止事項は [30. 方針と禁止事項](30-test-policy.md) にある。

## 31.1 読み方

### UT-090: 表の形式 **MUST**

各ケースは以下の形式で記す。

```
### UT-nnn: <観点>
対象: <パッケージ>.<関数>   根拠: <要求 ID> / <実装 ID>

| # | 入力 | 期待 |
```

- 「根拠」に挙げた仕様が変わったら、そのケースも見直す（UT-010）。
- 表の各行は、テーブル駆動テスト（UT-014）の 1 ケースに対応する。行の説明文をそのままサブテスト名にしてよい。
- ここに挙げたものは**最低限**であり、これで十分という意味ではない。実装中に気づいた境界値は追加してよい。逆に、ここにないケースを削る場合は理由を残す。

## 31.2 document パッケージ（UT-1xx）

### UT-101: BOM と改行コードの正規化
対象: `document.Normalize`　根拠: FR-021 / IMP-103

| # | 入力（バイト列） | 期待 |
| --- | --- | --- |
| 1 | `EF BB BF` + `"# A"` | `"# A"`（BOM 除去）、`replaced=false` |
| 2 | `"# A"`（BOM なし） | `"# A"` そのまま |
| 3 | `"a\r\nb"` | `"a\nb"` |
| 4 | `"a\rb"` | `"a\nb"` |
| 5 | `"a\nb"` | `"a\nb"`（変化なし） |
| 6 | `"a\r\n\r\nb"` | `"a\n\nb"` |
| 7 | `EF BB BF` のみ | `""` |
| 8 | 中間に現れる `EF BB BF` | 除去しない（先頭のみが BOM） |
| 9 | 空のバイト列 | `""`、`replaced=false` |

### UT-102: 不正な UTF-8 の置換
対象: `document.Normalize`　根拠: FR-021 / IMP-103

| # | 入力 | 期待 |
| --- | --- | --- |

| 2 | 正常な UTF-8 の日本語 | 変化なし、`replaced=false` |
| 3 | UTF-16 の BOM（`FF FE`）で始まる | 変換せず、不正バイトを置換して返す。**エラーにしない** |
| 4 | 途中で切れたマルチバイト列 | U+FFFD に置換、`replaced=true` |

| # | 入力 | 期待 |
| --- | --- | --- |

| 3 | `"a"` | 1 |

| 5 | `"\n"` | 1 |
| 6 | `"a\r\nb"`（正規化後に判定） | 2 |

### UT-104: サイズ閾値の判定
対象: `document.Load`　根拠: FR-016 / IMP-101, IMP-102

| # | ファイルサイズ | `Confirmed` | 期待 |
| --- | --- | --- | --- |
| 1 | 1 KB | false | 正常に読み込む |
| 2 | ちょうど 10 MiB | false | 正常に読み込む（**閾値ちょうどは超過ではない**） |
| 3 | 10 MiB + 1 バイト | false | `ErrNeedsConfirm`。`*SizeError` に実サイズと閾値が入る |
| 4 | 10 MiB + 1 バイト | **true** | 正常に読み込む |
| 5 | ちょうど 50 MiB | true | 正常に読み込む |
| 6 | 50 MiB + 1 バイト | true | `ErrTooLarge`（`Confirmed` でも読み込まない） |
| 7 | 0 バイト | false | 正常に読み込む。空の HTML を返す |

> [!NOTE]
> ケース 2 と 5（閾値ちょうど）、ケース 6（`Confirmed` でも拒否）が、この機能で最も間違えやすい箇所である（UT-013）。

### UT-105: 拡張子の判定
対象: `mdfile.IsMarkdown`　根拠: FR-010, FR-031, FR-013 / IMP-105

| # | 入力 | 期待 |
| --- | --- | --- |
| 1 | `README.md` | true |
| 2 | `README.MD` | true（大文字小文字を区別しない） |
| 3 | `a.markdown` / `a.mdown` / `a.mkd` | いずれも true |
| 4 | `a.txt` / `a.png` / `a.go` | false |
| 5 | `md`（拡張子なし、名前が md） | false |
| 6 | `.md`（名前が拡張子のみ） | false |
| 7 | `a.md.txt` | false |
| 8 | 空文字列 | false |

### UT-106: 読み込みエラーの種別
対象: `document.Load`　根拠: FR-110 / IMP-021, IMP-102

| # | 状況 | 期待 |
| --- | --- | --- |
| 1 | 存在しないパス | `errors.Is(err, ErrNotFound)` が true |
| 2 | 読み取り権限のないファイル | `errors.Is(err, ErrPermission)` が true |
| 3 | 拡張子が Markdown でない | `errors.Is(err, ErrNotMarkdown)` が true |
| 4 | ディレクトリのパス | エラーを返す（`ErrNotMarkdown` または `ErrNotFound`） |

- エラーメッセージの文字列を比較しない。種別のみを `errors.Is` で判定する（UT-042）。
- ケース 2 は Windows では再現が難しい。`runtime.GOOS` で分岐し、Linux でのみ実行してよい。

### UT-202: 見出しアンカーの生成

| 3 | `概要` | `概要`（非 ASCII は保持） |
| 4 | `a   b`（連続空白 3 つ） | `a---b`。**空白 1 つにつき `-` 1 つ。まとめない**（MD-021 の 3） |
| 5 | `1. はじめに` | `1-はじめに` |

### UT-216: PlantUML の取り込み指令の検査
対象: `renderer.Render`　根拠: MD-084, NFR-032 / IMP-119

| 2 | `Alice -> Bob : !include a` | **拒まない**（行頭でなければ指令ではない。境界） |
| 3 | `' !include a`（コメント行） | **拒まない**（境界） |
| 4 | `!include foo.puml` | `data-plantuml` を**持たず**、`data-puml-error="include"` を持つ |
| 5 | `  !include foo.puml`（行頭に空白） | 同上（前の空白は許す） |
| 6 | `!INCLUDE FOO.PUML` | 同上（大小を区別しない） |
| 7 | `!includeurl http://example.com/a` | 同上 |
| 8 | `!includesub a.puml!X` | 同上。**`!include` の前方一致ではなく、独立した指令として判定する** |
| 9 | `!import a.puml` | 同上 |
| 10 | `!theme x from https://example.com/` | 同上（`from` を伴う） |
| 11 | `!include <C4/C4_Container>`（標準ライブラリ） | 同上（MD-083。描けないものをエラー図ではなく理由で返す） |
| 12 | 指令を含むブロック**だけ**の文書 | **`NeedsPlantUML` が false**（IMP-119。読む必要の無い 5 MiB を読ませない） |
| 13 | 指令を含むブロックと正常なブロックの両方 | `NeedsPlantUML` が true。**指令のブロックだけが除外される** |

> [!IMPORTANT]
> **ケース 1・2・3 を欠かさない。** 「`!include` という文字列があれば拒む」実装でもケース 4〜11 はすべて通る。**拒んではいけないものを拒んだことは、拒む側のケースでは検出できない。**

### UT-405: 監視対象の切り替え
対象: `watcher.Watch`　根拠: NFR-020 / IMP-140

| # | 操作 | 期待 |
| --- | --- | --- |
| 1 | A を監視 → B を監視 → A を変更 | イベントが届かない（A の監視が解除されている） |

> 解除漏れが表面化するのは OS の監視数の上限に達したときであり、テストで再現するのは現実的でない。監視中のディレクトリを削除できるかでも判別できない（fsnotify は削除を許す共有モードでハンドルを開く）。**この 1 点はレビューで担保する。**

### UT-901: テストを持たない要求の扱い **MUST**

上表で `—` となっている要求には、次の分類記号を付している。**単体テストの不足ではない。**

| 記号 | 分類 | 検証手段 |
| --- | --- | --- |
| GUI | GUI・フロントエンドの振る舞い | **描画**は描画スモークテスト（BR-054）、**操作は手動テスト（41 章）**。表示仕様書（20〜22）が期待する見た目を定める |
| PERF | 性能目標 | 測定条件（07 章 7.1）に基づく計測。単体テストで代替しない |
| ABSENCE | 「行わないこと」の要求 | 実装の不在で満たされる。テストでの証明は困難であり、レビューで担保する |
| BUILD | 構成・ビルド・CI の要求 | CI の実行そのものが検証となる |
| DESIGN | 設計判断・運用の記録 | 検証対象を持たない |

> [!NOTE]
> 性能目標（PERF）を単体テストで測ろうとすると、実行環境に依存する不安定なテスト（UT-035, UT-037）になる。ベンチマーク（`go test -bench`）を参考値として置くことは妨げないが、**合否の基準にはしない**。

> [!IMPORTANT]
> **`GUI` の検証手段を「描画スモークテストと手動確認」とひとまとめに書かない。**
> 描画スモークテスト（BR-054, E2E-109）が見るのは **Mermaid / PlantUML / 数式が描けたか**だけであり、
> **クリックもキー入力もスクロールも行わない。** 検索バーのように「操作したときの振る舞い」を持つ
> 要求は、**手動テスト（41 章）だけが唯一の検証機会**である。
>
> ひとまとめに書くと、**手動テストのケース定義に穴があっても「スモークが見ているはず」と
> 誤解される。** 実際に FR-080 のボタン経路がそのまま通り抜けた
> （[調査報告](../bugs/2026-09-03-search-jump-buttons.md)）。

### UT-902: 対応表の網羅性 **MUST**

- 本表には**要求仕様書に定義されたすべての ID が 1 行ずつ現れる**。範囲表記（`FR-010〜FR-016` のような省略）を用いない。省略すると、要求が追加されたときに漏れが検出できなくなるためである。
- 要求を追加・削除した場合、本表を同じ変更で更新する（NFR-071）。
- 網羅性は機械的に検査できる。要求仕様書の見出しから抽出した ID の集合と、本表の第 1 列の集合が一致することを確認する。
